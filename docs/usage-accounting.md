# Учёт расхода

После **каждого** прогона ревью review-agent дописывает одну строку в
`<work_dir>/usage/ledger.jsonl`. Это касается прогонов по расписанию,
`poll --all`, интерактивного `poll` и ручного режима, а также упавших и
прерванных. Учёт никогда не влияет на ревью: если расход собрать не
удалось, отчёт всё равно публикуется, а в записи остаётся причина.
Выключается учёт через `usage.enabled: false` ([configuration.md](configuration.md#usage)).

## Откуда токены

После завершения харнесса review-agent выполняет (только чтение)
`opencode --version`, `usage.session_list_command` и
`usage.session_export_command`, а затем находит сессию прогона по пути его
worktree. Дочерние сессии субагентов находятся рекурсивно (глубина до 5,
не больше 50 сессий). Их токены входят в итог, а в записи есть разбивка
по каждой сессии. Для подписки OpenCode пишет `cost: 0`, поэтому деньги
считает сводка, а не журнал.

## Запись журнала

Имена полей — OpenTelemetry `gen_ai.*` (semantic conventions для
generative AI) плюс собственные `review.*`. Каждый ключ присутствует в
каждой записи, неизвестное значение — `null`.

| Поле | Что это |
| --- | --- |
| `schema`, `time` | версия формата записи, время записи |
| `review.run_id`, `review.source` | какой прогон; `poll` или `manual` |
| `review.project`, `review.mr.iid`, `review.base_sha`, `review.head_sha` | что ревьюилось |
| `gen_ai.provider.name`, `gen_ai.request.model`, `review.reasoning_effort`, `review.skills` | конфиг прогона (у skill'ов — только имена файлов) |
| `review.harness.name`, `review.harness.version` | харнесс и его версия |
| `review.outcome`, `review.duration_ms` | `succeeded` / `failed` / `interrupted`, общее время |
| `gen_ai.usage.input_tokens` | **весь** вход, включая кэш (как в OTel) |
| `gen_ai.usage.cache_read.input_tokens`, `gen_ai.usage.cache_creation.input_tokens` | чтение и запись кэша |
| `gen_ai.usage.output_tokens`, `review.usage.reasoning_tokens`, `review.usage.steps` | выход, reasoning, шаги модели |
| `review.sessions[]` | каждая сессия: id, parent, agent, токены, длительность |
| `review.change.files`, `review.change.lines_added`, `review.change.lines_deleted`, `review.change.commits` | размер изменения между base и head (считает review-agent, агенту не передаётся) |
| `review.findings` | находки Blocker / Major / Minor — **оценка** по меткам в тексте отчёта |
| `review.quota` | остаток лимитов до и после ревью — только у интерактивно измеренных |
| `review.usage.missing_reason`, `review.usage.format_problems` | почему нет токенов; что в ответе OpenCode было не так |

В журнале **нет** текста промпта и отчёта, заголовка и описания MR, кода и
кредов — только числа и идентификаторы.

**Находки** считаются по меткам `SEV: Major`, `[Minor]`, `**Blocker**`,
`Major:` в начале пункта и по заголовкам-группам уровня (`### Major` и
пункты под ним). Источник правды — сам отчёт.

## Если OpenCode ответил не так

Другая версия OpenCode (проверено на 2.0.21), нет поля токенов, строка
вместо числа, непонятный вывод `session list` — всё это **не ошибка**.
Ревью и код выхода не меняются, но в консоли (если она есть) и в логе
прохода появляется `Предупреждение: Учёт расхода: неожиданный ответ
opencode: ...` — по одному на проход для каждого вида проблемы. Затронутые
числа в записи становятся `null`, а сводка показывает, сколько таких
записей за период.

Что делать: сравнить запись журнала с `opencode session export <id>` этой
сессии. Если формат действительно изменился, нужна правка разбора в
`src/review_agent/usage_source.py`.

«Сессия прогона не найдена» (например, прогон прерван до старта харнесса)
пишется только в лог. Если так со всеми прогонами — добавьте `--standalone`
в `usage.session_list_command`.

Сверка с OpenCode: `opencode stats --json --project <projectID> --days 7`
даёт агрегаты по проекту. Сумма по журналу за тот же период должна с ними
сходиться, если в этом проекте не было ручных сессий OpenCode.

## Замер квоты подписки

Проценты лимитов подписки (у ChatGPT — окна «5 часов» и «неделя»)
review-agent получить сам не может (см. бэклог в AGENTS.md). Поэтому они
вводятся вручную, и только там, где их можно честно привязать к одному
ревью: в **интерактивном** `review-agent poll` (без `--all`) и в ручной
команде из консоли.

```
Замер квоты openai (до ревью): сколько % лимита ОСТАЛОСЬ сейчас (как в UI подписки). Enter — пропустить.
  окно 5h, осталось %: 88
  окно week, осталось %: 60
... ревью ...
Замер квоты openai (после ревью): ...
  окно 5h, осталось %: 79
  окно week, осталось %: 58
```

- Вводится **оставшийся** процент, как в UI ChatGPT/Codex. В журнал
  пишется использованный (`100 − остаток`): в примере ревью заняло 9 % окна
  5h и 2 % недели.
- Вопросы задаются сразу перед запуском харнесса и сразу после него, до
  публикации.
- Enter пропускает окно. Не число или значение вне 0–100 — вопрос
  повторяется.
- В `--all`, под Task Scheduler и без консоли вопросов **нет никогда**.
- Окна настраиваются в `usage.quota_windows`.
- Во время замера **не работайте параллельно** в ChatGPT/Codex: лимиты
  общие на аккаунт, и параллельная работа завысит долю ревью.

## Сводка: review-agent usage

Команда читает журнал, скачивает актуальный справочник цен и **печатает
сводку в консоль**. Сама она ничего не сохраняет, кроме копии справочника
цен. Нужен файл — перенаправьте вывод.

```bash
review-agent usage                          # всё время, по каждому ревью, короткая таблица
review-agent usage --by model               # по модели и effort — для сравнения моделей
review-agent usage --by day                 # по дням
review-agent usage --by mr --since 2026-10-01 --until 2026-10-07
review-agent usage --since 30d              # последние 30 дней
review-agent usage --wide                   # таблица со всеми колонками
review-agent usage --format csv > usage.csv # все колонки, для Excel
review-agent usage --format json
```

| Флаг | Значения | По умолчанию |
| --- | --- | --- |
| `--since` | `<N>d` (последние N дней) или `YYYY-MM-DD` | весь журнал |
| `--until` | `YYYY-MM-DD`, включительно | сейчас |
| `--by` | `review`, `mr`, `model`, `day` | `review` |
| `--format` | `table`, `csv`, `json` | `table` |
| `--wide` | таблица со всеми колонками (CSV и JSON — всегда все) | выкл. |
| `--config` | путь к конфигу | `config.yaml` |

Пример вывода:

```
Период: всё время — сейчас
Ревью: 1; без данных о расходе: 0; без цены (не вошли в сумму $): 0; с проблемами формата харнесса: 0
Справочник цен: https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json (2026-10-04 17:19)

when              mr   model         effort  tokens_k  min  lines  B/M/m  usd     5h %      week %
----------------  ---  ------------  ------  --------  ---  -----  -----  ------  --------  --------
2026-10-04 17:01  511  gpt-5.6-luna  low     134.2     1.3  424    0/1/2  0.0238  0 (изм.)  0 (изм.)
```

**Шапка**: период; сколько ревью и сколько из них неполных (без данных о
расходе, без цены, с проблемами формата OpenCode) — хорошо, когда везде
нули; откуда и когда взяты цены («копия от …» — сети не было, цены могут
быть старыми); предупреждения.

**Короткая таблица** (по умолчанию):

| Колонка | Что это |
| --- | --- |
| `when`, `mr`, `model`, `effort` | когда, какой MR, чем. При `--by mr/model/day` — ключ группы и `reviews` (число ревью) |
| `tokens_k` | все токены, тысячи: вход вместе с кэшем + выход + reasoning |
| `min` | время ревью, минуты |
| `lines` | изменённые строки MR (+ и −) |
| `B/M/m` | находки Blocker / Major / Minor |
| `usd` | API-эквивалент в долларах |
| `<окно> %` | доля лимита подписки: `(изм.)` — измерено вашим вводом, `(оц., n=N)` — оценка по N замерам той же модели; пусто — замеров для этой модели нет |

**`--wide`, CSV и JSON** — все колонки: токены по видам (`fresh_input` —
вход без кэша, `cache_read`, `cache_write`, `output`, `reasoning`),
`duration_min`, `files`, `lines`, `blocker` / `major` / `minor`, `cost_usd`,
`price_source` (`catalog` / `override` / `catalog (копия от …)`), для
каждого окна `share_<окно>_pct` и `share_<окно>_note`. При `--by review` к
ним добавляются `run_id`, `project`, `outcome`, `provider`.

### API-эквивалент

`cost_usd` — сколько стоили бы эти токены по публичным ценам API: вход без
кэша, чтение кэша, запись кэша, выход + reasoning, каждый по своей цене.
Цены берутся из справочника `usage.price_catalog`, который **загружается
заново при каждом запуске**, поэтому история всегда пересчитывается по
актуальным ценам. `usage.price_overrides` перекрывает справочник. Без сети
используется последняя сохранённая копия (`usage/price-catalog.json`), и
выводится предупреждение с её датой. Модель без цены показывается как
`n/a` и в сумму не входит. Если модели нет в справочнике, добавьте её в
`price_overrides` (например, скопировав запись ближайшей API-модели) и
явно оговаривайте это допущение, показывая цифры.

### Доля лимитов

- `измерено` — у ревью с замером (после − до).
- `оценка, замеров N` — для остальных ревью **той же** группы
  «провайдер + модель + effort»: пересчёт по коэффициенту из замеров этой
  группы (вес — API-доллары ревью, а без цены — сумма токенов).
- У группы без замеров доли нет, и шапка подскажет, для какой модели нужен
  интерактивный прогон.
- Если окно сбросилось во время ревью (после < до), замер невалиден и в
  расчёт не идёт.
- Проценты в UI целые, одно ревью даёт 0–2 %, поэтому оценка точнее с
  каждым замером.
