# Технические решения

Решения, которые выглядят странно, пока не знаешь, какой сбой без них
случается. Каждое решение проверено на реальном окружении: Windows,
OpenCode 2.0.21, облачный провайдер, боевой GitLab. Подробные протоколы
проверок лежат в `validation-notes.md` архивов OpenSpec
(`openspec/changes/archive/<дата>-<change>/`). Архитектурные принципы
(агентный харнесс, минимальный контекст, состояние в GitLab, отказ от
готовых ботов) описаны в [AGENTS.md](../AGENTS.md), п.3–6.

Формат: **что сделано** → почему → где проверено → где реализовано.

## denylist вместо allowlist

**Что:** `permission.bash` в `opencode.json` — список запрещённых шаблонов
(`safety.denied_bash_patterns`) без общего `"*"`.

**Почему:** задумывался allowlist (разрешить read-only `git`/`rg`, остальное
запретить через `"*": "deny"`). Но в OpenCode 2.0.21 `"*": "deny"` делает
bash-инструмент **полностью недоступным**, включая шаблоны с `"allow"`, а
без общего правила всё неперечисленное разрешено. Запретить всё, кроме
списка, нельзя. Denylist слабее (команду можно сформулировать иначе), но
это то, что реально работает. Живая проверка: `git log` и `git status`
выполняются, `npm *` блокируется с `Permission denied: shell` без побочных
эффектов. Компенсация: worktree одноразовый, у агента нет прав на запись в
GitLab и нет веб-доступа.

**Проверено:** `2026-10-02-core-review-engine/validation-notes.md`.
**Где:** `harness_config.py`, `config.py` (`SafetyConfig`).

## opencode run --standalone

**Что:** флаг `--standalone` в `harness.command` обязателен.

**Почему:** без него `opencode run` может подключиться к долгоживущему
фоновому сервису, который не знает про только что созданный worktree
(каждый прогон — новая папка) и падает с `Agent not found` на только что
сгенерированном агенте.

**Проверено:** `2026-10-02-core-review-engine/validation-notes.md`.
**Где:** `config.example.yaml`, `harness.py`.

## Промпт через --file

**Что:** промпт пишется в файл и передаётся `--file "{prompt_file}"` плюс
короткая однострочная фраза. Позиционный `"{prompt}"` поддерживается, но
использовать его нельзя.

**Почему:** на Windows `opencode` из PATH — это npm-шим `opencode.CMD`, а
`.CMD` исполняется через `cmd.exe`, который режет командную строку по
переводу строки. Многострочный промпт доходил до модели обрезанным до
первой строки («Role: Senior Software Engineer.»), модель отвечала без
единого вызова инструмента, а процесс завершался с кодом 0 — без видимой
ошибки.

**Проверено:** `2026-10-02-core-review-engine/validation-notes.md`
(бенчмарк-MR). **Где:** `harness.py`, `pipeline.py`, `config.example.yaml`.

## Явная кодировка UTF-8

**Что:** все `subprocess.run` с текстовым выводом (харнесс, git, glab) идут с
`encoding="utf-8"`. Файлы review-agent пишутся в UTF-8.

**Почему:** без этого Python на Windows декодирует вывод кодовой страницей
консоли, и русский текст отчёта превращается в мохибейк.

**Проверено:** `2026-10-02-core-review-engine/validation-notes.md`.
**Где:** `harness.py`, `worktree.py`, `gitlab.py`.

## reasoning_effort: null

**Что:** ключ `provider.reasoning_effort` обязателен, но может быть `null`.
Тогда суффикс `#variant` к модели не добавляется.

**Почему:** reasoning effort задаётся явно, а не остаётся на усмотрение
харнесса: в исходном исследовании это была незакрытая переменная. Но
variant есть не у всех моделей: для локальных моделей без вариантов любой
суффикс даёт `Variant unavailable`. `null` явно означает «неприменимо»,
пустая строка запрещена как двусмысленная.

**Проверено:** `2026-10-02-core-review-engine` (design.md,
validation-notes.md). **Где:** `config.py`, `harness.py`.

## Харнесс без stdin

**Что:** `opencode run` запускается со `stdin=DEVNULL`.

**Почему:** `opencode run` читает дополнительный ввод из stdin, если тот не
консоль, и ждёт EOF. Запущенный из оболочки с открытым pipe (как в CI или
из некоторых обёрток), прогон висел бесконечно.

**Проверено:** `2026-10-04-review-usage-accounting/validation-notes.md`.
**Где:** `harness.py`.

## Консоль, а не isatty()

**Что:** интерактивный режим `poll` проверяет, что stdin — настоящий
консольный дескриптор (`GetConsoleMode` на Windows), а не только
`isatty()`.

**Почему:** на Windows `isatty()` истинен для `NUL`. `review-agent poll < NUL`
без `--all` считал себя интерактивным, получал пустой ввод и молча выходил
с кодом 0. Теперь без консоли — сразу код 2 и подсказка про `--all`.

**Проверено:** `2026-10-02-gitlab-polling-and-publishing/validation-notes.md`.
**Где:** `polling.py`.

## pythonw вместо conhost --headless

**Что:** задача Task Scheduler по умолчанию запускает
`pythonw.exe -m review_agent poll --all ...` того же Python, что и
`review-agent.exe`.

**Почему:** `review-agent.exe` — консольное приложение, и окно всплывало бы
каждые N минут, а его закрытие обрывает проход. `conhost.exe --headless`
прячет окно, но **всегда** возвращает 0, поэтому Планировщик не увидит
сбоев. `pythonw` окна не создаёт и передаёт код выхода как есть.

**Проверено:** `2026-10-02-scheduling-and-multi-repo-config/validation-notes.md`.
**Где:** `scripts/register-task.ps1`.

## CREATE_NO_WINDOW только без консоли

**Что:** дочерние процессы (git, glab, opencode) получают `CREATE_NO_WINDOW`,
только если у самого review-agent нет консоли.

**Почему:** под `pythonw` каждый консольный дочерний процесс открыл бы своё
видимое окно. Но в обычном терминале флаг вредит: дети перестают делить
консоль, и Ctrl+C не доходит до всего дерева (`opencode` — это
`cmd.exe → node`, и убийство только `cmd.exe` оставило бы `node` сиротой).

**Проверено:** `2026-10-04-managed-repo-cache/validation-notes.md` (клон без
консоли). **Где:** `proc.py`.

## Авторизация кэш-клонов через glab

**Что:** в конфиг bare-клона записываются пустой `credential.helper=` и затем
`!'<путь к glab>' auth git-credential`. Сетевые git-команды идут с
`GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`.

**Почему:** нужен один источник кредов — уже авторизованный `glab`, а не
отдельный токен в конфиге. Пустой helper сбрасывает унаследованный Git
Credential Manager, который иначе открыл бы окно логина (под
планировщиком его никто не увидит, и проход повис бы). Переменные
окружения заставляют git падать сразу, а не ждать ввода. Токен на диск не
пишется: `glab` достаёт его из своего хранилища при каждом fetch. В
пользовательский `local_repo` хелпер не пишется.

**Проверено:** `2026-10-04-managed-repo-cache/validation-notes.md` (в т.ч.
без консоли). **Где:** `repo_source.py`.

## opencode.json в корне worktree

**Что:** конфиг агента пишется в корень временного worktree, а не в
отдельную папку.

**Почему:** OpenCode берёт проектный конфиг из текущей папки, а флага вроде
`--agents-file` нет. Запись безопасна: worktree одноразовый, а имя
`opencode.json` не перекрывает `AGENTS.md` / `CLAUDE.md` ревьюируемого
репозитория.

**Проверено:** `2026-10-02-core-review-engine/validation-notes.md`.
**Где:** `harness_config.py`.

## Ссылки на коммит, а не на ветку

**Что:** пути в отчёте переписываются в `<проект>/-/blob/<head_sha>/<путь>#L<n>`
(для удалённых в MR файлов — на base). Это детерминированная
постобработка, промпт о ссылках ничего не говорит.

**Почему:** ссылка на ветку съезжает после новых пушей и умирает после
мержа и удаления ветки. Указание формата в промпте — лишнее ограничение
поведения модели, которое может снизить recall (AGENTS.md, п.3).
Inline-код становится ссылкой, только если путь точно есть в коммите
(`git ls-tree`), чтобы не превращать в ссылки идентификаторы.

**Проверено:** `2026-10-04-gitlab-file-links/validation-notes.md`.
**Где:** `file_links.py`, `polling.py`.

## Claim редактируется в отчёт

**Что:** перед ревью публикуется claim-комментарий, после ревью **тот же**
комментарий редактируется в отчёт. Из двух одновременных claim'ов
побеждает меньший id комментария.

**Почему:** lock видит только свою рабочую папку, а проходы могут идти с
разных машин. Claim в GitLab — единственное общее место. Редактирование
оставляет на MR один комментарий бота. Порядок id задаёт GitLab, а не часы
машин. Минус: письмо-уведомление GitLab приходит с текстом claim'а, потому
что на редактирование письма нет.

**Проверено:** `2026-10-02-scheduling-and-multi-repo-config/validation-notes.md`.
**Где:** `publishing.py`, `polling.py`.

## Промпт — Jinja2-шаблон

**Что:** промпт рендерится Jinja2 из файла шаблона. Встроенный
`prompts/default.md.j2` разбит на блоки и даёт базовый промпт посимвольно.
В Python нет ни строчки текста промпта, только значения переменных.

**Почему:** промпт нужно менять для другого стека без правки кода, вместе
с формулировками секций, которые зависят от данных (инструкции, docs,
skills). `string.Template` не умеет условий, поэтому формулировки секций
остались бы в коде. У Mustache нет наследования блоков, Mako менее
распространён. Jinja2 (Pallets) — де-факто стандарт шаблонов в Python
(Ansible, dbt, chat-templates HuggingFace). Наследование блоков позволяет
заменить, например, только чек-лист и сохранить остальную проверенную
методологию. Базовый промпт — эмпирически лучший baseline (AGENTS.md
п.3), поэтому совпадение «до символа» закреплено golden-тестом против
прежнего рендерера на всех комбинациях входов.

**Проверено:** `tests/test_prompt.py` (golden-тест); живой прогон — в
`validation-notes.md` архива `configurable-review-prompt`.
**Где:** `prompt.py`, `prompts/default.md.j2`.

## Переопределение prompt по ключам

**Что:** ключи `prompt` (`template`, `instruction_files`, `docs_dirs`)
проекта, глобальной секции и встроенных значений объединяются по
отдельности, а не блоком, как `provider`.

**Почему:** `provider` — связанная тройка (модель без своего
reasoning effort бессмысленна), а ключи `prompt` независимы. Бэкенд-проекту
обычно нужен свой шаблон при общих кандидатах инструкций. Блочная замена
заставила бы копировать списки в каждый проект.

**Проверено:** `tests/test_config.py`.
**Где:** `config.py` (`merge_prompt`).

## Шаблон только из конфига

**Что:** шаблон загружается из файла, указанного в конфиге, и из пакета.
Загрузчик не видит worktree ревьюируемого MR. Файлы инструкций
репозитория по-прежнему передаются агенту путём, а не встраиваются.

**Почему:** содержимое worktree контролирует автор MR. Шаблон оттуда
позволил бы ему переписать методологию ревьюера (prompt injection на
уровне инструкций, а не данных).

**Проверено:** `tests/test_prompt.py`.
**Где:** `prompt.py` (`make_environment`).

## Проверка шаблона пробным рендером

**Что:** шаблон проверяется рендером с метками в значениях переменных, а
не статическим разбором. Неизвестные имена собирает `Undefined`, который
записывает их, а не падает. В боевом рендере — `StrictUndefined`.

**Почему:** статический разбор (`jinja2.meta`) не видит переменных
родителя при `{% extends %}` и не знает, что реально попало в текст. По
меткам видно и `{{ path.name }}`, и переменные из встроенного родителя.
Записывающий `Undefined` выдаёт все неизвестные имена за один раз, а не
первое. Проверка выполняется до lock и GitLab, поэтому отказ не оставляет
claim'ов.

**Проверено:** `tests/test_prompt_check.py`, `tests/test_polling.py`,
`tests/test_cli.py`.
**Где:** `prompt_check.py`, `polling.py`, `cli.py`.
