# Proposal

## Why

Сейчас для каждого проекта в `gitlab.projects` обязателен `local_repo` —
путь к заранее склонированному человеком репозиторию. Для запуска в
GitLab CI (и вообще на новой машине) это лишняя ручная подготовка:
идентификатор проекта (`path`) и хост GitLab в конфиге уже есть, и этого
достаточно, чтобы review-agent сам получил копию репозитория. Кроме того,
в давно не обновлявшемся клоне может не оказаться base-коммита MR — его
сейчас подтягивает только fetch по SHA, который зависит от настроек
сервера.

## What Changes

- `local_repo` у проекта становится **необязательным**. Если он указан —
  поведение как сейчас (worktree во временной папке, в клоне только fetch).
  Если не указан — review-agent использует собственный кэш-клон проекта.
- Новый **управляемый кэш репозиториев** `<work_dir>/repos/`: bare-клон по
  HTTPS, URL выводится из `gitlab.hostname` + `path`
  (`https://<hostname>/<path>.git`). Зависимости не устанавливаются,
  рабочих файлов в кэше нет. Клонирование ленивое — только когда MR этого
  проекта реально берётся в ревью.
- Авторизация git для кэша — через уже авторизованный `glab`
  (`glab auth git-credential` как credential helper, только для этого
  кэш-клона). Токены не записываются ни в конфиг, ни в URL, ни на диск.
- Перед каждым ревью **актуализируются ветки, участвующие в MR**: одним
  `git fetch` — целевая ветка MR и `refs/merge-requests/<iid>/head`
  (голова исходной ветки, в том числе из форка). Это касается и
  `local_repo`, и кэша; локальные ветки и рабочие файлы пользовательского
  клона по-прежнему не трогаются.
- Кэш-клоны живут дольше прохода и удаляются, если не использовались
  дольше `storage.repo_retention_days` (по умолчанию 30 дней; `null` —
  не удалять). Worktree, как и сейчас, живут в `tmp/` и удаляются сразу
  после ревью — отдельно от папки репозиториев.
- `remote` у проекта имеет смысл только вместе с `local_repo`; без него —
  ошибка конфигурации.
- Вне объёма: ручной режим `review-agent --repo` (остаётся только с
  локальным путём), SSH, несколько хостов GitLab, partial clone.

Не BREAKING: существующие конфиги с `local_repo` работают без изменений.

## Capabilities

### New Capabilities
- `managed-repo-cache`: получение и хранение собственных клонов
  репозиториев проектов без `local_repo` — вывод URL, клонирование с
  авторизацией через `glab`, атомарность, повторное использование и
  удаление неиспользуемых клонов по сроку.

### Modified Capabilities
- `review-polling-run`: требование «Review runs against a configured
  local clone» заменяется на «ревью идёт по репозиторию-источнику
  проекта» (`local_repo` или кэш) с обязательной актуализацией целевой
  ветки и головы MR перед ревью.
- `local-artifact-lifecycle`: рабочая папка включает кэш репозиториев;
  кэш не считается временным и не удаляется после ревью, но истекает по
  собственному сроку; уборка остатков прерванных прогонов охватывает и
  кэш-клоны (осиротевшие worktree, недокачанные клоны).

## Impact

- Код: `config.py` (необязательный `local_repo`, `storage.repo_retention_days`,
  проверка `remote`), новый модуль источника репозитория (кэш + подготовка
  к MR), `worktree.py` (fetch нескольких refspec), `gitlab.py`
  (`target_branch` в ответе `get_diff_refs`), `polling.py` (шаг подготовки
  репозитория вместо голого `fetch_fn`, housekeeping по кэшу),
  `housekeeping.py` (раскладка `repos/`, истечение кэша).
- Внешние инструменты: `glab` теперь используется и как git credential
  helper — нужна версия с `glab auth git-credential` (проверить вживую).
- Документация: `config.example.yaml`, README, AGENTS.md (дорожная карта).
- Диск: кэш хранит полные bare-клоны проектов без `local_repo`.
