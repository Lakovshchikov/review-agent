# Design

## Context

Мотивация описана в proposal.md (раздел Why), требования — в
`specs/review-publishing/spec.md`.

Как всё устроено сейчас:

- `pipeline.run_review` создаёт worktree по пути
  `<work_dir>/tmp/<run_id>/worktree` (`worktree.create_worktree`, путь
  абсолютный после `.resolve()`), передаёт этот путь в промпт и после
  прогона удаляет worktree. Наружу возвращается `ReviewResult(report,
  harness_stderr, run_id)` — пути worktree в нём нет.
- `polling._review_one` берёт отчёт без изменений, передаёт его в
  `publishing.format_comment(report=…)` и публикует. На этом шаге уже
  известны `refs.head_sha`/`refs.base_sha` (`DiffRefs`),
  `meta.web_url` (`https://<host>/<group>/<proj>/-/merge_requests/<iid>`)
  и `prepared.path`, то есть репозиторий (локальный или bare-кэш), в
  котором есть оба коммита: перед ревью их подтягивает
  `ensure_commits_available`.
- В реальных отчётах встречаются два формата ссылок (proposal.md):
  markdown-ссылка на абсолютный путь worktree с `#L<n>` и путь без
  ссылки в inline-коде вида `` `path:n` `` или `` `path:n-m` ``.

## Goals / Non-Goals

**Goals:**
- Переписывание детерминированное и не зависит от модели: результат один
  и тот же, какой бы формат ссылок модель ни выбрала из двух известных.
- Ссылка не может сломать публикацию: при любой ошибке отчёт уходит хотя
  бы с относительными путями.

**Non-Goals:**
- Ссылки на вкладку Changes MR (diff-якоря GitLab `#<sha1(path)>_<old>_<new>`).
  Они работают только для изменённых строк, и формат якоря недокументирован.
- Проверка, что номер строки существует в файле. Номер переносится как
  есть.
- Изменения промпта и формата отчёта модели.
- Ссылки в отчёте ручного режима `review-agent` (локальный файл): он
  остаётся как есть.
- Распознавание путей в обычном тексте вне inline-кода и ссылок
  (кроме удаления абсолютного пути worktree): слишком велик риск
  ложных срабатываний.

## Decisions

### 1. Переписываем после прогона, промпт не трогаем

Альтернатива — попросить модель в промпте писать ссылки в нужном виде
(дать ей URL проекта и SHA). Отклонена по двум причинам. По AGENTS.md п.3
любое добавление в промпт может повлиять на recall, и это пришлось бы
проверять на бенчмарке. Кроме того, модель всё равно иногда отступает от
формата, а постобработку можно покрыть тестами. Переписывание — чистая
функция над текстом.

### 2. Ссылка закреплена на head SHA

Решение пользователя: `/-/blob/<head_sha>/…`, а не `/-/blob/<source_branch>/…`.
Номера строк из отчёта относятся ровно к этому коммиту, и ссылка
продолжает работать после мержа и удаления ветки. Отчёт уже называет
отревьюенный коммит в заголовке (`format_comment`), так что такие ссылки
с ним согласованы.

### 3. Web-URL проекта берётся из `web_url` MR

`meta.web_url.split("/-/merge_requests/")[0]`. Это канонический адрес
проекта по версии GitLab, с учётом подгрупп, нестандартного порта и
переименований. Отдельный вызов API не нужен. Запасной вариант, если
разделителя в URL нет: `https://<gitlab.hostname>/<project.path>`.

### 4. Новый модуль `file_links.py` — чистая логика

`link_file_references(report, *, worktree_path, project_url, head_sha,
base_sha, head_paths, base_paths) -> str`. Модуль ничего не читает и не
вызывает. Наборы путей `head_paths`/`base_paths` могут быть `None`, если
неизвестны. Вызов встраивается в `polling._review_one` прямо перед
`format_comment`, так что dry-run получает тот же текст. Сам
`format_comment` не меняется: заголовок и маркер к ссылкам отношения не
имеют.

Порядок обработки отчёта:

1. **Fenced-блоки кода** (```` ``` ````/`~~~`) вырезаются из обработки.
   Внутри них только удаляется префикс worktree (`<worktree>/src/a.ts` →
   `src/a.ts`).
2. **Markdown-ссылки** `[text](target)`. Если `target` после нормализации
   (см. п.5) начинается с пути worktree, относительный путь и якорь
   (`#L13`, `#L13-L20`, `#L13-20`) превращаются в URL GitLab. Если этот
   путь известен по `head_paths`, ссылка ведёт на head; если только по
   `base_paths`, то на base; если не найден нигде, ссылка снимается и
   остаётся `text`. Если наборы путей неизвестны (`None`), ссылка ведёт
   на head без проверки: путь пришёл из worktree, то есть из head. Из
   `text` тоже удаляется префикс worktree, если он там есть. Ссылки на
   http(s) и прочие адреса не трогаются. Относительная ссылка
   (`[x](src/a.ts#L3)`) переписывается по тем же правилам, но только если
   путь точно найден в одном из коммитов; иначе она остаётся как есть.
3. **Inline-код** `` `X` `` вне ссылок. `X` разбирается целиком как путь
   без двоеточий, за которым может идти `:<start>` или `:<start>-<end>`.
   Пробелы в пути допустимы: бывают и в реальных путях, а лишнего всё
   равно не совпадёт, потому что путь сверяется с файлами коммита
   точно.
   Префикс worktree перед этим удаляется, и `./` в начале пути тоже. Код
   превращается в ссылку только при точном совпадении `path` с элементом
   `head_paths` (иначе `base_paths`). Именно эта проверка защищает от
   ложных срабатываний на `` `isFallback` `` или `` `useGetGroup()` ``. Если
   наборы путей неизвестны, inline-код не трогается.
4. **Остаток текста.** Все оставшиеся вхождения префикса worktree
   удаляются.

Формат URL: `<project_url>/-/blob/<sha>/<quote(path, safe="/")>`, затем
`#L<start>` или `#L<start>-<end>`. Если `end <= start`, используется
только `#L<start>`. Директории (`git ls-tree -t` отдаёт и их) получают
`/-/tree/<sha>/<path>` без якоря.

### 5. Нормализация пути worktree

Модель может написать путь с прямыми или обратными слэшами, с другим
регистром буквы диска, с префиксом `file:///` или в URL-кодировке
(`%20`). Префикс ищется регулярным выражением, построенным из пути
worktree: каждый разделитель соответствует `[\\/]`, сравнение без учёта
регистра, допускаются необязательные `file:///` и `/` перед буквой диска.
Перед сравнением `target` ссылки декодируется через `unquote`. Без учёта
регистра сравнивается только сам префикс worktree, а относительная часть
пути сохраняет регистр: в git регистр значим.

### 6. Пути коммитов через `git ls-tree`

`worktree.list_tree_paths(repo_path, sha) -> set[str]` выполняет
`git -c core.quotepath=off ls-tree -r -t -z --name-only <sha>` с
`encoding="utf-8"`. Это урок Change 1: без явной кодировки Windows
портит вывод, а `-z` защищает от экранирования не-ASCII путей. Команда
read-only, работает и в bare-кэше, сеть не нужна: оба коммита уже
подтянуты перед ревью. Функция вызывается для head и для base всегда,
без ленивой логики: это два быстрых локальных вызова.

Альтернатива — собрать список файлов в `pipeline` через `git ls-files`,
пока worktree ещё существует. Отклонена: так можно получить только head,
`pipeline` разросся бы обязанностями публикации, а `prepared.path` и так
доступен в `polling`.

### 7. `ReviewResult.worktree_path`

Новое поле `worktree_path: Path | None = None`. Значение по умолчанию
нужно, чтобы не сломать тестовые подделки `ReviewResult(...)` в
`test_polling.py`. К моменту публикации worktree уже удалён, но путь
нужен только как текстовый префикс для поиска. Если пути нет (`None`),
шаги 2 и 4 ничего не делают, а шаг 3 работает.

### 8. Ошибки не мешают публикации

`list_tree_paths` при ненулевом коде возврата выбрасывает исключение.
`polling` перехватывает его, пишет `ctx.log.warning(...)` с проектом,
MR и stderr git и передаёт `None`. Любое неожиданное исключение внутри
`link_file_references` (например, ошибка в регулярном выражении на
экзотическом тексте) тоже перехватывается в `polling`: публикуется
исходный отчёт, в лог пишется предупреждение. Публикация важнее ссылок.

## Risks / Trade-offs

- [Модель придумает третий формат ссылок, например `src/a.ts (строка 13)`]
  → Такая ссылка останется текстом. Это деградация, а не ошибка: отчёт
  читаем, а локальный путь всё равно удаляется на шаге 4. При появлении
  нового формата его можно добавить в модуль. Если на живой проверке
  (tasks.md, 4.2) и первых боевых отчётах окажется заметно много таких
  упоминаний, нужен отдельный change: одна строка о формате мест в промпте
  (`` `путь/от/корня:строка` ``) и A/B-прогон на бенчмарке. Сейчас эта
  инструкция не добавляется, потому что любое изменение промпта может
  повлиять на recall (AGENTS.md п.3), а постобработка нужна в любом
  случае.
- [Ложная ссылка из inline-кода, совпавшего с реальным путём, например
  `` `package.json` ``] → Ссылка на настоящий файл коммита не вредит.
  Совпадение проверяется точно, без нечёткого поиска.
- [Номер строки в отчёте неверный] → Ссылка откроет файл на другой
  строке, ровно так же, как и текст отчёта. Проверять номера строк мы не
  берёмся (Non-Goals).
- [Публичность коммита] → Ссылки ведут на тот же приватный GitLab, что и
  MR. Новых раскрытий нет, а локальный путь машины, напротив, перестаёт
  попадать в комментарий.
- [Большой репозиторий, длинный `ls-tree`] → Десятки тысяч путей
  выводятся за доли секунды. Это несравнимо меньше времени ревью.

## Migration Plan

Миграция не нужна: конфигурации и формата состояния change не касается.
Уже опубликованные комментарии не переписываются. Откат — revert
коммита.
