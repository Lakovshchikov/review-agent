# Design

## Context

Мотивация — см. `proposal.md`; требования — `specs/`.

Текущее состояние (Change 1): `review_agent.pipeline.run_review(repo_path, base_sha, head_sha, mr_title, mr_description, config_path, scratch_dir)` делает полный прогон (worktree → `opencode.json` → промпт через `--file` → харнесс → отчёт в `report.output_path` с `{run_id}` → удаление worktree) и возвращает путь к отчёту. `ensure_commits_available` умеет только `git fetch origin <sha>`. CLI — плоский `argparse` без подкоманд. Внешние процессы вызываются через `subprocess.run` с резолвингом через PATH (`harness.py`).

Ограничения, которые формируют подход:
- `glab` — единственный инструмент доступа к GitLab (`AGENTS.md` §5). В автоматических тестах GitLab-взаимодействие подменяется стабом; итоговая проверка всегда выполняется пользователем на боевом (VPN-only) GitLab на своей машине — тесты должны проходить и там.
- `glab` используется уже авторизованным на машине запуска (`glab auth login`); креды в конфиге не хранятся.
- Windows как первая платформа: уроки Change 1 — явный `encoding="utf-8"` у каждого `subprocess.run` и никаких многострочных/длинных payload'ов в argv.
- Состояние «отревьюено» — только в GitLab (маркер), локального state нет.
- Движок ревью не должен знать о GitLab (MODIFIED-требование `mr-review-engine`).

## Goals / Non-Goals

**Goals**
- Оркестратор прохода как отдельный слой поверх неизменённого движка: `poll` → для каждого кандидата вызывает тот же `run_review`, что и ручной CLI.
- Весь доступ к GitLab — в одном тонком адаптере над `glab` (по аналогии с адаптером харнесса), чтобы тестировать оркестратор без GitLab и при необходимости заменить транспорт.
- Предсказуемое поведение при сбоях: ничего не опубликовано ⇒ MR будет повторён.

**Non-Goals**
- Параллельные ревью — никакой параллели ни внутри прохода (MR строго по очереди), ни между проходами (см. Decision 10).
- Креды GitLab в конфиге и скрипт автоавторизации `glab` по ним — бэклог (после этого change).
- Структурированное логирование, ротация, уведомления — Change 3. Здесь только итоговая сводка в stdout/stderr.
- Inline-комментарии к строкам diff, discussions/threads — только обычный note на MR.

## Decisions

### 1. Чтение из GitLab — `glab mr view` для метаданных, `glab api` для хэшей и остального

Разделение ролей:
- **`glab mr view <iid> -R <project> --output json`** — базовая информация о MR: автор, title, description, `web_url` (ссылка для интерактивного списка), draft-статус. Это то, что видит человек, и высокоуровневая команда отдаёт это напрямую.
- **`glab api --hostname <host> <endpoint>`** (JSON, `--paginate` где нужно) — всё остальное:
  - текущий пользователь: `user` (проверка авторства маркера);
  - кандидаты: `projects/<url-encoded path>/merge_requests?state=opened&reviewer_username=<u>&per_page=100` для каждого сконфигурированного ревьюера; объединение по `iid` (MR с двумя нашими ревьюерами — один кандидат);
  - хэши: `projects/<p>/merge_requests/<iid>` → `diff_refs.base_sha/head_sha` (ровно так, как SHA были получены вручную при валидации Change 1);
  - комментарии: `projects/<p>/merge_requests/<iid>/notes?per_page=100`.

Почему `glab api`, а не `glab mr list --reviewer`, для поиска кандидатов: фильтр `reviewer_username` и пагинация на уровне REST API стабильны и не зависят от того, как конкретная версия `glab` форматирует вывод `mr list`. Всё это — `glab` (требование `AGENTS.md` соблюдено; `python-gitlab` не используется). Все вызовы собраны в одном адаптере — одна точка стаба в тестах. Если в установленной версии `glab mr view --output json` не отдаёт какое-то поле, адаптер берёт его из ответа `glab api` по тому же MR (проверяется вживую, задача 6.1).

### 2. Публикация — `glab api --method POST ... notes` с телом из файла

Тело комментария (отчёт может быть десятки КБ, многострочный, кириллица) пишется в JSON-файл в scratch и отправляется через `glab api --method POST projects/<p>/merge_requests/<iid>/notes --input <file> -H "Content-Type: application/json"`.

Почему не `glab mr note <iid> -m "<отчёт>"`: передавать весь отчёт аргументом командной строки — ровно та ошибка, которая в Change 1 тихо обрезала промпт. Даже если `glab.exe` нативный (не `.CMD`-шим), остаются лимит длины командной строки Windows (~32K символов) и риски кодировки argv. Файл снимает класс проблем целиком. Точный синтаксис `--input` проверяется вживую на установленной версии `glab` (задача в `tasks.md`); fallback, если `--input` недоступен — `-F body=@<file>`.

### 3. Формат комментария и маркер

```
### 🤖 AI code review

Автоматический отчёт по коммиту `<head_sha[:12]>` (base `<base_sha[:12]>`), модель `<provider/model#effort>`.
Находки могут быть неполными или ошибочными — это подсказка ревьюеру, не вердикт.

---

<отчёт харнесса как есть>

<!-- ai-review: sha=<head_sha> -->
```

Маркер — HTML-комментарий (GitLab не рендерит), ровно в формате из `AGENTS.md`; разбор — регулярным выражением `<!-- ai-review: sha=([0-9a-f]{7,64}) -->`. Маркер учитывается, только если автор note — текущий пользователь `glab` (защита от случайного/намеренного «выключения» ревью чужим комментарием). Если head сдвинулся во время ревью, маркер всё равно содержит отревьюенный SHA (спека `review-publishing`).

Правило пропуска в этом change: **любой** наш маркер на MR ⇒ MR пропускается, независимо от SHA. Предикат вынесен в одну функцию, так что будущая фича «ревью нового diff» меняет только его (`sha == current_head` вместо «есть маркер»), формат маркера и хранение не меняются.

### 4. Подготовка локального клона: fetch ref'а MR

Перед ревью: `git -C <local_repo> fetch <remote> refs/merge-requests/<iid>/head` (remote по умолчанию `origin`, настраивается на проект). Это работает и для MR из форков (GitLab держит ref в целевом проекте), не трогает ветки/индекс/рабочие файлы клона (обновляется только `FETCH_HEAD`), и после него существующий `ensure_commits_available` находит оба SHA локально, не пытаясь `fetch origin <sha>` (который GitLab по умолчанию может отклонить). Fetch делается всегда, даже если SHA уже есть, — дёшево и исключает устаревшее состояние. Автоклонирование отсутствующего репозитория — вне скоупа: путь к клону задаётся в конфиге, его отсутствие — ошибка проекта.

### 5. Конфиг: опциональная секция `gitlab`

```yaml
gitlab:
  hostname: gitlab.example.local     # передаётся в glab --hostname
  reviewers: [ai-reviewer]           # username'ы; MR берётся, если хоть один назначен ревьюером
  review_drafts: false               # draft-MR пропускаются по умолчанию
  min_report_chars: 200              # отчёт короче — не публикуется (см. Decision 7); значение подтверждено
  projects:
    - path: b2c/front-shopping
      local_repo: C:/repos/front-shopping
      remote: origin                 # опционально
```

Секция необязательна для ручного режима (старые `config.yaml` продолжают работать) и обязательна для `poll` — её отсутствие/невалидность даёт понятную `ConfigError` до любых сетевых вызовов. Токены в конфиг не кладутся: аутентификация — забота `glab auth login`. Список проектов здесь минимальный (путь + клон); per-project переопределения провайдера/скиллов и прочее «multi-repo» — Change 3.

### 6. CLI: подкоманда `poll` без поломки ручного режима

`review-agent poll [--all] [--dry-run] [--config config.yaml] [--scratch-dir ...]`. Если первый аргумент — `poll`, используется отдельный парсер; иначе — текущий парсер ручного ревью без изменений (`review-agent --repo ... --base ... --head ...` продолжает работать). Альтернатива — перевести всё на подкоманды (`review-agent review ...`) — отклонена: breaking для уже задокументированного и провалидированного вызова ради косметики.

Коды выхода: `0` — все выбранные кандидаты опубликованы или пропущены (в т.ч. «нечего ревьюить» и «пользователь отказался от выбора»); `1` — хотя бы один MR/проект упал (проход при этом доходит до конца); `2` — ошибка до начала ревью (невалидный конфиг, `glab` не найден/не авторизован/GitLab недоступен, другой проход уже идёт, интерактивный режим без терминала) — ни одного ревью не запускается.

### 6a. Режимы запуска: интерактивный по умолчанию, `--all` — автоматический

На время тестирования режим по умолчанию — интерактивный: после опроса (поиск кандидатов + отсев отревьюенных + метаданные через `glab mr view`) выводится нумерованный список:

```
Найдено MR, где ревьюер назначен: 5

  1) b2c/front-shopping !544  PLATVTRN-1258: Процесс оставления отзыва  (автор: ivanov)
     https://gitlab.example.local/b2c/front-shopping/-/merge_requests/544
  2) ...

Выберите номер MR для ревью (q — выход):
```

Ревьюится и публикуется только выбранный MR. Неверный ввод — повторный вопрос; `q` — выход с кодом 0 без ревью. Пустой список — сообщение и выход с кодом 0 без вопроса.

`--all` — автоматический режим: все найденные кандидаты ревьюятся по очереди без вопросов (это и есть режим для будущего планировщика, Change 3). Если `--all` не передан, а stdin — не терминал (`sys.stdin.isatty()` ложно, например запуск из Task Scheduler), команда завершается с кодом 2 и подсказкой про `--all`, а не зависает на вопросе. `--dry-run` комбинируется с обоими режимами. Ввод/вывод выбора инжектируются в оркестратор (функции чтения строки и печати), чтобы интерактивный режим тестировался без реального терминала.

Альтернатива — отдельный флаг `--select <iid>` вместо интерактивного вопроса — отклонена на этом этапе: пользователь хочет видеть, что нашёл опрос, и выбирать из списка; при необходимости добавляется позже без изменения остальной логики.

### 7. Проверка годности отчёта — минимальная эвристика по длине

Отчёт пустой или короче `min_report_chars` ⇒ не публикуется, MR считается упавшим (ретрай на следующем проходе), путь к отчёту и `harness-stderr.log` попадают в сводку. Это прямой ответ на пункт «Не доделано» из `validation-notes.md` Change 1. Более тонкие эвристики (число tool call'ов из stderr, наличие severity-меток) отклонены на этом этапе: формат stderr OpenCode не контракт, а ложные отказы публиковать хуже редких тонких отчётов.

### 8. Изменения движка — минимальные и GitLab-agnostic

`run_review` получает опциональный параметр для явного пути отчёта (оркестратор кладёт отчёты по `<project>-<iid>-<sha12>`, чтобы их было легко найти; ручной режим по-прежнему использует `report.output_path`) и продолжает возвращать путь к файлу; оркестратор сам читает отчёт. Никаких импортов GitLab-модулей из `pipeline.py`/`worktree.py`. Fetch ref'а MR (Decision 4) — отдельная функция в `worktree.py` без знания о GitLab API (принимает remote и refspec).

### 9. Структура модулей

- `gitlab.py` — адаптер над `glab` (`current_user`, `list_review_candidates`, `get_mr`, `list_notes`, `post_note`, preflight), с инъекцией runner'а как в `harness.py`; все вызовы — `encoding="utf-8"`, резолвинг `glab` через PATH.
- `publishing.py` — формат комментария, построение/разбор маркера, предикат «уже отревьюено», проверка годности отчёта. Чистые функции — без I/O.
- `polling.py` — оркестратор прохода, выбор кандидатов (интерактивно / `--all`), lock, сводка, код выхода.

### 10. Один проход за раз — lock-файл в scratch-директории

В начале прохода (до любых обращений к GitLab) создаётся `<scratch-dir>/poll.lock` атомарно (`open(..., "x")` — эксклюзивное создание, работает одинаково на Windows и Linux) с PID текущего процесса; в конце прохода (в `finally`) удаляется. Если файл уже существует:
- процесс с записанным PID жив → второй запуск сразу выходит с кодом 2 и сообщением «проход уже выполняется»;
- процесс мёртв (предыдущий проход убит) → lock считается протухшим, перезаписывается, проход идёт как обычно.

Проверка «жив ли PID» — небольшая кроссплатформенная функция (на Linux — `os.kill(pid, 0)`, на Windows — `OpenProcess` через `ctypes`), без новых зависимостей. Это не состояние ревью (оно по-прежнему только в GitLab-маркерах) — lock лишь гарантирует, что два прохода не возьмут один MR одновременно. Повторная проверка маркера перед публикацией остаётся вторым рубежом (на случай двух машин или разных scratch-директорий).

Альтернатива — полагаться на настройку Task Scheduler «не запускать новый экземпляр» — отклонена как единственная мера: не защищает от ручного запуска поверх запланированного и не переносится в cron/CI.

## Risks / Trade-offs

- [Risk] Два прохода наложились (длинное ревью + частый запуск) и оба ревьюят один MR → Mitigation: lock-файл (Decision 10) — второй проход не стартует; плюс повторная проверка маркера перед публикацией. Остаточный риск: проходы с разных машин/scratch-директорий — закрывается только повторной проверкой маркера (окно в секунды).
- [Risk] Head MR обновился во время ревью → опубликован отчёт по устаревшему коммиту, а из-за правила «любой маркер ⇒ пропуск» новый head не будет отревьюен → Mitigation: комментарий явно называет отревьюенный SHA; повторное ревью на новый diff — запланированная бэклог-фича, дизайн маркера её поддерживает.
- [Accepted] Ложноположительные находки публикуются в MR — осознанно принято: отчёт читает человек и сам решает, что из находок верно; в шапке комментария — дисклеймер.
- [Accepted] Код ревьюируемых репозиториев уходит внешнему провайдеру модели — для этого проекта допустимо.
- [Risk] Протухший lock после аварийного завершения блокирует следующие проходы → Mitigation: проверка PID владельца (Decision 10); в худшем случае — ручное удаление `poll.lock`, путь к нему указан в сообщении об ошибке.
- [Risk] Синтаксис `glab api` (`--paginate`, `--input`, `--hostname`) отличается в установленной версии → Mitigation: живая проверка на реальном GitLab — отдельная задача; все вызовы собраны в одном адаптере.
- [Trade-off] Эвристика по длине может пропустить «содержательно пустой», но длинный отчёт (например, модель вежливо описала, что ничего не смотрела) → принимается для v1; сводка всегда содержит путь к отчёту и stderr для ручного аудита.

## Migration Plan

1. Обновить `config.yaml`: добавить секцию `gitlab` (по `config.example.yaml`); ручной режим работает и без неё.
2. На машине запуска `glab` уже должен быть авторизован (`glab auth login --hostname <host>`); комментарии публикуются от имени этой учётной записи.
3. Первый прогон — `review-agent poll --dry-run` в интерактивном режиме: проверить список найденных MR и ссылки, выбрать один, проверить локальный отчёт.
4. Затем боевой проход в интерактивном режиме на одном выбранном MR; проверить комментарий и маркер, затем повторный проход — этот MR в списке больше не появляется.
5. После этого — проверка `--all`.

Откат: просто не вызывать `poll`; опубликованные комментарии удаляются вручную в GitLab (удаление маркера делает MR снова кандидатом).
