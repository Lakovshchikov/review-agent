# Proposal

## Why

Движок ревью (Change 1, `core-review-engine`) проверен на реальном бенчмарк-MR, но запускается только вручную: человек сам ищет MR, достаёт base/head SHA через `glab api` и копирует отчёт из файла в GitLab. Чтобы агент стал автономным (см. `AGENTS.md` §1, §5), нужен один идемпотентный проход «найти MR, где назначен наш ревьюер → прогнать движок → опубликовать отчёт комментарием», безопасный к повторному вызову по расписанию. Сейчас — потому что go-решение по Change 1 зафиксировано, и Change 3 (шедулинг) строится поверх именно этого прохода.

## What Changes

- Новая CLI-команда `review-agent poll` — **один** проход опроса/ревью/публикации и выход. Без внутреннего цикла, демона и локального state-файла: кто и когда её вызывает — не её забота (`AGENTS.md` §5).
- Обнаружение MR через `glab`: для каждого сконфигурированного GitLab-проекта — открытые MR, где ревьюером назначен один из сконфигурированных пользователей (список ревьюеров — в конфиге); метаданные MR (автор, title, description, ссылка) — через `glab mr view`, актуальные `diff_refs` (base/head SHA) — через `glab api`.
- **Интерактивный режим по умолчанию** (на время тестирования): после опроса выводится нумерованный список найденных MR со ссылками, пользователь выбирает один — ревьюится только он. **Автоматический режим** (флаг `--all`): все найденные MR ревьюятся по очереди без вопросов. Без `--all` и без терминала команда отказывается работать, а не зависает (защита для планировщика).
- **Один проход за раз**: lock-файл в scratch-директории не даёт двум запускам пересечься и отревьюить один MR дважды; ревью внутри прохода — строго последовательно, без параллели.
- Идемпотентность через состояние в самом GitLab: маркер `<!-- ai-review: sha=<head_sha> -->` в комментарии, оставленном пользователем, от имени которого работает `glab`. MR с таким маркером считается отревьюенным и пропускается.
- Подготовка локального клона перед ревью: подтягивание `refs/merge-requests/<iid>/head` из GitLab, чтобы head SHA был доступен локально (в т.ч. для MR из форков), затем вызов существующего движка без изменения его поведения.
- Публикация отчёта комментарием к MR через `glab`, только оркестратором после завершения прогона (агент по-прежнему не имеет прав на запись в GitLab).
- Минимальная проверка годности отчёта перед публикацией (пустой/подозрительно короткий отчёт не публикуется) — прямой вывод из `validation-notes.md` Change 1, где баг транспорта тихо дал «пустой» отчёт с кодом выхода 0.
- Изоляция ошибок по MR: сбой одного MR (fetch, харнесс, публикация) логируется и не мешает остальным; маркер не ставится, MR будет повторён следующим проходом.
- Режим `--dry-run`: всё, кроме публикации (отчёты пишутся локально, комментарии не создаются) — для безопасной первой проверки на реальном GitLab.
- Новая секция конфига `gitlab` (список ревьюеров, список проектов с путём к локальному клону, опции фильтрации).
- Существующая команда ручного ревью (`review-agent --repo ... --base ... --head ...`) сохраняется и продолжает работать без обращений к GitLab — **не breaking**.

Вне скоупа (явно): креды GitLab в конфиге и скрипт автоавторизации `glab` (сейчас используется уже авторизованный `glab`), повторное ревью при новом head SHA после правок разработчика (бэклог; дизайн маркера его допускает, но в этом change MR с любым нашим маркером не ревьюится повторно), авто-resolve тредов, inline-комментарии к строкам diff, планировщик/Task Scheduler, ротация логов и прочее из Change 3, автоматическое клонирование репозиториев.

## Capabilities

### New Capabilities
- `mr-discovery`: обнаружение MR, подлежащих ревью, в сконфигурированных GitLab-проектах — фильтр по ревьюеру, состоянию, draft-статусу и наличию маркера уже выполненного ревью; получение base/head SHA.
- `review-publishing`: публикация готового отчёта комментарием к MR с маркером состояния, проверка годности отчёта перед публикацией, dry-run.
- `review-polling-run`: один проход оркестрации «обнаружить → выбрать (интерактивно или все) → подготовить клон → ревью → опубликовать» как отдельная CLI-команда, с защитой от параллельных проходов, изоляцией ошибок по MR и итоговым кодом выхода.

### Modified Capabilities
- `mr-review-engine`: требование «Single-invocation CLI entrypoint» сейчас запрещает любые обращения к GitLab со стороны CLI вообще. Уточняется: команда ручного ревью по-прежнему не обращается к GitLab, а взаимодействие с GitLab разрешено только отдельной командой опроса (`review-polling-run`); сам движок ревью остаётся GitLab-agnostic.

## Impact

- Код: новые модули в `src/review_agent/` (GitLab-адаптер поверх `glab`, оркестратор прохода, форматирование комментария), расширение `config.py` (секция `gitlab`), `cli.py` (подкоманда `poll`), `pipeline.py` — минимально (возможность передать явный `run_id`/путь отчёта и вернуть результат для публикации), `worktree.py` — fetch ref'а MR.
- Внешние зависимости: `glab` должен быть установлен и авторизован (`glab auth login --hostname <host>`) на машине запуска; новых Python-зависимостей не требуется (`python-gitlab` — только как fallback, в этом change не нужен).
- Конфиг: `config.example.yaml` и README дополняются секцией `gitlab`; существующие конфиги без неё продолжают работать для ручного режима.
- Тесты: `glab` в автоматических тестах подменяется стабом (как харнесс в Change 1); итоговая проверка на боевом GitLab выполняется пользователем на своей машине.
