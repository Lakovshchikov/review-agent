# Proposal: scheduling-and-multi-repo-config

## Why

`review-agent poll --all` проверен на боевом GitLab (Change 2), но пока запускается только руками из терминала: результат прохода виден лишь в консоли, папки прогонов `<scratch>/<run_id>/` копятся без очистки, а все проекты обязаны делить одного провайдера, один набор knowledge-skill'ов и один список ревьюеров. Для безнадзорной работы по расписанию на Windows (`AGENTS.md` §2, §5; итог `validation-notes.md` Change 2) нужны три вещи: штатная регистрация прохода в Task Scheduler, след каждого прохода на диске с ограниченным сроком хранения и конфиг, в котором у отдельного проекта могут быть свои настройки.

## What Changes

- **Регистрация в Task Scheduler** — PowerShell-скрипт `scripts/register-task.ps1`: создаёт/обновляет/удаляет задачу Windows, которая по интервалу вызывает `review-agent poll --all` с нужным конфигом и рабочей папкой; не допускает параллельных экземпляров задачи. Python-код о планировщике по-прежнему ничего не знает (`AGENTS.md` §5) — под cron/GitLab CI скрипт просто не используется. `--include-closed` скрипт не передаёт (тестовый флаг).
- **Лог прохода** — каждый вызов `review-agent poll` пишет файл лога `logs/poll-<дата>-<время>.log` (UTF-8, с отметками времени): всё, что проход выводит в консоль (найденные MR, ход ревью, итоговая сводка, ошибки, в т.ч. «проход уже выполняется» и «GitLab недоступен»), плюс начало/конец и длительность прохода. Под планировщиком консоли нет — лог становится единственным следом прохода. Отсутствие консоли (`stdout` = `None`) не ломает проход.
- **Очистка по сроку хранения** — в начале каждого прохода (под lock'ом) удаляются старше N дней: логи проходов, папки прогонов `<scratch>/<run_id>/` (кроме тех, где ещё есть worktree), тела публикаций `<scratch>/notes/*.json` и отчёты/`.comment.md`/`.harness-stderr.log` в папке отчётов. N задаётся в конфиге (по умолчанию 14), очистку можно выключить. Сбой очистки не валит проход.
- **Переопределения на уровне проекта** — у каждого элемента `gitlab.projects` появляются необязательные поля `enabled`, `reviewers`, `review_drafts`, `provider`, `skills`. Не указано — берётся глобальное значение (как сейчас). `enabled: false` выключает проект без удаления из конфига. Глобальный `gitlab.reviewers` становится необязательным, если у каждого включённого проекта есть свой список.
- Существующие конфиги и ручной режим `review-agent --repo ... --base ... --head ...` работают без изменений — **не breaking**. Ручной режим не пишет лог прохода и не выполняет очистку.

Вне скоупа (явно): креды GitLab в конфиге и автоавторизация `glab`; повторное ревью при новом head SHA; параллельные ревью и ограничение числа MR за проход; уведомления (почта/мессенджеры) о сбоях; cron/systemd/GitLab CI `schedule` (появятся при переезде, Python-часть к ним уже готова); per-project переопределение `safety`/`harness`/`min_report_chars`.

## Capabilities

### New Capabilities
- `project-review-settings`: эффективные настройки ревью для каждого сконфигурированного GitLab-проекта — включён ли проект, ревьюеры, политика draft-MR, провайдер модели и knowledge-skill'ы — с откатом к глобальным значениям.
- `pass-logging-and-retention`: файл лога на каждый проход опроса и удаление устаревших локальных артефактов (логи, папки прогонов, тела публикаций, отчёты) по сроку хранения.
- `scheduled-task-registration`: регистрация, обновление и удаление задачи Windows Task Scheduler, периодически запускающей автоматический проход опроса.

### Modified Capabilities
- `mr-discovery`: фильтр по ревьюеру и правило draft-MR применяются с настройками конкретного проекта; выключенные проекты не опрашиваются.

## Impact

- Код: `src/review_agent/config.py` (поля проекта, секция `housekeeping`, валидация), `src/review_agent/polling.py` (эффективные настройки проекта, лог прохода, вызов очистки), `src/review_agent/pipeline.py` (принимает уже разрешённые провайдер/skill'ы вместо чтения их только из глобального конфига), новый модуль `src/review_agent/housekeeping.py`, новый `scripts/register-task.ps1`.
- Конфиг: новые необязательные поля в `gitlab.projects[*]` и секция `housekeeping` (`log_dir`, `retention_days`); `config.example.yaml`, README.
- Зависимости: новых нет (стандартные `logging`/`pathlib`; PowerShell-модуль `ScheduledTasks` входит в Windows).
- Эксплуатация: относительные пути конфига по-прежнему разрешаются от рабочей папки процесса — задача Task Scheduler обязана запускаться с рабочей папкой проекта (скрипт это задаёт).
