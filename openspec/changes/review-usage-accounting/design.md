# Design

## Context

Мотивация — в proposal.md, требования — в `specs/`. Здесь то, что
выяснил ручной spike на машине автора (OpenCode v2.0.21, Windows,
ChatGPT-подписка), и что из этого следует для реализации.

- `opencode session export <id>` отдаёт JSON `{info, messages}`. В `info`
  уже есть **агрегат всей сессии**: `tokens {input, output, reasoning,
  cache {read, write}}`, `model {id, providerID, variant}`, `agent`,
  `outcome` (`succeeded` / `interrupted` / …), `time {created, updated,
  idle}`, `location.directory` (путь worktree прогона, в нём есть наш
  `run_id`), `projectID`. `cost` для подписки всегда 0. Кроме того, в
  экспорте **полный текст промпта** (описание MR) и ответов.
- `opencode session list` печатает текстом верхнеуровневые сессии
  *текущего проекта* (проект OpenCode определяется по git-репозиторию,
  worktree того же репо попадают в тот же проект): `ses_<id>  <заголовок>
  <дата>`, от новых к старым.
- `opencode stats --json [--project <id>] [--days N]` даёт агрегаты
  (сессии, шаги, токены по моделям). Это годится для ручной сверки с
  журналом. Субагентов в прогонах ревью нет (`subagents: 0`).
- `opencode run` имеет `--session <id>` («continue, or create if it does
  not exist»), `--title`, `--format json`. Формат ID для `--session` не
  проверен.
- Креды OpenCode v2 — внутри `opencode.db` (официальный доступ:
  `opencode auth export`). Прямой `GET chatgpt.com/backend-api/wham/usage`
  с этим токеном отвечает 401: у OpenCode свой OAuth-клиент, account id
  в JWT зашифрован. Автоматического источника процентов лимитов нет.
  Отсюда ручные отметки.
- Windows PowerShell 5.1 портит UTF-8 при `>`. В Python читаем вывод
  opencode с `encoding="utf-8", errors="replace"`, как уже делается в
  `harness.py`.
- `run_review` (`pipeline.py`) не знает проекта и MR. Worktree удаляется
  на выходе из `managed_worktree`, а при ошибке harness наружу летит
  `HarnessError`.

## Goals / Non-Goals

**Goals:**
- Расход по каждому прогону собирается без участия человека и без
  лишних обращений к провайдеру модели. Используются только локальные
  команды харнесса.
- Три независимые точки замены: **источник расхода** (харнесс), **цены**
  (данные), **лимиты** (сейчас ручные отметки). Смена провайдера не
  трогает ни одну из них. Смена харнесса трогает только источник расхода.
- Запись журнала переносима в OTel/шлюзы без миграции: те же имена
  полей, тот же `run_id` как ключ сверки.

**Non-Goals:**
- Не храним сырые экспорты сессий и вообще никакой текст. Только числа и
  идентификаторы.
- Не меняем stdout-контракт харнесса (отчёт = stdout `opencode run`) и
  командную строку прогона (`harness.command`).
- Не делаем UI. Сводка — CLI с выводом в CSV/JSON, их можно открыть в
  Excel.
- Не делаем автоматический probe лимитов, OTLP-экспорт и строку
  расхода в комментарии к MR (бэклог).

## Decisions

### 1. Источник расхода — после прогона, поиск сессии по пути worktree

После `invoke_harness` (успешного или с `HarnessError`), **ещё внутри
`managed_worktree`**, источник расхода делает следующее:

1. Запускает `usage.session_list_command` (по умолчанию
   `["opencode", "session", "list"]`) с `cwd` = worktree и берёт до 5
   первых ID вида `ses_\S+`.
2. По очереди запускает `usage.session_export_command` (по умолчанию
   `["opencode", "session", "export", "{session_id}"]`). Из JSON берётся
   только `info`, остальное сразу отбрасывается.
3. Первая сессия, у которой `info.location.directory` совпадает с путём
   worktree (сравнение через `os.path.normcase(os.path.realpath(...))`),
   считается сессией прогона.

Исполняемый файл резолвится через `shutil.which`, как в `harness.py`
(`.CMD`-шимы на Windows). Каждая команда идёт с таймаутом и
`no_window_flags()`.

Почему так:
- Путь worktree уникален для прогона и уже лежит в `info`. Сопоставление
  однозначное и не требует ничего добавлять в командную строку прогона.
- Шаблоны команд — в конфиге. Если живая проверка покажет, что `session
  list` нужен `--standalone` (прогон идёт через `run --standalone`),
  это правится конфигом, без кода.

Отклонённые альтернативы:
- `opencode run --session <наш id>`: самый прямой путь, но формат ID не
  проверен, а неверный ID ломает сам прогон ревью. Оставлено как
  возможная оптимизация после живой проверки (Open Questions).
- `opencode run --format json` и разбор событий: меняет stdout-контракт
  (отчёт придётся собирать из событий). Слишком дорого ради учёта.
- Чтение `opencode.db` напрямую: внутренний формат, меняется между
  версиями.
- `opencode stats` как основной источник: нет привязки к MR и прогону.

Источник расхода — интерфейс с двумя реализациями: `opencode` (по
умолчанию) и `none`. Он отдаёт нейтральную структуру `SessionUsage`
(токены по видам, шаги, модель/провайдер/вариант, исход, session id) или
причину, почему расхода нет. Новый харнесс означает новую реализацию,
остальной код не меняется.

**Шаги.** В `info` их нет. Считаем сообщения ассистента в `messages`,
если их тип однозначно распознаётся. Иначе `null`. Это проверяется на
живом экспорте (tasks).

**Длительность** меряет сам оркестратор вокруг `invoke_harness`.
`info.time` неоднозначно (`updated` против `idle`).

### 2. Где это в коде: рекордер, передаваемый в `run_review`

`run_review` получает необязательный `usage: UsageRecorder | None` и
метки прогона (`source`, `project`, `mr_iid`). `polling.py` и ручной CLI
создают рекордер из конфига и передают метки. Внутри `run_review`:

```
managed_worktree -> render prompt -> t0
  try:   invoke_harness
  except HarnessError: outcome = failed; raise   (после записи)
  finally (внутри with):
     size     = git diff --numstat base head ; git rev-list --count base..head
     session  = usage_source.collect(worktree)        # не бросает
     findings = count_findings(report) if report else None
     recorder.write(review_record(...))               # не бросает, warning в лог
```

Запись делается в `finally` внутри блока worktree: так покрыты и успех,
и `HarnessError`, а worktree ещё существует (нужен для `git diff` и
`cwd` команды `session list`). Все ошибки учёта ловятся внутри
рекордера. Наружу идёт только warning через переданный callback (в
`poll` это `PassLog.file_only`, в ручном режиме stderr). `run_review` с
`usage=None` ведёт себя ровно как сейчас, поэтому тесты пайплайна не
меняются.

Размер изменения: `base..head` для коммитов, `git diff --numstat base
head` для файлов и строк. base от GitLab (`diff_refs.base_sha`) уже
merge-base. Бинарные файлы (`-\t-`) считаются в файлах, но не в
строках. Промпт этого не видит: рендерится до замеров и не меняется.

### 3. Схема записи: JSONL, имена OTel `gen_ai.*` + `review.*`

`<work_dir>/usage/ledger.jsonl`, одна запись — одна строка UTF-8
(`ensure_ascii=False`), только дописывание. Пример review-записи:

```json
{"schema": "review-agent.usage/1", "kind": "review",
 "time": "2026-10-04T12:51:53+03:00", "review.run_id": "1791107508-472e2701",
 "review.source": "poll", "review.project": "b2c/front-shopping", "review.mr.iid": 544,
 "review.base_sha": "...", "review.head_sha": "...",
 "gen_ai.provider.name": "openai", "gen_ai.request.model": "gpt-5.6-terra",
 "review.reasoning_effort": "medium", "review.skills": ["frontend-pitfalls.md"],
 "review.outcome": "succeeded", "review.duration_ms": 312000,
 "review.harness.session_id": "ses_...",
 "gen_ai.usage.input_tokens": 340652,
 "gen_ai.usage.cache_read.input_tokens": 121856,
 "gen_ai.usage.cache_creation.input_tokens": 0,
 "gen_ai.usage.output_tokens": 3696,
 "review.usage.reasoning_tokens": 2269, "review.usage.steps": 4,
 "review.usage.missing_reason": null,
 "review.change.files": 12, "review.change.lines_added": 340,
 "review.change.lines_deleted": 85, "review.change.commits": 3,
 "review.findings": {"blocker": 0, "major": 2, "minor": 1}}
```

- В семантике OTel `gen_ai.usage.input_tokens` — **весь** вход,
  включая кэш. OpenCode отдаёт `input` без кэша, поэтому пишем `input +
  cache.read + cache.write`, а «свежий» вход сводка выводит вычитанием.
  Так запись честно читается любым OTel-инструментом.
- Для reasoning стандартного имени в стабильной части конвенций нет,
  поэтому оно лежит в `review.*`. Версию конвенций, с которой сверены
  имена, фиксируем в README.
- Quota-запись: `{"schema", "kind": "quota", "time", "review.quota.provider":
  "openai", "review.quota.windows": {"5h": 23, "week": 41}, "review.quota.source":
  "manual"}`. Будущий автоматический probe пишет ту же запись с другим
  `source`. Схема, сводка и калибровка от этого не меняются.
- Почему JSONL, а не SQLite: дописывание без схемы и миграций, читается
  руками и Excel'ем (через CSV из сводки), переносится в CI как артефакт.
  Объём ничтожный (~1 КБ на ревью).
- Почему не OTel SDK сейчас: лишняя зависимость ради файла. Запись уже
  совместима по именам. OTLP-sink — отдельный будущий change: он читает
  ту же структуру.

Конкурентная запись: ревью пишут журнал под `poll.lock` (и `poll`, и
ручной режим его берут). `quota note` lock не берёт: это одна короткая
строка, дописанная одним `write` в режиме `a`. Порчи соседних записей
это не вызывает. Сводка пропускает нечитаемые строки и сообщает об этом.

### 4. Находки по SEV — эвристика по тексту отчёта

Отчёт — свободный markdown модели. Считаем строки, где слово
`Blocker|Major|Minor` стоит **как метка** (без учёта регистра):
`SEV: Major`, `SEV Major`, `[Major]`, `**Major**`, `(Major)`, `Major:` в
начале заголовка или пункта списка. Одна строка — не больше одной
находки (берётся первая метка). Это приближение: в README прямо сказано,
что это «оценка по отчёту». Тесты — на фрагментах реальных отчётов
(`!544`, `!587`) с известным числом находок. Альтернатива — просить
модель выдавать машиночитаемый блок находок, но это изменило бы промпт.
Промпт — объект исследования (AGENTS.md п.3), поэтому отклонено.

### 5. Цены: таблица в конфиге поверх локального каталога LiteLLM

```yaml
usage:
  enabled: true                       # по умолчанию true
  source: opencode                    # opencode | none
  session_list_command: [opencode, session, list]
  session_export_command: [opencode, session, export, "{session_id}"]
  price_catalog: ./prices/litellm-model-prices.json   # необязательно, локальный файл
  prices:                             # $ за 1M токенов; перекрывает каталог (цифры ниже условные)
    openai/gpt-5.6-terra: {as: openai/gpt-5.5}        # "заменитель" для модели без API-цены
    openai/gpt-5.5: {input: 1.25, cache_read: 0.125, cache_write: 0, output: 10}
```

- Поиск цены: `prices["<provider>/<model>"]` → каталог по ключу
  `<provider>/<model>`, затем `<model>`. Поле `as` разрешается один раз,
  цепочки и циклы — ошибка конфигурации. Reasoning оплачивается как
  output.
- Каталог — локальный файл в формате LiteLLM
  `model_prices_and_context_window.json` (`input_cost_per_token`,
  `output_cost_per_token`, `cache_read_input_token_cost`,
  `cache_creation_input_token_cost`). Пользователь скачивает его сам,
  когда хочет обновить цены. Сети при сводке нет. Так результат
  воспроизводим (видно, по какому файлу посчитано) и нет внешних
  обращений с машины в VPN. В выводе сводки указываются источник цены
  каждой модели (`config` / `catalog` / `as:<model>`) и дата изменения
  файла каталога.
- Почему не models.dev напрямую: OpenCode его использует, но формат
  каталога LiteLLM самый распространённый и тот же, что у шлюза для
  этапа CI.
- Цены применяются **только в сводке**. В журнале нет денег, поэтому
  смена прайса пересчитывает историю.

### 6. Оценка доли лимитов — калибровка по API-эквиваленту

Для каждого окна (`5h`, `week`, …) идём по quota-записям этого окна во
времени. Пара соседних отметок `(t1, p1) → (t2, p2)` валидна, если
`p2 ≥ p1` и между ними есть хотя бы одно ревью с ценой. Тогда
коэффициент окна = `Σ(p2 − p1) / Σ $` по валидным парам, а доля ревью =
`$ревью × коэффициент`.

- Почему вес — API-доллары, а не сырые токены: сырые токены уравнивают
  cache read с fresh input, а провайдер их явно взвешивает по-разному.
  Соотношение API-цен — лучшее доступное приближение этих весов.
  Следствие: без цены у модели доли нет. Для модели подписки без
  API-цены задаётся `as`.
- Пара с уменьшением процента означает сброс окна, она выбрасывается.
- Параллельное ручное использование ChatGPT/Codex может только
  **завысить** Δ%. Поэтому оценка — сверху, и сводка это пишет вместе с
  числом пар. В README описана процедура чистого замера: отметка до и
  после одиночного ревью без параллельной работы.
- Квантильная регрессия по нижней огибающей из обсуждения откладывается,
  пока данных мало. Отношение сумм проще, объяснимо и не ломается на
  2–3 парах.

### 7. CLI: подкоманды по первому токену

По образцу `poll` (`cli.main` смотрит на `argv[0]`):

- `review-agent usage [--config PATH] [--since 7d|YYYY-MM-DD] [--until
  YYYY-MM-DD] [--by review|mr|model|day] [--format table|csv|json]`.
  По умолчанию: последние 7 дней, `--by review`, `table`. Таблица
  печатается в консоль (UTF-8-безопасно, как в `passlog`), CSV/JSON — в
  stdout для перенаправления в файл.
- `review-agent quota note WINDOW=PCT [WINDOW=PCT ...] [--provider NAME]
  [--config PATH]`. Провайдер по умолчанию — `provider.name` из конфига.

Обе команды только читают конфиг, ничего не трогают в GitLab и не
вызывают харнесс.

### 8. Рабочая папка

`housekeeping.WorkDir` получает свойство `usage`. Папка не входит в
`RETAINED_AREAS`, и уборка `tmp/` её не касается. Создаётся лениво при
первой записи.

## Risks / Trade-offs

- [Формат `session export` / `session list` изменится в новой версии
  OpenCode] → Разбор защитный: отсутствующее поле даёт `null` и
  `missing_reason`, ревью не страдает. Шаблоны команд в конфиге. Тесты
  на зафиксированных образцах вывода v2.0.21.
- [`session list` через background-сервис не видит сессию
  `--standalone`-прогона] → Проверяется живым прогоном. Если так,
  в шаблон команд добавляется `--standalone`. Это правка конфига или
  значения по умолчанию, а не архитектуры.
- [Экспорт содержит текст промпта и отчёта] → Парсим в памяти, берём
  только `info` (и счётчик сообщений), ничего из экспорта не пишем на
  диск и в лог.
- [Эвристика находок ошибается на нестандартном отчёте] → Помечена как
  оценка. Тесты на реальных отчётах. Сам отчёт в GitLab — источник
  правды.
- [Оценка доли лимитов шумная и завышенная] → Показываются число пар и
  пометка «оценка». Процедура чистого замера в README. Автоматический
  замер — бэклог.
- [Доп. время после прогона: `session list` + до 5 экспортов] → Это
  локальные команды, секунды. Таймаут на каждую.
- [Цена «заменителя» (`as`) условна] → Сводка явно показывает, какая
  модель взята заменителем. Для отчёта работодателю это допущение
  оговаривается.

## Migration Plan

Миграции нет: секция `usage` необязательна, по умолчанию учёт включён с
источником `opencode`. Для конфигов с другим харнессом сбор просто
даёт записи с `missing_reason`. Откат — `usage.enabled: false`. Журнал
остаётся, его можно удалить руками.

## Open Questions

- Принимает ли `opencode run --session` произвольный ID (например,
  `ses_<run_id>`)? Если да, поиск по пути можно заменить прямым экспортом
  и добавить `--title "review-agent <project>!<iid>"`. Это оптимизация,
  на спеки не влияет.
- Есть ли в debug-логе OpenCode (`--print-logs --log-level debug`)
  заголовки `x-codex-*-used-percent`. Проверяется заодно при живой
  проверке. Если есть, это вход для будущего автоматического probe
  (бэклог), в этом change не реализуется.
