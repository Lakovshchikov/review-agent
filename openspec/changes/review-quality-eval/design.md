# Design

> Статус: отложено. Документ фиксирует итог обсуждения (explore) — что
> решено, что отклонено и почему, что осталось открытым. Имена команд,
> файлов и ключей — предварительные.

## Context

См. `proposal.md` — Why. Что уже есть и на что опираемся:

- ручной режим `review-agent --repo --base --head` и `pipeline.py` — один
  прогон ревью; eval переиспользует его как есть;
- журнал `usage/ledger.jsonl` — токены (включая `cache_read` /
  `cache_write`), время, стоимость прогона;
- `review_stats.count_findings` — оценка числа находок по SEV регуляркой;
- `file_links.py` — ссылки на файл в коммите GitLab;
- `repo_source.py` — кэш-клоны, fetch `refs/merge-requests/<iid>/head`;
- `harness.py` — вызов `opencode run --standalone` с промптом через
  `--file` (обход обрезки в `cmd.exe`) и `stdin=DEVNULL` (обход зависания).

Ограничения из AGENTS.md, которые формируют дизайн:

- промпт ревью не меняется ради eval (п.3–4: жёсткий формат роняет recall;
  отчёт остаётся свободным markdown) — разбор отчёта только постфактум;
- агенту-ревьюеру не передаются данные оркестратора, в т.ч. эталон;
- креды не в конфиге — модели только через авторизованный OpenCode;
- лимит подписки — главный бюджет; Windows — основная среда.

## Goals / Non-Goals

**Goals:**

- объективная, воспроизводимая оценка «окружение ревью стало ближе к
  эталону или дальше» на фиксированном наборе MR;
- минимум ручной работы при разметке;
- экономия лимита подписки (ранняя остановка, переиспользование замеров);
- карта недостигнутого: что лечится моделью/промптом, а что окружением.

**Non-Goals:**

- автоматический PASS/FAIL — решение всегда за человеком;
- статистическая значимость: 3 кейса × 3 повтора её не дают, отчёт делает
  разброс видимым, интерпретирует человек;
- онлайн-сигнал из реакций на опубликованные комментарии (возможное
  будущее, для gate не годится — медленный и шумный);
- синтетические кейсы с внесёнными багами (на старте не нужны).

## Decisions

### 1. Термины

- **Эталон** — все подтверждённые находки по MR, найденные любыми
  средствами, вплоть до код-стайла. Заведомо недостижимая цель: новая
  конфигурация лучше, если она **ближе** к эталону, чем baseline, а не
  если она его достигла.
- **Baseline** — боевой `config.yaml` и всё, на что он ссылается (шаблон
  промпта, skills, сгенерированный `opencode.json` с инструментами и MCP,
  версии). Отдельного «экспериментального» конфига нет: эксперимент — это
  правка того же конфига (решено: один конфиг — не проблема).
- **Замер baseline** — сохранённые отчёты прогонов, а не цифры: цифры
  всегда пересчитываются судьёй против текущей версии эталона.

### 2. Данные — вне репозитория

Путь `eval.dir` в конфиге. В наборе будут фрагменты кода и комментарии
приватного GitLab, поэтому в репозитории `review-agent` — только код и
пример формата на выдуманном кейсе. Состояние eval локальное — осознанное
исключение из принципа «состояние только в GitLab» (п.5 относится к
`poll`); записать в `docs/decisions.md`.

```
<eval_dir>/
  cases/<case>/
    case.yaml        project, iid, base, head ревью, финальный head, title, description
    sources/         комментарии GitLab, отчёт бота, ручное ревью, линтер, ...
    findings.yaml    эталон (версионируется)
    inbox.yaml       кандидаты на разметку
  baselines/vN/
    snapshot/        итоговый конфиг по проекту, шаблон, skills, opencode.json, versions
    fingerprint.yaml хэши по слоям
    runs/            отчёты ревью + результаты судьи
  history            accept / reject с заметками и ссылками на отчёты
```

### 3. Кейс

- Кейс — реальный MR с живым ревью (для старта 2–3, можно больше).
- **Head кейса — коммит, который видели ревьюеры**, а не финальный: в
  финальном замечания уже исправлены. Берётся из API версий diff MR
  (`/versions`) или `position.head_sha` diff-комментариев. По умолчанию —
  первый раунд ревью; комментарии последующих раундов — вне кейса (или
  отдельный кейс).
- Финальный head тоже сохраняется: diff «head ревью → финальный» — подсказка
  вердикта `fixed`.
- Отклонено: финальный head (баги уже исправлены); один эталонный MR (нет
  разброса по кейсам).

### 4. Источники и формирование эталона — один механизм

Любой источник — текстовый отчёт. Формирование эталона и оценка прогона
идут одним конвейером: извлечение → склейка → сопоставление с эталоном →
новое в `inbox.yaml` → разметка → применение → новая версия эталона.

Источники:

- комментарии людей в MR — автоматически через `glab` (файл, строки,
  автор, resolved, текст треда);
- отчёт бота `ai-review` на этом MR — автоматически, с пометкой, если `sha`
  маркера не совпадает с head кейса;
- любой текст от пользователя: своё ручное ревью, вывод линтера / `tsc` /
  Sonar, отчёт другого AI-инструмента, баг из трекера, найденный после
  мержа;
- отчёты прогонов агента — автоматически.

У каждой находки эталона `source` — только пометка происхождения, на
метрики не влияет. Отклонено: держать находки агента отдельно от
«ручного» эталона — эталон по определению всё найденное (п.1).

Рост эталона справедлив сам: если кандидат нашёл новые реальные проблемы,
baseline, перепроверенный судьёй по сохранённым отчётам, их «не нашёл».
Перепроверка не требует перезапуска ревью.

### 5. Разметка

Поля находки:

- `verdict`: `real` / `not-a-problem` / `duplicate: G-..` / `unclear` —
  влияет на метрики; `unclear` исключается;
- `outcome`: `fixed` / `tech-debt` / `ignored` — только информация,
  подсказывается git'ом;
- `severity`: blocker / major / minor — **оценка человека**, не агента;
- `needs`: `code` / `repo-docs` / `business-rules` / `runtime` / `history` —
  какое знание нужно, чтобы найти; для анализа «что лечится моделью, а что
  окружением».

Граница автоматики (решено): **`verdict` ставит только человек**, кроме
явных авто-правил; `severity`, `needs`, `outcome` принимаются из
предложений судьи, если человек их не поправил. Иначе эталон делала бы
модель, которую им же и меряют.

Сокращение ручной работы (оценка: ~150 сырых находок за сравнение → обычно
0–3 строки для человека):

1. склейка повторов — одна проблема из нескольких отчётов = один кандидат;
2. уже в эталоне — судья узнаёт, работы нет; совпадение с
   `not-a-problem` автоматически считается ложным срабатыванием;
3. авто-правила (настраиваемые, отключаемые, помечаются
   `labeled_by: rule:<имя>`): «комментарий человека + участок изменён
   после ревью» → `real`/`fixed`; «находка линтера» → `real`/`minor`;
4. ленивая разметка — `inbox.yaml` сортируется по влиянию на текущее
   сравнение: важно только то, что нашла одна сторона; отчёт пишет, сколько
   неразмеченных могут изменить вывод;
5. в каждой строке готовые предложения судьи, ссылка на код в GitLab,
   git-подсказка `after_review: changed`; человек правит несогласное и
   отмечает просмотренное, затем одна команда применяет.

Интерфейс — файл YAML (решено: проще работать с файлом). Отклонено:
интерактивная разметка в терминале — нельзя отложить и вернуться.

### 6. Судья

- Отвечает на узкий вопрос «эта находка отчёта — та же, что эталонная?»,
  истинность не оценивает.
- Шаги: извлечь находки из отчёта (сверка числа с `count_findings` —
  при расхождении пометка «проверь извлечение»); склеить; сопоставить.
- Вердикты сопоставления: `match` — то же место и тот же механизм
  («разработчик исправил бы то же самое»); `partial` — место верное,
  причина неверна или размыта (для gate — не найдено, но видно в отчёте);
  `new` — кандидат на разметку. Одна находка может закрыть две эталонные;
  две находки про одну эталонную — дубль.
- Для `match` / `partial` обязательна цитата из отчёта, без неё вердикт не
  принимается.
- Судья видит только текст (отчёт и эталон), не код — поэтому описание
  эталонной находки должно быть конкретным: файл, строки, механизм,
  последствие.
- Конфиг: `eval.judge.model`, `reasoning_effort`, `template` (по умолчанию
  встроенный шаблон, по аналогии с промптом ревью). Ответ — JSON (судье
  можно, он не измеряемая система).
- Вызов — наша обёртка поверх `opencode run` с агентом без инструментов,
  через тот же `harness.py` (`--file`, `stdin=DEVNULL`). Отклонено: прямой
  вызов API через SDK — нужен API-ключ, отдельная оплата, своя интеграция
  на провайдера.
- Проверка судьи: на первых прогонах человек смотрит таблицу сопоставления;
  частые ошибки → правка шаблона или модели.
- Результат судьи кэшируется по `(хэш отчёта, версия эталона, версия
  судьи)`; при изменении эталона перепроверяются только текущий baseline и
  последний кандидат, а не вся история.

### 7. Снимок и отпечаток окружения

- При `accept` сохраняется **снимок**: итоговые настройки по проекту кейса
  (с переопределениями), отрендеренный шаблон, содержимое skills,
  сгенерированный `opencode.json`, версии (OpenCode, точный ID модели,
  коммит `review-agent`). По снимку инструмент сам показывает, что
  изменилось, и даёт diff для отката.
- Отпечаток (хэши снимка) — **по проекту кейса**: изменение настроек одного
  проекта не делает недействительными замеры другого.
- Слои (состав настраивается в конфиге):
  - строгий — модель, effort, промпт, skills, `opencode.json`: отчёты
    baseline недействительны, нужен перезапуск;
  - мягкий — версия OpenCode, коммит `review-agent`: отчёты годны,
    в отчёте сравнения предупреждение;
  - судья — модель и шаблон судьи: отчёты ревью годны всегда, нужна только
    перепроверка судьёй.
- Замер годен, пока совпадает строгий слой, **без срока годности**
  (решено). Принудительный перезамер — явным флагом.
- Отклонено: «любое изменение отпечатка = недействительный замер» —
  обновление OpenCode вероятно влияет слабее смены модели; срок годности
  замера (2 недели).

### 8. Прогон

- `eval run` без аргументов: собирает текущее окружение, показывает
  изменения относительно последнего принятого baseline (строгие / мягкие),
  годность отчётов baseline, план и цену («9 ревью, продолжить?»). Если
  ничего не изменилось — «мерить нечего».
- Набор кейсов и число повторов — в конфиге (`eval.suite`,
  `eval.repeats`), по умолчанию 3 кейса × 3 повтора.
- Повторы независимы: отдельная сессия на каждый. Отклонено: одна сессия
  на несколько повторов — второй проход видит находки первого, разброс не
  измерить.
- **Волны**: волна = каждый кейс по одному разу; судья — сразу после
  каждого ревью; после волны — правило ранней остановки (подтверждено):
  стоп, если кандидат потерял Blocker, который baseline находил во всех
  повторах, или по всем SEV ниже худшего повтора baseline. Отключается в
  конфиге. Остановленный прогон выпускает отчёт с пометкой «неполный».
  Ранняя остановка опирается только на сопоставление с размеченным
  эталоном.
- **Worktree**: один на кейс, общий для его повторов (одновременно —
  столько, сколько кейсов); перед повтором проверка чистоты (`git status`
  пуст); удаление гарантировано в любом исходе — конец, ранняя остановка,
  Ctrl+C, ошибка; жёстко убитый процесс подбирает существующая очистка
  сирот. Побочный эффект — одинаковый путь worktree в промпте даёт
  небольшой выигрыш prompt-cache между повторами.
- Кэш провайдера: привязан к префиксу запроса, а не к сессии; внутри
  прогона уже работает (`cache_read` в журнале), между повторами общий
  только короткий префикс — экономия на уровне процентов. Основная
  экономия — не запускать лишние прогоны (переиспользование замера
  baseline, ранняя остановка).

### 9. Отчёт и решение

Отчёт сравнения (markdown в `eval_dir`):

- шапка: версия эталона, число неразмеченных и сколько из них может
  изменить вывод; diff отпечатков;
- таблица покрытия эталона **по SEV** (Blocker / Major / Minor), baseline
  против кандидата; ложные срабатывания; стоимость и время из журнала;
- по каждой эталонной находке — доля повторов, где найдена; списки
  «потеряно» и «приобретено»;
- не найдено обеими сторонами — с разбивкой по `needs`.

Отклонено: одна взвешенная цифра recall (веса SEV 3/2/1) — менее понятна,
чем таблица по SEV.

Решение — за человеком:

- `accept` — проверяет, что окружение не менялось после замера (иначе
  отказ), снимок текущего окружения становится baseline vN+1, запись в
  историю;
- `reject` — запись в историю (что изменили, что ухудшилось, отчёт,
  заметка); откат делает человек, инструмент показывает diff к снимку
  baseline.

Абсолютная мера (покрытие эталона по версиям baseline) показывается как
траектория прогресса; для решения используется относительное сравнение.

### 10. Типовые сценарии (для ориентира при реализации)

Заведение кейса: `case add` (glab: MR, комментарии, head ревью и
финальный, отчёт бота) → человек `source add` (своё ревью, линтер) →
`ingest` (судья + git-подсказки + авто-правила → inbox) → **разметка**
(разово крупная) → `apply` (эталон v1) → кейс в `eval.suite` → `run
--baseline` (3 повтора текущего окружения) → доразметка нового от агента →
`apply` (эталон v2).

Итерация: человек правит окружение → `run` (что изменилось, план, цена,
подтверждение) → волны с ранней остановкой → отчёт + inbox по влиянию →
разметка 0–3 строк → `apply` (перепроверка судьёй, отчёт заново) →
`accept` / `reject`.

### 11. План реализации

1. **Spike** (вживую): (а) можно ли получить head ревью после force-push
   автора MR (`git fetch origin <sha>`, keep-around refs GitLab);
   (б) надёжность JSON-ответа судьи через `opencode run` на Windows.
2. **Change A — кейсы и эталон** (`review-eval-golden-set`): кейсы,
   источники, судья, inbox / apply, авто-правила, git-подсказки. Полезен
   сам по себе: покрытие эталона текущим боевым ревью по сохранённым
   отчётам. Ручная проверка — завести 1–2 реальных кейса.
3. **Change B — замер окружения** (`review-eval-runs`): снимок и
   отпечаток, волны, общий worktree, ранняя остановка, отчёт, accept /
   reject / история, пометка в журнале, lock.
4. Отдельно (можно раньше): починка knowledge-skills (бэклог п.7) — иначе
   eval по skills покажет «без эффекта» из-за бага, а не из-за skills.

## Risks / Trade-offs

- [Head ревью недоступен после force-push: кэш берёт только последний
  `refs/merge-requests/<iid>/head`] → spike; до него `case add` проверяет
  доступность коммита и отказывает понятным сообщением.
- [Битый JSON от судьи в выводе OpenCode] → проверка схемы, один повтор,
  иначе «судья не справился» для этого отчёта.
- [Ctrl+C на Windows не гасит дочерний `opencode`] → явное завершение
  дочернего процесса; проверить вживую.
- [Лимит подписки: ~9 ревью на итерацию плюс судья; первичный кейс дороже]
  → ранняя остановка, переиспользование замера, подтверждение плана с ценой;
  годится для редких итераций, не для ежедневных.
- [Малая выборка — шум выдаётся за эффект] → доля по каждой находке в
  отчёте; решение за человеком.
- [Судья систематически ошибается в сопоставлении] → обязательная цитата,
  ручная проверка на первых прогонах, версия судьи в отпечатке.
- [Эталон делает модель] → `verdict` только человек, авто-правила явные и
  помечены.
- [Пока идёт эксперимент, `poll` по расписанию ревьюит боевые MR
  экспериментальным окружением] → принято осознанно (один конфиг).
- [`opencode.db` растёт быстрее — ~1,3 МБ на прогон] → уже в бэклоге.
- [Баг knowledge-skills искажает выводы по skills] → починить до замеров
  skills (п.11.4).

## Open Questions

- Lock с `poll`: брать тот же `poll.lock` (просто, но `poll` пропускает
  проходы около часа) или отдельный lock с разделением кэша клонов и
  профиля OpenCode. Склоняемся к общему `poll.lock`.
- Пороги правила ранней остановки и авто-правил — уточнить после первых
  реальных прогонов, когда виден разброс.
- Точные имена подкоманд и раскладка файлов `eval_dir` — решить при
  propose change A (интерфейс сознательно отложен).
- Формат источника «ручное ревью» — свободный markdown предполагается
  достаточным (его разбирает судья); проверить на первом кейсе.
