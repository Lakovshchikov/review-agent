# Design

## Context

Конфиг загружается в `config.load_config(path)`; `--config` в четырёх разборщиках `cli.py` имеет default `"config.yaml"`. Сейчас `_absolute()` делает `os.path.abspath` от текущей папки только для `skills` и `prompt.template`; `storage.work_dir` (default `./.review-agent`), `report.output_path` и проектный `local_repo` остаются относительными и трактуются процессом от cwd. `best_effort_work_dir` читает `work_dir` из сырого YAML для лога ошибки конфига. `register-task.ps1` задаёт рабочую папку сам, поэтому планировщик от этого change не зависит. Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**
- Один источник «дома»: `REVIEW_AGENT_HOME`; конфиг и все относительные пути привязаны к папке конфига.
- Скрипты настройки машины для Windows и macOS без вопросов пользователю.

**Non-Goals:**
- Не меняем место конфига по умолчанию на системное (`~/.config`) — дом это репозиторий.
- Не трогаем ручной режим: репозиторий для ревью по-прежнему задаётся `--repo`.
- Не поддерживаем Linux-скрипт отдельно (`set-home.sh` по умолчанию пишет в `~/.zshrc`, `--rc-file` позволяет указать `~/.bashrc`), системные и CI-окружения.

## Decisions

1. **Функция `resolve_config_path(arg: str | None) -> Path` в `config.py`.** Порядок: `arg` → `$REVIEW_AGENT_HOME/config.yaml` → `./config.yaml`. Возвращает путь, существование проверяет `load_config` (его ошибка «Could not read config file» дополняется подсказкой про `REVIEW_AGENT_HOME`/`--config`). Все четыре подкоманды вызывают её; default у `--config` становится `None`. *Альтернатива:* env-переменная с путём к самому файлу — отклонена: дом нужен и как база путей, одна переменная проще.
2. **База относительных путей — папка конфига.** `load_config` получает `base = path.resolve().parent` и применяет `_absolute(value, base)` к `skills`, `prompt.template` (глобальный и проектный), `storage.work_dir`, `report.output_path`, `local_repo`. `best_effort_work_dir` резолвит так же. Результат для конфига в корне репо при запуске оттуда не меняется. *Альтернатива:* резолвить от папки конфига только при поиске через переменную — отклонена: два правила в одной системе путают сильнее, чем мягкая несовместимость (проект один пользователь, поведение при `--config` на чужую папку и так редкое).
3. **`report.output_path` содержит `{run_id}`**: резолвится как строка-шаблон (`os.path.join(base, value)` до `.format`), а не как существующий путь. Печать итогового абсолютного пути остаётся в `cli.py`; для `poll --dry-run` проверяем, что итоговая сводка проходa перечисляет `kept_paths`, и добавляем вывод, если нет.
4. **Скрипты в стиле `register-task.ps1`.** `set-home.ps1`: параметры `-Remove`, `-DryRun`; `[Environment]::SetEnvironmentVariable("REVIEW_AGENT_HOME", $home, "User")`; предварительно проверка `pipx` (`Get-Command`), затем `pipx install --force -e $home`. `set-home.sh`: `--remove`, `--dry-run`, `--rc-file`; блок между строками `# >>> review-agent >>>` и `# <<< review-agent <<<` заменяется целиком (`awk`/`sed`), значение пути экранируется кавычками. Путь дома: `$PSScriptRoot\..` и `$(cd "$(dirname "$0")/.." && pwd)`. Установка не отдельный флаг, а нормальное поведение (решение пользователя). Удаление: `pipx uninstall review-agent` и снятие переменной/блока.
5. **Проверка скриптов.** Статические тесты по образцу `test_register_script.py` (наличие параметров, маркеров, команд). `.sh` дополнительно прогоняется в тесте на временном rc-файле через `bash` (пропуск на Windows без bash), проверяя идемпотентность блока. Живая проверка на Windows и macOS — в `validation-notes.md` после apply.

## Risks / Trade-offs

- [Старый запуск с `--config` на файл в другой папке и относительными путями меняет место `work_dir`] → в README и `docs/configuration.md` явное правило «от папки конфига»; `docs/troubleshooting.md` — «файлы появились не там».
- [Открытая консоль не видит новую переменную] → скрипт печатает «откройте новую консоль»; troubleshooting.
- [Перенос репозитория ломает переменную и editable-установку] → повторный запуск скрипта (идемпотентен).
- [`pipx` отсутствует] → скрипт останавливается до изменений и печатает команды установки.
- [Переменная на macOS видна только интерактивным zsh; cron/GUI её не увидят] → для таких запусков `--config`; указано в docs.

## Migration Plan

Пользователь один раз запускает `set-home.ps1` / `set-home.sh`. Существующий `config.yaml` в корне репо и Task Scheduler (рабочая папка = корень) продолжают работать без правок. Откат: запуск скрипта с `-Remove`/`--remove`.
