# Design

## Context

Мотивация описана в proposal.md (раздел Why). Ниже только то, что влияет на
подход.

- Читатели документации: человек, который ставит и запускает агент
  (оператор), и агент, который дорабатывает проект (Claude Code,
  OpenSpec-сессии). Оператору нужен справочник, агенту нужны ограничения и
  карта.
- На разделы AGENTS.md ссылаются код и конфиг: «AGENTS.md section 4/5» в
  `cli.py`, `publishing.py`, `review_stats.py`, `register-task.ps1`;
  «AGENTS.md п.7» в `openspec/config.yaml`. На раздел README «Как следить
  за задачей» ссылается подсказка в `register-task.ps1`.
- Архивы change'ей (`openspec/changes/archive/*/validation-notes.md`,
  `design.md`) уже хранят полную историю проверок. Документация может
  ссылаться на них, а не пересказывать.
- OpenSpec-артефакты (`openspec/specs/`, архив, схема) по желанию
  пользователя не меняются.

## Goals / Non-Goals

**Goals:**
- Каждый факт об использовании живёт в одном подробном месте (`docs/*`).
  README даёт краткую, но **полную** выжимку: все команды, флаги,
  параметры скрипта, ключи конфига, коды выхода, установку и зависимости.
- Документация описывает текущее состояние, а не историю появления:
  в README и `docs/` (кроме `decisions.md`) нет «Change N», «раньше было»,
  «проверено вживую на …».
- Агент по одному AGENTS.md понимает, где что лежит и какой документ
  обновить при изменении.

**Non-Goals:**
- Переписывать или переструктурировать спецификации OpenSpec и архивы.
- Менять поведение, формат конфига или CLI. Исключение: правка docstring
  и текста подсказки без изменения логики.
- Переводить документацию на английский или поднимать генератор сайта
  (mkdocs и т.п.).
- Документировать будущие фичи из бэклога (кроме самого списка бэклога в
  AGENTS.md).

## Decisions

### 1. Три слоя по читателю

| Слой | Читатель | Содержимое |
|---|---|---|
| `README.md` | оператор, первый вход | что это, схема (5–7 строк), зависимости, установка, быстрый старт, справочник команд/флагов/параметров/ключей одной строкой на пункт, ссылки на `docs/` |
| `docs/*.md` | оператор, когда нужны подробности; агент — по ссылкам из карты | по одному файлу на тему (список в proposal.md) |
| `AGENTS.md` | агент, разработчик проекта | принципы и ограничения, карта репозитория, правила обновления документации, дорожная карта (кратко), бэклог |

Почему не держать всё в README: ровно это и привело к 940 строкам.
Почему не убрать справочник из README полностью: пользователь хочет видеть
все команды, флаги и параметры в README сразу, без перехода по ссылкам.
Поэтому в README идёт краткая версия (таблицы «флаг — что делает»), а
подробности — в `docs/`.

### 2. Куда уходит каждый текущий раздел README

| Текущий раздел README | Куда |
|---|---|
| Вступление, «Два режима» | README: «Что это» без отсылок к Change N |
| Установка | README (как есть, плюс явный список внешних зависимостей с проверенными версиями: OpenCode 2.0.21, glab 1.115.0, Git for Windows 2.49, Python 3.10+) |
| Конфигурация, `storage`, `usage`, `gitlab`, переключение провайдера | README: таблица ключей (ключ — default — смысл). Полностью — `docs/configuration.md` |
| Безопасность: read-only permission setup | README: 3–4 строки «что агенту запрещено». Механизм — `docs/architecture.md`. Почему denylist и `--standalone` — `docs/decisions.md` |
| Критичный баг `--file` | `docs/decisions.md`. В README и `configuration.md` — одна строка «промпт передаётся только через `--file`, не меняйте» |
| Запуск (ручной режим), 7 шагов | README: синтаксис и флаги. Шаги — `docs/architecture.md` |
| Рабочая папка | README: дерево папок без пояснений. Полностью — `docs/work-dir.md`. Заметка о BREAKING `--scratch-dir` сводится к одной строке о ручном удалении старых папок |
| Учёт расхода, квота, `usage` | README: флаги `usage` и одна фраза о журнале. Полностью — `docs/usage-accounting.md` |
| Опрос GitLab (шаги, кэш, лог, режимы, маркер, ссылки, claim, lock) | README: синтаксис, флаги, режимы в две строки, коды выхода. Полностью — `docs/polling.md` |
| Запуск по расписанию | README: команды и таблица параметров `register-task.ps1`. Остальное — `docs/scheduling.md` |
| Как следить за задачей | `docs/scheduling.md`. Таблица кодов `0x…` дублируется в `docs/troubleshooting.md` ссылкой, не копией |
| Тесты | README: `pytest`, две строки. История живых прогонов удаляется: она есть в архивах |

### 3. `docs/decisions.md` — формат «решение → причина → где проверено»

Каждое решение оформляется коротким блоком: что сделано, почему (какой
сбой без этого), где проверено (ссылка на `validation-notes.md` нужного
архива) и где реализовано (модуль). Подробности не пересказываются: вместо
этого стоит ссылка на архив. Так длинные пояснения уходят из README,
`config.example.yaml` и AGENTS.md п.4, но не теряются.

Альтернатива: оставить обоснования в AGENTS.md. Отклонена, потому что
AGENTS.md читается каждой сессией целиком, и детали вроде cmd.exe-шимов
нужны ей только при работе с харнессом. Хватит одной строки с ссылкой.

### 4. AGENTS.md: сохраняем нумерацию разделов

Разделы 1–9 сохраняют номера и названия, чтобы ссылки «section 4/5» и
«п.7» остались верными. Новые разделы («Карта репозитория», «Актуализация
документации») добавляются в конец как 10 и 11. В шапку AGENTS.md
добавляется одна строка: «каждый change обязан актуализировать
документацию — см. п.11». Сокращаем так:

- п.4: принципы остаются, абзац про механизм denylist сжимается до 2–3
  строк со ссылкой на `docs/decisions.md`;
- п.7: шесть подробных абзацев превращаются в таблицу «# — change — суть
  одной строкой — архив». Бэклог остаётся списком;
- п.9: команды остаются, описание рабочей папки заменяется ссылкой на
  `docs/work-dir.md`.

Карта репозитория (п.10): `src/review_agent/` — модуль и его
ответственность (одна строка на модуль), `tests/` и
`tests/fixtures/`, `scripts/`, `docs/`, `openspec/specs/` (capability →
какие модули), `openspec/changes/archive/` (где искать историю и
validation-notes), `config.example.yaml`.

Содержимое п.11 описано в решении 7.

### 7. Правило «каждый change актуализирует документацию»

Правило должно срабатывать само, без того чтобы кто-то о нём вспоминал.
Поэтому оно живёт в одном месте, а в момент работы его подтягивают
отсылки.

**Источник правды — AGENTS.md п.11 «Актуализация документации».** Здесь,
а не в README: README адресован оператору, а AGENTS.md каждая сессия
(Claude Code, OpenSpec) читает целиком перед работой. В п.11 входят:

- Общее правило: change считается завершённым, только когда README,
  `docs/`, AGENTS.md, `config.example.yaml` и `openspec/config.yaml`
  описывают состояние **после** него. Если документация не затронута,
  это записывается явно («документация не затронута: …»), а не
  подразумевается молча.
- Таблица «что изменилось → что обновить»:

  | Изменение | Обновить |
  |---|---|
  | флаг или подкоманда CLI | README (таблица флагов), `docs/<тема>.md` |
  | параметр `register-task.ps1` | README, `docs/scheduling.md` |
  | ключ конфига, значение по умолчанию | README (таблица ключей), `docs/configuration.md`, `config.example.yaml` |
  | новый файл или папка в `work_dir`, срок хранения | README (дерево), `docs/work-dir.md` |
  | поведение `poll` (шаги, маркер, claim, коды выхода) | `docs/polling.md`, коды выхода в README |
  | новый модуль, перенос ответственности | AGENTS.md п.10 (карта), `docs/architecture.md` |
  | новая capability в `openspec/specs/` | AGENTS.md п.10 (capability → модули) |
  | обходной путь, проверенный вживую | `docs/decisions.md` |
  | новый симптом сбоя и способ его исправить | `docs/troubleshooting.md` |
  | новая внешняя зависимость или проверенная версия | README (зависимости), AGENTS.md п.5 при изменении интеграции |
  | изменение принципов или ограничений | AGENTS.md п.3–5 |
  | архивация change | AGENTS.md п.7 (строка таблицы, бэклог), статус в `openspec/config.yaml` |

- Стиль: README и `docs/` (кроме `decisions.md`) описывают текущее
  состояние без истории («Change N», «раньше»). История живёт в архиве
  OpenSpec.

**Отсылки в `openspec/config.yaml`, которые подставляются в рабочий
процесс:**

- `rules.proposal`: в Impact перечислить затрагиваемые документы по
  AGENTS.md п.11;
- `rules.tasks`: каждая группа задач включает обновление документации по
  таблице AGENTS.md п.11 для своих изменений. Это согласуется с
  требованием схемы «каждая группа приносит свои тесты и документацию»;
- `operations.apply.guidance`: перед тем как отметить последнюю задачу,
  сверить документацию по AGENTS.md п.11 и прогнать `pytest
  tests/test_docs.py`;
- `operations.archive.guidance`: обновить AGENTS.md п.7 и статус в
  `openspec/config.yaml`; не архивировать, если документация не
  актуализирована.

Текст правила в `config.yaml` не копируется, только ссылка на п.11. Это
согласуется с шапкой AGENTS.md («не дублируй туда полный текст»).

**Механическая страховка** — тест `tests/test_docs.py` (решение 5). Он
ловит то, что можно проверить автоматически: флаги, параметры скрипта и
битые ссылки.

Альтернативы:
- Отдельный `docs/CONTRIBUTING.md` с правилом. Отклонено: агент читает его
  только если знает, что надо, а AGENTS.md читается всегда.
- Только текст в AGENTS.md без `openspec/config.yaml`. Отклонено: при
  генерации `tasks.md` агент получает `rules` прямо в инструкциях
  артефакта, и задача по документации появляется в плане сама, а не
  зависит от того, вспомнит ли агент про п.11.
- Хук Claude Code или CI-проверка «изменён код без изменения docs».
  Отклонено как избыточное на сейчас: много ложных срабатываний
  (рефакторинг без изменения поведения). Можно вернуться к этому на этапе
  CI.

### 5. Тест полноты README

`tests/test_docs.py` строит парсеры (`build_arg_parser`,
`build_poll_arg_parser`, `build_usage_arg_parser`), собирает все
`option_strings` с `--`, а из блока `param(...)` в
`scripts/register-task.ps1` — имена параметров, и проверяет, что каждое
имя встречается в `README.md`. Отдельно тест проверяет, что все
относительные ссылки на `docs/*.md` из README и AGENTS.md ведут на
существующие файлы.

Альтернатива: генерировать справочник флагов из argparse. Отклонена:
появляется шаг сборки документации, а русские описания пришлось бы держать
в коде, где `help` сейчас на английском. Тест на упоминание дешевле и
ловит главное — забытый флаг.

Ключи конфига тестом не проверяются: парсинг в `config.py` ручной, и
надёжно вытащить список ключей без рефакторинга нельзя. Это правило
вынесено в AGENTS.md п.11.

### 6. `config.example.yaml`: короткие комментарии

Остаются комментарии вида «что это; default; варианты». Пояснения багов
(`--file`, `--standalone`, denylist) сокращаются до одной строки
«обязательно, см. docs/decisions.md». Ключи и значения не меняются.

## Risks / Trade-offs

- [При переносе потеряется факт из README] → Перед удалением старого
  README пройти по его разделам по таблице из решения 2 и отметить, куда
  ушёл каждый абзац (задача в tasks.md). Удаляется только история, которая
  уже есть в архивах.
- [README и `docs/` разойдутся при следующих change'ах] → Правило
  AGENTS.md п.11, отсылки к нему в `openspec/config.yaml` (`rules` и
  `operations`, решение 7) и тест флагов.
- [Правило в `config.yaml` (`rules` и `operations`) не дойдёт до агента,
  если текущая версия OpenSpec CLI не выводит какое-то из этих полей] →
  При apply проверить: `openspec instructions tasks --change <любой>
  --json` содержит текст правила в `rules`. Если `operations` не
  поддерживается, правило остаётся в AGENTS.md п.11 и `rules`.
- [Сжатие AGENTS.md уберёт контекст, на который полагаются будущие
  сессии] → Исследовательский вывод (п.3) и принципы п.4–5 остаются
  полностью. Сжимаются только хроника и механика, и на каждое сжатие
  ставится ссылка.
- [Ссылки в старых архивах на разделы README («см. README, „Кэш
  репозиториев“») станут неточными] → Архивы — исторические документы,
  их не правим (Non-Goal). В `docs/` сохраняем узнаваемые заголовки
  разделов, чтобы ссылки было легко найти поиском.

## Migration Plan

Только документация. Откат делается через `git revert` коммита. Порядок
работ: сначала `docs/` (перенос без потерь), потом новый README, потом
AGENTS.md и мелкие правки, в конце тест. Так в любой точке ничего не
теряется.
