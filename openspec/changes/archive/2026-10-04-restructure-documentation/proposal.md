# Proposal

## Why

Документация проекта росла вместе с шестью change'ами и перестала быть
удобной. README — 940 строк, где справочник по использованию перемешан с
историей разработки («Change 1/2/3», «задачи 8.1/8.2»), живыми проверками
и объяснениями, почему решения приняты именно так (denylist вместо
allowlist, `--file` вместо позиционного промпта). Человеку трудно быстро
найти нужный флаг или ключ конфига. В AGENTS.md больше половины объёма
занимает подробная хроника change'ей (п.7), которая дублирует архив
OpenSpec и `openspec/config.yaml`. Карты «что где лежит» для агента при этом
нет. Сейчас все пункты дорожной карты выполнены, и следующие change пойдут
из бэклога, так что сейчас удобный момент навести порядок, пока
документацию не пришлось дописывать в восьмой раз.

## What Changes

- **README.md переписывается как краткий справочник по использованию**
  (~250–300 строк вместо 940). В нём: что это и схема работы в нескольких
  строках, внешние зависимости, установка, быстрый старт, **все** команды
  (`review-agent`, `poll`, `usage`, `scripts/register-task.ps1`) со
  **всеми** флагами и параметрами, коды выхода, **все** ключи конфига
  (кратко, одной строкой каждый), что остаётся на диске, тесты. Каждый
  раздел ссылается на подробный файл в `docs/`. Из README уходят история
  change'ей, рассказы о живых проверках, внутреннее устройство и
  обоснования решений.
- **Новая папка `docs/`** — подробности, перенесённые из README и
  дополненные:
  - `docs/configuration.md` — полный справочник конфига: каждый ключ,
    тип, значение по умолчанию, обязателен ли он, переопределения
    проекта, смена провайдера, skills;
  - `docs/polling.md` — проход `poll` по шагам, режимы, маркер, claim,
    lock, кэш репозиториев, ссылки на файлы в отчёте, лог прохода;
  - `docs/work-dir.md` — раскладка `storage.work_dir`, что и когда
    удаляется;
  - `docs/scheduling.md` — Task Scheduler: регистрация, режимы запуска,
    окно, как следить за задачей и коды результата;
  - `docs/usage-accounting.md` — журнал расхода, замер квоты, сводка
    `review-agent usage`;
  - `docs/architecture.md` — как устроено: поток одного прогона, модули
    `src/review_agent/` и их ответственность, внешние процессы;
  - `docs/decisions.md` — технические решения и их проверенные причины:
    denylist, `--standalone`, `--file` и cmd.exe, `encoding="utf-8"`,
    stdin у `opencode run`, isatty на Windows, `pythonw` вместо
    `conhost --headless`, credential helper `glab`;
  - `docs/troubleshooting.md` — симптом → причина → что делать (пустой
    отчёт, повисший claim/lock, «Agent not found», «Variant unavailable»,
    предупреждения учёта расхода, коды Task Scheduler).
- **AGENTS.md ужимается и получает карту проекта.** Остаются п.1–6
  (суть, среда, исследовательский вывод, архитектурные принципы,
  интеграция, отклонённые альтернативы) в сокращённом виде, без
  повторения технических подробностей, которые уходят в
  `docs/decisions.md`. П.7 становится таблицей «change → одна строка →
  ссылка на архив» и бэклогом. Добавляется раздел «Карта репозитория»:
  где код, тесты, docs/, openspec/, скрипты, а также какой документ
  обновлять при каком изменении. Номера разделов 4, 5 и 7 сохраняются,
  потому что на них ссылаются код и `openspec/config.yaml`.
- **Правило «каждый change актуализирует документацию».** Правило
  записывается в AGENTS.md п.11 «Актуализация документации»: change
  считается завершённым, только когда README, `docs/`, AGENTS.md,
  `config.example.yaml` и `openspec/config.yaml` описывают состояние после
  него. Там же — таблица «что изменилось → какой документ обновить». В шапке
  AGENTS.md стоит отсылка к п.11. В `openspec/config.yaml` добавляются
  короткие ссылки на п.11 в `rules` (proposal и tasks) и в `operations`
  (apply и archive). Так обновление документации само попадает в план
  каждого будущего change, а не зависит от того, вспомнит ли о нём агент.
- **Мелкие неточности, найденные при сверке с кодом**, исправляются по
  ходу. Примеры: README называет `reports/` неиспользуемой папкой, хотя
  это путь по умолчанию для отчёта ручного режима
  (`report.output_path`); список `denied_bash_patterns` в README
  расходится с `config.example.yaml`; формат `skills` (список путей к
  файлам) нигде не описан; в docstring `cli.py` не упомянут
  `--include-closed`; `scripts/register-task.ps1` отсылает к разделу
  README, который переезжает в `docs/scheduling.md`.
- **Комментарии `config.example.yaml`** сокращаются до «что это и
  значение по умолчанию» со ссылкой на `docs/configuration.md`. Длинные
  объяснения багов из комментариев переносятся в `docs/decisions.md`.
- **Проверка полноты README тестом:** новый тест проверяет, что каждый
  флаг из argparse-парсеров (`review-agent`, `poll`, `usage`) и каждый
  параметр `register-task.ps1` упомянут в README. Так README не отстанет
  от CLI при следующих change'ах.
- OpenSpec почти не трогается: `openspec/specs/`, архив и схема остаются
  как есть. В `openspec/config.yaml` добавляются только `rules` и
  `operations` со ссылкой на AGENTS.md п.11. Блок `context` не меняется.

## Capabilities

### New Capabilities

Нет. Change чисто документационный, поведение системы не меняется, поэтому
в `.openspec.yaml` стоит `skip_specs: true`.

### Modified Capabilities

Нет.

## Impact

- Файлы: `README.md`, `AGENTS.md`, новые `docs/*.md`,
  `openspec/config.yaml` (`rules` и `operations`),
  `config.example.yaml` (только комментарии), `scripts/register-task.ps1`
  (только текст подсказки), `src/review_agent/cli.py` (только docstring),
  новый тест `tests/test_docs.py`.
- Поведение CLI, формат конфига, публикуемые комментарии и журнал расхода
  не меняются.
- Для людей: README становится точкой входа, подробности лежат в `docs/`.
  Для агентов: AGENTS.md становится короче, в нём появляется карта.
  Устаревший раздел «Переход с Change 1–2 (BREAKING)» удаляется: флаг
  `--scratch-dir` убран давно. Короткая заметка о ручном удалении старой
  папки `.review-agent-scratch/` переезжает в `docs/work-dir.md`.
