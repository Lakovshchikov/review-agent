# Design

## Context

Мотивация — в proposal.md, раздел Why. Что есть сейчас:

- `prompt.py` содержит `string.Template` с методологией и две функции,
  собирающие секции «инструкции/docs» и «skills». Текст при пустом
  title/description тоже задан в коде. Там же лежат списки-кандидаты
  `_INSTRUCTION_FILE_CANDIDATES` и `_DOCS_DIR_CANDIDATES`.
- `pipeline.run_review` вызывает `discover_*` и `render_review_prompt`,
  пишет `prompt.md` и передаёт `config.skills` в журнал расхода.
- `config.effective_settings` подменяет у проекта `provider` и `skills`
  целиком через `dataclasses.replace(config, ...)`. Движок получает
  готовый `Config` проекта.
- Текущий промпт — проверенный baseline (AGENTS.md п.3). Его нельзя
  изменить даже пробелом незаметно.

## Goals / Non-Goals

**Goals:**

- Любой текст промпта и любая формулировка секций задаются файлом шаблона.
  В Python остаются только значения переменных.
- Встроенный шаблон даёт байт-в-байт прежний промпт. Это закреплено
  тестом на всех комбинациях входных данных.
- Ошибку в шаблоне видно до начала работы, все замечания сразу.

**Non-Goals:**

- Доставка содержимого skill-файлов агенту. Живая проверка показала, что
  OpenCode отклоняет чтение вне worktree (`external_directory`), так что
  skills не работали и до этого change. Чинится и переосмысляется
  отдельной задачей (AGENTS.md п.7); здесь — только абсолютные пути и
  предупреждение об отсутствующем файле.

- Переопределение `safety.denied_bash_patterns` для отдельного проекта
  (отдельная задача).
- Шаблоны из ревьюируемого репозитория (запрещено, см. решение 4).
- Новые переменные шаблона сверх текущего набора (например, head SHA или
  размер MR). Минимальный контекст по п.4 AGENTS.md не расширяется.
- Шаблон фразы-обёртки в `harness.command`: она уже настраивается.

## Decisions

### 1. Jinja2, только штатные механизмы

Нужны условия (секция есть, только если найден файл), циклы (список
skills) и наследование блоков. Сравнение вариантов:

- `string.Template` (stdlib) — без условий. Формулировки секций остались бы
  в коде, то есть переопределить можно было бы не всё. Отклонён.
- Mako — менее распространён, синтаксис похож на Python-код в тексте.
- Mustache/chevron — нет наследования блоков, библиотеки слабо
  поддерживаются.
- **Jinja2 3.1** — Pallets, активно выпускается, на нём работают Ansible,
  dbt, Home Assistant и chat-templates HuggingFace. Выбран.

Окружение рендера:

```
Environment(
  loader=ChoiceLoader([
      PrefixLoader({"builtin": PackageLoader("review_agent", "prompts")}),
      FileSystemLoader(<папка файла шаблона>),
  ]),
  undefined=StrictUndefined,   # боевой рендер: неизвестная переменная -> ошибка
  keep_trailing_newline=True,
  autoescape=False,            # markdown, не HTML
)
```

`PrefixLoader` стоит первым, поэтому `builtin/...` всегда ведёт в пакет, даже
если рядом с пользовательским шаблоном лежит папка `builtin/`. Шаблон
пользователя загружается из своей папки по имени файла, и
`{% include "common.md.j2" %}` рядом работает без дополнительной настройки.
`trim_blocks` и `lstrip_blocks` не включаются: пробелы встроенного шаблона
выверяются вручную и закрепляются golden-тестом (решение 2), а у
пользовательских шаблонов поведение остаётся стандартным для Jinja2.

### 2. Встроенный шаблон и проверка «байт в байт»

`src/review_agent/prompts/default.md.j2` поставляется как package data
(`[tool.setuptools.package-data]`). Блоки: `role`, `task`, `mr_context`,
`repo_context`, `skills`, `checklist`, `severity`, `fix`, `coverage`,
`confidence`, `restrictions`, `output`. Блоки позволяют наследнику заменить
один кусок, а `{{ super() }}` — дополнить его.

Регрессия: старый рендерер (`string.Template` и две функции секций)
переносится в тест как эталон. Тест сравнивает рендер нового шаблона и
эталона на всех комбинациях: инструкции есть/нет, docs есть/нет, skills
0/1/2, title и description пустые/непустые. Такое сравнение ловит любой
сдвиг пробела или перевода строки.

### 3. Модель настроек: по ключам, три уровня

```
встроенный дефолт  ->  глобальная секция prompt:  ->  prompt: проекта
(template=None,        (каждый ключ необязателен)     (каждый ключ необязателен)
 текущие списки)
```

- `PromptSettings(template: str | None, instruction_files: list[str],
  docs_dirs: list[str])` — итоговые значения. `template=None` означает
  встроенный шаблон. Глобальная секция загружается сразу в
  `PromptSettings`: незаданный ключ получает встроенный дефолт.
- У проекта есть `PromptOverrides` с теми же полями, все `None` по
  умолчанию. `effective_settings` объединяет значения по ключам и кладёт
  итог в `dataclasses.replace(config, prompt=...)`, как сейчас делается с
  `provider` и `skills`. Движок по-прежнему получает один готовый `Config`.
- Это отличается от `provider`, где блок заменяется целиком. `provider` —
  связанная тройка (модель без своего reasoning effort не имеет смысла), а
  ключи `prompt` независимы. Разница описывается в
  `docs/configuration.md`.
- Различать «явно `template: null` у проекта» (вернуться к встроенному при
  глобальном своём) и «не задан» нужно: `null` у проекта означает
  встроенный шаблон, отсутствие ключа — наследование. При загрузке это
  различается по наличию ключа в YAML, а «встроенный» хранится сентинелом
  `BUILTIN_TEMPLATE = "builtin/default.md.j2"`. Так у `PromptOverrides`
  `None` всегда означает «не задано».
- Пустые списки кандидатов допустимы: «не искать инструкции».

### 4. Шаблон только из конфига

Worktree — это head MR, его содержимое контролирует автор MR. Шаблон из
worktree позволил бы автору переписать инструкции ревьюеру (prompt
injection на уровне методологии). Загрузчик знает только папку файла из
конфига и пакет. Кандидаты `instruction_files` по-прежнему передаются
агенту путём, а не содержимым, как и раньше.

### 5. Проверка шаблона: пробный рендер с метками

Статический разбор (`jinja2.meta.find_undeclared_variables`) не видит
переменные родительского шаблона при `{% extends %}` и не различает, что
реально попало в текст. Поэтому применяется пробный рендер:

- Каждая переменная получает значение с уникальной меткой: строки вида
  `RACHECK_base_sha`, пути вида `Path("/RACHECK/worktree_path_RACHECK")`,
  список skills из одного такого пути. Опциональные значения задаются
  непустыми, чтобы условные секции рендерились. Переменная считается
  неиспользованной (**предупреждение**), если её метки нет в результате.
  Так учитывается и `{{ path.name }}`: метка входит в имя.
- Неизвестные переменные и атрибуты (**ошибки**, все сразу): при проверке
  `undefined` — подкласс `ChainableUndefined`, который записывает имя
  (`_undefined_name`, а для атрибута — `объект.имя`) при любом обращении
  (`__str__`, `__iter__`, `__bool__`, `__len__`, `__getattr__`) и не
  падает. Боевой рендер использует `StrictUndefined` (spec: «never
  substituting an empty value»).
- `TemplateSyntaxError` и `TemplateNotFound` (в том числе для
  `include`/`extends`) — ошибка файла. Jinja останавливается на первой
  синтаксической ошибке, поэтому для такого файла она единственная.
- Отсутствующий файл skill — предупреждение. Прогон без него возможен, а
  ломать работающее расписание из-за подсказки не стоит.

Результат проверки — список `PromptIssue(level, template, projects,
message)`. Одинаковые итоговые `PromptSettings` (шаблон и skills)
проверяются один раз, а в отчёте перечисляются все проекты, где они
используются. Логика живёт в новом модуле `prompt_check.py`, а `prompt.py`
остаётся местом рендера и поиска кандидатов.

### 6. Где и как проверка встраивается в команды

```
poll:    load_config -> (интерактив без консоли? отказ) -> проверка шаблонов
         включённых проектов -> ошибки? exit 2
                              -> только WARN: --all -> лог, дальше
                                              интерактив -> один вопрос [y/N]
         -> lock -> housekeeping -> GitLab ...
manual:  load_config -> проверка глобальных настроек -> ошибки? exit 2
         -> WARN: консоль есть -> вопрос; нет -> stderr, дальше -> lock -> ревью
prompt-check: только проверка (+ --show), без lock, GitLab и worktree
```

Проверка идёт до lock и GitLab, чтобы отказ ничего не оставлял за собой.
Отказ в ответ на вопрос — `EXIT_NOT_STARTED` (2): проход не начинался.
Это отличается от `q` при выборе MR (0), где проход прошёл, но ревьюить
нечего. Новых флагов нет: `--all` и отсутствие консоли уже означают «без
вопросов».

`prompt-check` — подкоманда, которая определяется по первому токену, как
`poll` и `usage` (решение 6 из core-review-engine). Коды выхода: 0 — чисто,
1 — только WARN, 2 — ERROR или конфиг не загрузился. `--template FILE`
проверяет файл с глобальными skills из конфига, если конфиг загрузился.
Без конфига skills пустые, конфиг для этого режима необязателен.
`--project` и `--template` взаимоисключающие.

### 7. Абсолютные пути

`load_config` превращает `prompt.template` (глобальный и проектов) и
`skills` в абсолютные пути через `os.path.abspath` (от CWD, без
разворачивания symlink). Правило «относительно текущей папки процесса» не
меняется, но фиксируется в момент загрузки. Агент работает из worktree и
теперь получает в промпте рабочий путь к skill (прочитать файл ему мешает
`external_directory` — см. Non-Goals). `work_dir`, `local_repo` и
`report.output_path` не трогаются: их использует сам процесс, проблемы с
ними нет.

### 8. Журнал расхода

Новые поля `review.prompt.template` (абсолютный путь или
`builtin/default.md.j2`) и `review.prompt.sha256` (sha256 содержимого
файла шаблона). При `extends`/`include` хэшируется только сам файл.
Изменение родителя видно по смене версии пакета (встроенный шаблон) или по
хэшу собственного include-файла. Это ограничение описывается в документации.
Схема остаётся `review-agent.usage/1`: поля только добавляются, а
`usage_summary` читает записи через `.get`, поэтому старые строки журнала
остаются валидными.

## Risks / Trade-offs

- [Незаметная регрессия baseline при переносе текста в шаблон] →
  golden-тест на всех комбинациях входов против старого рендерера, который
  сохранён в тесте.
- [Фигурные скобки `{{ }}` в тексте пользовательского шаблона, например в
  примерах кода, Jinja2 поймёт как выражение] → ошибка видна в
  `prompt-check`, обход `{% raw %}` описан в `docs/prompt.md`. Во
  встроенном тексте скобок нет.
- [Шаблон без нужной переменной (например, `base_sha`) даёт слабое ревью]
  → предупреждение и вопрос в интерактиве. В `--all` только запись в лог —
  это осознанный выбор пользователя ради стабильного расписания.
- [Проверка по меткам считает переменную, использованную только в условии
  `{% if %}` без вывода, неиспользованной] → это предупреждение, а не
  ошибка: агент действительно не получает значение. Поведение описывается в
  документации.
- [Новая зависимость Jinja2] → широко распространённая, чистый Python плюс
  MarkupSafe, wheels для Windows есть.
- [sha256 не отражает изменений родительского шаблона при `extends`] →
  описано, решение 8.

## Migration Plan

Действий не требуется. Конфиг без секции `prompt` работает как раньше и
даёт тот же промпт. Относительные `skills` становятся абсолютными при
загрузке, и в промпт попадает уже рабочий путь. Откат — предыдущая версия
пакета: незнакомую секцию `prompt` старый загрузчик игнорирует.
