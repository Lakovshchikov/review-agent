# Proposal: scheduling-and-multi-repo-config

## Why

`review-agent poll --all` проверен на боевом GitLab (Change 2), но пока запускается только руками из терминала. Для безнадзорной работы по расписанию на Windows (`AGENTS.md` §2, §5; итог `validation-notes.md` Change 2) не хватает:
- штатной регистрации в Task Scheduler;
- предсказуемого следа на диске: сейчас временные файлы прогонов копятся в разных местах, а результат прохода виден лишь в консоли;
- защиты от двойного ревью одного MR, когда проходов много: список кандидатов устаревает за время длинного прохода, а ревью, идущее на другой машине или из другой рабочей папки, ничем не видно;
- конфига, в котором у отдельного проекта могут быть свои настройки.

## What Changes

- **Регистрация в Task Scheduler.** PowerShell-скрипт `scripts/register-task.ps1` создаёт, обновляет и удаляет задачу Windows. Задача по интервалу вызывает `review-agent poll --all` с нужным конфигом из папки проекта и не запускает второй экземпляр, пока идёт первый. Режимы `-DryRun` и `-DebugMode`. Python-код о планировщике ничего не знает (`AGENTS.md` §5). README получает инструкцию, как следить за задачей встроенными средствами Windows (Планировщик заданий, Диспетчер задач, Монитор ресурсов, Просмотр событий, `Get-ScheduledTaskInfo`). Бандл в один exe не собирается: задача запускает обычный pip-запускатель из venv.
- **Рабочая папка в конфиге, по умолчанию удаляется всё.** Новая секция `storage.work_dir`: всё, что `review-agent` пишет на диск, лежит только в ней.
  - Временное (worktree, промпт, safety-note, отчёт, тело запроса в GitLab) создаётся в `<work_dir>/tmp/` и удаляется сразу после каждого MR. Ручной режим оставляет только итоговый отчёт по `report.output_path`.
  - Остатки упавших прогонов удаляются в начале следующего прохода.
  - Сохраняются только: лог каждого прохода (`logs/`), stderr харнесса **для упавших** ревью (`logs/`), несостоявшийся комментарий в `--dry-run` (`dry-run/`). Всё это удаляется в начале прохода по сроку хранения `storage.retention_days` (по умолчанию 7 дней, `null` — не удалять).
  - Флаг `--debug` сохраняет все артефакты прогона в `debug/`; они удаляются по тому же сроку хранения.
- **Защита от двойного ревью через claim в GitLab.**
  - Прямо перед ревью каждого MR (а не только в начале прохода) заново проверяются маркер готового ревью и «живой» claim — комментарий бота «ревью выполняется».
  - Затем публикуется свой claim. Гонка двух одновременных claim'ов разрешается в пользу более раннего.
  - По окончании claim-комментарий редактируется в итоговый отчёт. При сбое claim удаляется.
  - Claim старше `gitlab.claim_ttl_minutes` считается мёртвым.
  - В `--dry-run` в GitLab по-прежнему ничего не пишется.
- **Переопределения на уровне проекта.** У каждого элемента `gitlab.projects` появляются необязательные поля `enabled`, `reviewers`, `review_drafts`, `provider`, `skills`. Если поле не указано, берётся глобальное значение. Глобальный `gitlab.reviewers` становится необязательным, если у каждого включённого проекта есть свой список.
- **BREAKING:** флаг `--scratch-dir` убран из `review-agent poll` и из ручного режима — путь задаётся только `storage.work_dir`. Отчёты `poll` больше не пишутся в папку `report.output_path`. Ручной прогон теперь берёт тот же lock рабочей папки, что и `poll`. Конфиги без новых секций по-прежнему загружаются (используются значения по умолчанию).

Вне скоупа (явно):
- креды GitLab в конфиге и автоавторизация `glab`;
- повторное ревью при новом head SHA;
- параллельные ревью и ограничение числа MR за проход;
- уведомления о сбоях;
- cron/systemd/GitLab CI `schedule`;
- сборка бандла (PyInstaller и т.п.);
- per-project переопределение `safety`/`harness`/`min_report_chars`;
- очистка git-объектов, принесённых `git fetch` в локальный клон, и собственной истории сессий OpenCode в профиле пользователя (не наши файлы; ограничение описано в design).

## Capabilities

### New Capabilities
- `project-review-settings`: эффективные настройки ревью для каждого сконфигурированного GitLab-проекта (включён ли проект, ревьюеры, политика draft-MR, провайдер модели, knowledge-skill'ы) с откатом к глобальным значениям.
- `local-artifact-lifecycle`: единая рабочая папка из конфига, немедленное удаление временных файлов прогона, лог каждого прохода, удаление сохраняемых артефактов по сроку хранения, режим отладки.
- `review-claim`: метка «ревью выполняется» в GitLab, которая не даёт двум проходам (на одной или разных машинах) ревьюить один MR одновременно.
- `scheduled-task-registration`: регистрация, обновление и удаление задачи Windows Task Scheduler, периодически запускающей автоматический проход опроса.

### Modified Capabilities
- `mr-discovery`:
  - фильтр по ревьюеру и правило draft-MR применяются с настройками проекта, выключенные проекты не опрашиваются;
  - проверка «уже отревьюен» повторяется прямо перед ревью каждого MR и учитывает живой claim.
- `review-publishing`:
  - отчёт публикуется заменой текста claim-комментария;
  - при сбое claim удаляется;
  - в dry-run результат сохраняется в рабочей папке.
- `review-polling-run`: один проход за раз — на рабочую папку из конфига, а не на `--scratch-dir`.

## Impact

- Код:
  - `src/review_agent/config.py` — поля проекта, секции `storage`, `gitlab.claim_ttl_minutes`;
  - `src/review_agent/polling.py` — настройки проекта, claim, лог прохода, очистка;
  - `src/review_agent/pipeline.py` и `src/review_agent/cli.py` — готовый `Config`, рабочая папка вместо `--scratch-dir`, `--debug`, lock в ручном режиме;
  - `src/review_agent/gitlab.py` — `post_note` возвращает id, новые `update_note`/`delete_note`;
  - `src/review_agent/publishing.py` — маркер claim и его разбор;
  - новые модули `passlog.py`, `housekeeping.py`;
  - новый скрипт `scripts/register-task.ps1`.
- Конфиг: новая секция `storage`, необязательные поля в `gitlab.projects[*]`, `gitlab.claim_ttl_minutes`; правки `config.example.yaml`, README, `AGENTS.md` §9.
- GitLab: на каждый MR в работе бот на время ревью публикует claim-комментарий и потом редактирует его. Нужны права на редактирование и удаление своих notes (у автора они есть по умолчанию).
- Зависимости: новых нет.
- Эксплуатация: относительные пути конфига (включая `storage.work_dir`) разрешаются от рабочей папки процесса — задача Task Scheduler запускается с рабочей папкой проекта (скрипт это задаёт).
