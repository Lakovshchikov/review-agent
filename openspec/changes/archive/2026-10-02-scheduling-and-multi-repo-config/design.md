# Design: scheduling-and-multi-repo-config

## Context

Мотивация — `proposal.md` (Why). Что уже есть после Change 2 и на что опирается дизайн:

- **Вывод прохода.** `review-agent poll` (`src/review_agent/polling.py`) — один проход. Весь вывод идёт через инжектируемый `output_fn` (по умолчанию `print`), ошибки до старта — прямыми `print(..., file=sys.stderr)`. Лог-файла нет.
- **Lock и выбор MR.** `poll_lock` (`<scratch>/poll.lock`) пускает только один проход за раз. Список кандидатов с проверкой маркера строится **один раз в начале прохода**. Повторная проверка маркера есть только перед публикацией. Ревью, идущее в другом проходе (другая scratch-папка, другая машина), ничем не видно.
- **Мусор на диске** (разбросан по трём местам):
  - `<scratch>/<run_id>/`: worktree удаляется, но `prompt.md` и safety-note остаются;
  - `<scratch>/notes/*.json` — тела POST-запросов;
  - отчёты, `.comment.md` и `.harness-stderr.log` — в папке `report.output_path`.

  `--scratch-dir` — флаг CLI, а не настройка конфига.
- **Движок.** `pipeline.run_review` сам читает конфиг по `config_path` и пишет `prompt.md`/stderr рядом с worktree. `managed_worktree` перед каждым прогоном вызывает `cleanup_orphaned_worktrees(repo, scratch)`: это удалит и чужой живой worktree, если два прогона делят одну scratch-папку.
- **GitLab-адаптер.** `GitLabClient.post_note` ничего не возвращает. Методов редактирования и удаления note нет.
- **Проекты.** `gitlab.projects[*]` — только `path`/`local_repo`/`remote`. `design.md` Change 2 отложил per-project переопределения на этот change.
- **Пути.** Все относительные пути конфига разрешаются от рабочей папки процесса.

## Goals / Non-Goals

**Goals**
- Python-часть остаётся «одним вызовом без знания о вызывающем»: всё Windows-специфичное про расписание живёт только в PowerShell-скрипте.
- После прохода без `--debug` в `<work_dir>/tmp/` пусто. Всё, что осталось на диске, лежит в `<work_dir>` в понятных подпапках и имеет срок жизни.
- Один MR не ревьюится дважды, даже когда проходы идут параллельно на разных машинах. Состояние хранится только в GitLab (`AGENTS.md` §5).
- Конфиг без новых полей загружается и работает.

**Non-Goals**
- Сборка в один exe. Решение 1: задача запускает pip-запускатель из venv.
- Ротация логов по размеру, сжатие, отправка логов куда-либо.
- Свой инструмент мониторинга: следим только встроенными средствами Windows (решение 10).
- Очистка того, что создают не наши процессы в чужих местах:
  - объекты и `FETCH_HEAD` после `git fetch` в локальном клоне;
  - история сессий и логи OpenCode в профиле пользователя.

  Это зафиксировано как ограничение и проверяется вживую (задача 7.2).
- Per-project переопределение `safety`/`harness`/`min_report_chars` и свой GitLab-хост у проекта.

## Decisions

### 1. Регистрация — `scripts/register-task.ps1` поверх модуля `ScheduledTasks`, без бандла

Параметры (все необязательные):

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `-TaskName` | `review-agent-poll` | имя задачи (повторный запуск обновляет её) |
| `-IntervalMinutes` | `30` | интервал повтора |
| `-ConfigPath` | `config.yaml` | передаётся как `--config` |
| `-WorkingDirectory` | папка репозитория (родитель `scripts/`) | «Рабочая папка» задачи |
| `-ReviewAgentPath` | `(Get-Command review-agent).Source` | абсолютный путь к запускателю |
| `-ExecutionTimeLimitHours` | `4` | Task Scheduler завершит зависший проход |
| `-LogonDelayMinutes` | `5` | второй триггер «при входе в систему» с задержкой: проход, пропущенный пока пользователь не вошёл, выполняется после входа; `0` — без триггера |
| `-DryRun` | выкл. | добавляет `--dry-run` |
| `-DebugMode` | выкл. | добавляет `--debug` (имя `-Debug` занято общим параметром PowerShell) |
| `-ShowConsole` | выкл. | запускать `review-agent.exe` с консольным окном; по умолчанию — без окна через `pythonw.exe` (см. ниже) |
| `-RunWhetherLoggedOn` | выкл. | `LogonType S4U` вместо `Interactive` (см. риски) |
| `-Remove` | выкл. | `Unregister-ScheduledTask`, идемпотентно |

**Что делает скрипт**
- Действие: `New-ScheduledTaskAction -Execute <abs exe> -Argument "poll --all --config <cfg> [--dry-run] [--debug]" -WorkingDirectory <dir>`. Передавать `--include-closed` скрипт не умеет вообще.
- Триггеры: `-Once -At (Get-Date) -RepetitionInterval` и `-AtLogOn -User <текущий>` с `Delay` (добавлено по итогам 7.6: пользователю не нужна работа без входа, но пропущенный проход должен выполниться после входа; `StartWhenAvailable` для `Interactive`-задачи этого не гарантирует, а лишний проход безвреден — `IgnoreNew`, lock, claim). Задержка — чтобы успел подняться VPN; проверено, что такой триггер регистрируется без прав администратора.
- Настройки: `-MultipleInstances IgnoreNew`, `-ExecutionTimeLimit`, `-StartWhenAvailable`, работа от батареи разрешена.
- Регистрация: `Register-ScheduledTask -Force`, то есть обновление на месте.
- Проверки до регистрации: exe и конфиг (относительно `WorkingDirectory`) существуют, иначе ошибка без регистрации.
- В конце печатает итоговую команду и подсказку, где смотреть результат (решение 10).

**Без окна по умолчанию** (добавлено по итогам живой проверки 7.5). В режиме `Interactive` консольная программа открывает окно на каждом запуске; закрытие окна обрывает проход (`0xC000013A`). Поэтому по умолчанию задача запускает `pythonw.exe -m review_agent <аргументы>` того же интерпретатора, что и `review-agent.exe` (рядом с ним в venv или уровнем выше в обычной установке). Код выхода сохраняется (`__main__.py` передаёт `main()` в `SystemExit` — до этого `python -m review_agent` всегда завершался с 0). У процесса без консоли каждый консольный потомок (`git`, `glab`, `opencode`) открыл бы своё окно, поэтому все `subprocess`-вызовы получают `CREATE_NO_WINDOW` — только когда своей консоли нет (`proc.no_window_flags`), чтобы в терминале Ctrl+C по-прежнему доходил до `opencode` (cmd.exe → node). `-ShowConsole` возвращает прямой запуск `review-agent.exe` с окном. Отклонено: `conhost.exe --headless` — проверено, что он всегда возвращает 0 и скрыл бы сбои от Планировщика; `powershell -WindowStyle Hidden` — окно всё равно мелькает.

**Почему без бандла.** `ReviewAgentPath` — это не собранный exe, а `.venv\Scripts\review-agent.exe`: маленький запускатель, который создаёт `pip install -e .`. Сборка PyInstaller'ом отклонена:
- `git`, `opencode` и `glab` всё равно ставятся отдельно;
- добавляется шаг сборки на каждое изменение;
- одно-файловые PyInstaller-exe часто дают ложные срабатывания антивируса.

**Отклонённые альтернативы регистрации**
- Подкоманда `review-agent schedule install` — тянет Windows-специфику в пакет.
- `schtasks.exe` строкой — нет `MultipleInstances`/`ExecutionTimeLimit` без XML.
- Только инструкция в README — много шагов, легко забыть `--all` или рабочую папку.

### 2. Рабочая папка — `storage.work_dir`, единственное место записи

```yaml
storage:
  work_dir: ./.review-agent   # по умолчанию ./.review-agent
  retention_days: 7           # положительное целое; null — не удалять по возрасту
```

Раскладка:

```
<work_dir>/
  poll.lock                      lock рабочей папки (решение 6)
  tmp/<run_id>/                  временное: worktree/, prompt.md, safety-note, report.md,
                                 harness-stderr.log, note.json — удаляется сразу после MR
  logs/poll-<время>-<pid>.log    лог прохода (хранится retention_days)
  logs/<время>-<slug>-<iid>.harness-stderr.log   stderr харнесса упавшего ревью (хранится)
  dry-run/<время>-<slug>-<iid>.comment.md        несостоявшийся комментарий (хранится)
  debug/<время>-<slug>-<iid>/    всё из tmp/<run_id>/ кроме worktree (только --debug, хранится)
```

`--scratch-dir` удаляется из обоих CLI. Это **BREAKING** для флага, а поведение по умолчанию работает. Один источник пути — конфиг, поэтому «всё ли удалилось» проверяется одним взглядом на `<work_dir>/tmp/`. `report.output_path` используется только ручным режимом: его отчёт — результат, который человек сам попросил, поэтому он остаётся. Отчёты `poll` временные: результат уже в GitLab.

Отклонено — оставить `--scratch-dir` как переопределение: два источника пути — это именно то, что мешает отследить след на диске.

### 3. Временные файлы удаляются сразу; остатки — в начале следующего прохода

`run_review` пишет всё своё в `tmp/<run_id>/` (так уже устроено для `prompt.md`; отчёт и stderr тоже переезжают туда) и в `finally` удаляет эту папку целиком, а не только worktree. До удаления оркестратор (или ручной CLI) успевает:
- **ручной режим:** скопировать отчёт в `report.output_path`;
- **`poll`, ревью упало:** перенести `harness-stderr.log` в `logs/`;
- **`poll`, `--dry-run`:** сохранить `.comment.md` в `dry-run/`;
- **`--debug`:** скопировать всю папку (кроме `worktree/`) в `debug/`.

В начале прохода, под lock'ом:
1. для каждого включённого проекта — `cleanup_orphaned_worktrees(local_repo, tmp)`;
2. удаление всего содержимого `tmp/`.

Под lock'ом другой живой прогон этой рабочей папки исключён (решение 6), поэтому всё в `tmp/` — гарантированно остатки. `cleanup_orphaned_worktrees` внутри `managed_worktree` остаётся и тоже безопасен по той же причине.

### 4. Удаление хранимых артефактов по сроку

Модуль `src/review_agent/housekeeping.py`, функция `cleanup_expired(work_dir, retention_days, now, log) → int` (число удалённых).

- **Что удаляется:** файлы в `logs/` и `dry-run/` и папки в `debug/`, у которых mtime старше `now - retention_days`.
- **Что не трогается:** ничего вне `<work_dir>` и сам `poll.lock`.
- **Ошибки:** ошибка удаления любого элемента пишется в лог как `warning`, проход продолжается.
- **Когда запускается:** только под lock'ом (значит, проход, упёршийся в lock, ничего не удаляет). Запускается и в `--dry-run`: это локальная уборка, а dry-run касается записи в GitLab.

Альтернатива «оставлять последние N» отклонена: срок в днях предсказуемее для человека.

### 5. Лог прохода — `logging` + двойной вывод

`src/review_agent/passlog.py`: контекст-менеджер `pass_log(logs_dir)`.

- **Файл:** `FileHandler(encoding="utf-8")` на `poll-YYYYMMDD-HHMMSS-<pid>.log`. pid нужен, чтобы проход, упёршийся в lock в ту же секунду, не перетёр чужой файл. Формат — `%(asctime)s %(levelname)s %(message)s`.
- **Вывод:** функции `info`/`warning`/`error` пишут в файл и в консоль. Запись в консоль пропускается, если поток `None`; её ошибки (`OSError`, `UnicodeEncodeError`) глотаются, так что проход от консоли не зависит.
- **Тесты:** `output_fn`/`input_fn` по-прежнему инжектируются.

**Порядок в `run_poll`**
1. Загрузить конфиг. При `ConfigError` — по возможности взять из сырого YAML `storage.work_dir`, иначе использовать значение по умолчанию; залогировать ошибку и выйти с кодом 2.
2. Открыть лог. Первая строка — cwd, путь конфига, версия, рабочая папка, флаги.
3. Проверить интерактивность.
4. Взять lock; отказ тоже логируется.
5. Под lock'ом выполнить решения 3 и 4.
6. Сам проход.
7. Итог и длительность.

В интерактивном режиме в лог попадают список кандидатов и выбранный номер. Ручной режим лог прохода не пишет.

### 6. Lock — на рабочую папку, и для ручного режима тоже

`poll_lock` переезжает в `<work_dir>/poll.lock`, а ручной `review-agent --repo ...` тоже берёт его на время прогона. Иначе ручной прогон и проход, разделяющие `tmp/`, удалили бы друг другу worktree (решение 3). Сообщение для ручного режима — «прогон уже выполняется (PID …)», код 2.

Отклонено — отдельный `tmp/` для ручного режима: прогоны тогда всё равно конфликтуют через `cleanup_orphaned_worktrees` в общем клоне, а ручной прогон во время планового — редкость.

### 7. Claim в GitLab — метка «ревью выполняется»

`publishing.py` получает чистые функции:
- `build_claim_marker(head_sha, started_at)` → `<!-- ai-review-claim: sha=<head> started=<ISO-8601 UTC> -->`;
- разбор claim'ов из notes бота: `(note_id, started_at)`;
- `live_claims(notes, bot, now, ttl)` и `stale_claims(...)`.

Текст claim-комментария: «⏳ AI-ревью коммита `<sha12>` выполняется (начато `<время>`). Комментарий будет заменён отчётом.»

`gitlab.py` получает:
- `post_note(...) → int` — id созданного note из JSON-ответа `glab api`;
- `update_note(project, iid, note_id, body, body_file)` — `--method PUT .../notes/<id> --input <file>`;
- `delete_note(project, iid, note_id)` — `--method DELETE`.

Тело запроса, как и раньше, передаётся только файлом в `tmp/<run_id>/`.

**Алгоритм `_review_one`, вне dry-run**
1. **Свежая проверка.** `list_notes`:
   - маркер ревью бота → `skipped`, «уже отревьюен»;
   - живой claim бота → `skipped`, «ревью уже выполняется (начато …)».
2. **Протухшие claim'ы.** Для каждого `stale_claims` — `delete_note`. Ошибку удаления логируем и продолжаем.
3. **Свой claim.** `post_note(claim)` → `my_id`.
4. **Разрешение гонки.** Снова `list_notes`:
   - если среди живых claim'ов есть note с id меньше `my_id`, то `delete_note(my_id)` → `skipped`, «другой проход взял MR раньше»;
   - id note в GitLab монотонно растут, поэтому меньший id — более ранний claim; часы машин тут не участвуют.
5. **Ревью** (`run_review`). При любой ошибке или негодном отчёте — `delete_note(my_id)` → `failed`.
6. **Перед публикацией** — снова `list_notes`:
   - маркер ревью бота появился → `delete_note(my_id)` → `skipped`;
   - иначе `update_note(my_id, итоговый комментарий)`;
   - если `my_id` удалён кем-то (404) → `post_note(итоговый)`.
7. **Если не удалось удалить свой claim** (шаги 4–6): outcome получает пометку. Claim перестанет блокировать MR через TTL.

**В dry-run** выполняется только шаг 1 (чтение) и ревью. Результат кладётся в `dry-run/`.

Срок жизни claim — `gitlab.claim_ttl_minutes` (по умолчанию 240). README требует, чтобы он был не меньше `-ExecutionTimeLimitHours` задачи, иначе ещё живой проход потеряет claim. Время claim'а берётся из `created_at` note, который выставляет GitLab, а не из маркера. Маркерное `started` нужно только для текста.

Проверка «уже отревьюен» (`is_already_reviewed`) не меняется: любой маркер бота означает «отревьюен».

**Отклонённые альтернативы**
- Только свежая проверка маркера без claim — не видит параллельный проход.
- Локальный реестр «в работе» — противоречит «состояние только в GitLab» и не работает между машинами.
- Лейбл MR вместо комментария — нужны права на изменение MR и виден всем как «статус».
- Отдельный итоговый комментарий с удалением claim — даёт два уведомления и «прыгающую» ленту. Выбрано редактирование, но см. риски про уведомления.

### 8. Переопределения проекта — замена целиком, разрешение до прохода

`GitLabProjectConfig` получает:
- `enabled: bool = True`;
- `reviewers: list[str] | None`;
- `review_drafts: bool | None`;
- `provider: ProviderConfig | None`;
- `skills: list[str] | None`.

`None` означает «не задано, взять глобальное»; `[]` для `skills` — «явно без skill'ов».

Разбор `provider` выносится в общую `_load_provider(data, section)`. `gitlab.reviewers` становится необязательным; у каждого **включённого** проекта эффективный список ревьюеров должен быть непустым, иначе `ConfigError` с именем проекта. Все проекты могут быть выключены.

Функция `effective_settings(config, project)` возвращает эффективные `reviewers`, `review_drafts` и `Config` для движка (`dataclasses.replace(config, provider=..., skills=...)`).

Поверхностное слияние вложенного `provider` отклонено: правило «замена целиком» проще объяснить, и оно не даёт склеить модель одного провайдера с `api_key_env` другого.

**Выключенный проект** пропускается до проверки клона и до запросов в GitLab, без `Outcome`. В логе прохода — одна строка со списком выключенных проектов.

### 9. Движок принимает готовый `Config` и рабочую папку

`run_review(..., config: Config | None = None, debug_dir: Path | None = None)`, рабочая папка берётся из `config.storage`. `polling._review_one` передаёт эффективный конфиг проекта и строит шапку комментария через `build_model_string(effective.provider)`.

Отклонено — отдельные параметры `provider=`/`skills=`: движок читает и `harness`/`safety`, поэтому один объект конфига проще держать согласованным.

### 10. Наблюдение за задачей — только встроенные средства Windows

Кода нет — только раздел README «Как следить за задачей». В нём:
- **Планировщик заданий** (`taskschd.msc`): «Состояние», «Время прошлого/следующего запуска», «Результат последнего запуска». Коды: `0x0` — ок; `0x1` — какой-то MR упал; `0x2` — проход не стартовал; `0x41301` — выполняется сейчас; `0x41306` — завершён по лимиту времени. Ещё там: вкладка «Журнал» (один раз включить «Включить журнал всех заданий») и кнопки «Выполнить»/«Завершить».
- **Диспетчер задач** → «Подробности»: CPU и память у `review-agent.exe`, `python.exe`, `opencode`/`node.exe`, `git.exe`.
- **Монитор ресурсов** (`resmon`): диск и сеть этих процессов.
- **Просмотр событий:** `Microsoft-Windows-TaskScheduler/Operational`.
- **PowerShell:** `Get-ScheduledTaskInfo`, `Get-ScheduledTask | Select -Expand Triggers`.
- **Логи прохода:** `<work_dir>/logs/`.

## Risks / Trade-offs

- **[E-mail-уведомление приходит с текстом claim'а, а не с отчётом]** GitLab уведомляет участников MR о новом комментарии, а при редактировании — нет. → Текст claim'а говорит, что отчёт появится в этом же комментарии. Поведение проверяется вживую (задача 7.3). Если неудобно — переход на «новый комментарий + удаление claim» меняет только шаг 6 решения 7.
- **[Claim виден в MR несколько минут]** Ожидаемо: это и есть сигнал «ревью идёт».
- **[Проход убит Task Scheduler'ом по лимиту → claim висит до TTL]** → TTL по умолчанию равен лимиту задачи (4 ч). Следующий проход после TTL удаляет его и берёт MR.
- **[TTL меньше реальной длительности ревью]** Второй проход сочтёт живой claim протухшим. → README требует TTL ≥ лимита задачи. Одно ревью — 3–4 мин, лимит — часы.
- **[`glab api` PUT/DELETE и формат ответа POST на `glab 1.115.0`]** → Проверить вживую (задача 7.1). Ответ POST парсится тем же `_parse_json_stream`.
- **[Удалено всё временное, а ревью нужно разобрать]** → stderr упавшего ревью сохраняется автоматически, остальное — повторить с `--debug`.
- **[След вне `<work_dir>`: git-объекты в клоне, история OpenCode в профиле]** → Не наши файлы и не удаляются (Non-Goals). Задача 6.2 фиксирует, что именно остаётся после прохода, чтобы решить, нужна ли отдельная мера (например, настройка хранилища OpenCode) в следующем change.
- **[Interactive-задача мелькает консольным окном]** → `-RunWhetherLoggedOn` (S4U) запускает без окна, но без сетевых кредов Windows/DPAPI. Если токен `glab` в keyring или VPN поднимается только в пользовательской сессии, проход упадёт на preflight (код 2, причина в логе). Проверяется вживую (задача 7.6). По умолчанию — `Interactive`.
- **[VPN выключен → каждый проход «GitLab недоступен», код 2]** → Причина в логе прохода; логи ограничены сроком хранения.
- **[Проход дольше интервала]** → `IgnoreNew` и lock; пропущенный интервал безвреден. Claim защищает и от параллельной задачи с другой рабочей папкой. В логе — длительность прохода.
- **[`-RepetitionInterval` без `-RepetitionDuration` на некоторых версиях Windows повторяется не бесконечно]** → Проверить вживую (задача 7.5).
