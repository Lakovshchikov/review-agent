# Design

## Context

Мотивация — в proposal.md, требования — в `specs/`. Здесь то, что
выяснил ручной spike на машине автора (OpenCode v2.0.21, Windows,
ChatGPT-подписка), и что из этого следует для реализации.

- `opencode session export <id>` отдаёт JSON `{info, messages}`. В `info`
  уже есть **агрегат сессии**: `tokens {input, output, reasoning, cache
  {read, write}}`, `model {id, providerID, variant}`, `agent`, `outcome`
  (`succeeded` / `interrupted` / …), `time {created, updated, idle}`,
  `location.directory` (путь worktree прогона, в нём есть наш `run_id`),
  `projectID`. `cost` для подписки всегда 0. У сообщений есть поля `id,
  time, type, agent, previous`. Кроме того, в экспорте **полный текст
  промпта** (описание MR) и ответов.
- `opencode session list` печатает текстом **верхнеуровневые** сессии
  *текущего проекта*: `ses_<id>  <заголовок>  <дата>`, от новых к старым.
  Проект OpenCode определяется по git-репозиторию, worktree того же
  репо попадают в тот же проект. Дочерние сессии существуют
  (`session delete` удаляет «session and its child sessions»), но в
  `list` не видны. В прогонах ревью их пока нет (`opencode stats`:
  `subagents: 0`), и как именно они связаны с родителем, не проверено.
- `opencode stats --json [--project <id>] [--days N]` даёт агрегаты.
  Годится для ручной сверки с журналом.
- `opencode run` имеет `--session <id>`, `--title`, `--format json`.
  Формат ID для `--session` не проверен.
- Прямой `GET chatgpt.com/backend-api/wham/usage` с токеном OpenCode v2
  отвечает 401. Автоматического источника процентов лимитов нет,
  поэтому проценты вводятся интерактивно.
- Windows PowerShell 5.1 портит UTF-8 при `>`. В Python читаем вывод
  opencode с `encoding="utf-8", errors="replace"`, как уже делается в
  `harness.py`.
- `run_review` (`pipeline.py`) не знает проекта и MR. Worktree удаляется
  на выходе из `managed_worktree`, при ошибке harness наружу летит
  `HarnessError`. Интерактивный `poll` ревьюит ровно один выбранный MR.
  Признак консоли — `polling.stdin_is_interactive()`. `PassLog.warning`
  пишет и в консоль, и в файл, а `file_only` только в файл.

## Goals / Non-Goals

**Goals:**
- Расход по каждому прогону в любом режиме собирается без участия
  человека и без обращений к провайдеру модели. Используются только
  локальные команды харнесса.
- Три независимые точки замены: **источник расхода** (харнесс), **цены**
  (внешний справочник), **квота** (сейчас интерактивный ввод). Смена
  провайдера не трогает ни одну из них.
- Запись журнала переносима в OTel/шлюзы без миграции: те же имена
  полей, тот же `run_id` как ключ сверки.
- Изменения во внешнем формате OpenCode **видны сразу**, а не
  обнаруживаются через месяц по пустой сводке.

**Non-Goals:**
- Не храним сырые экспорты сессий и вообще никакой текст. Только числа и
  идентификаторы.
- Не меняем stdout-контракт харнесса (отчёт = stdout `opencode run`) и
  командную строку прогона (`harness.command`).
- Не делаем UI. Сводка — CLI с выводом в CSV/JSON для Excel.
- Не делаем автоматический замер квоты, OTLP-экспорт и строку расхода
  в комментарии к MR (бэклог).

## Decisions

### 1. Источник расхода — после прогона, поиск сессии по пути worktree, дети рекурсивно

После `invoke_harness` (успешного или с `HarnessError`), **ещё внутри
`managed_worktree`**, источник расхода делает следующее:

1. Запускает `usage.session_list_command` (по умолчанию
   `["opencode", "session", "list"]`) с `cwd` = worktree и берёт до 5
   первых ID вида `ses_\S+`.
2. По очереди запускает `usage.session_export_command` (по умолчанию
   `["opencode", "session", "export", "{session_id}"]`). Из JSON берутся
   только `info` и служебные поля сообщений, остальное сразу
   отбрасывается.
3. Первая сессия, у которой `info.location.directory` совпадает с путём
   worktree (`os.path.normcase(os.path.realpath(...))`), — **корневая**
   сессия прогона.
4. **Дочерние сессии.** Из экспорта корневой сессии извлекаются ID
   дочерних, после чего каждая экспортируется и обходится так же
   (обход в ширину). Ограничения: глубина 5, не больше 50 сессий,
   повторно ID не посещается. Как дочерняя сессия связана с
   родителем (`info.parentID` у ребёнка или ID сессии в части
   tool-вызова `task` у родителя), выясняется на живом образце
   (tasks 1.1). Обе формы поддерживаются через одну функцию
   «извлечь ID детей». Если ни одна форма не найдена, считаем, что
   детей нет. Если ограничение превышено, срабатывает предупреждение
   (решение 4), а учитывается то, что успели обойти.

Исполняемый файл резолвится через `shutil.which`, как в `harness.py`.
Каждая команда идёт с таймаутом и `no_window_flags()`.

Итог прогона — сумма по всем сессиям, плюс список `review.sessions[]`
(id, parent, agent, токены по видам, длительность).

**Длительности.** Общая — `time.monotonic()` вокруг `invoke_harness`
(источник правды для «сколько занял прогон»). Длительность сессии —
`max(time.updated, time.idle) − time.created` из `info`, потому что в
spike у прерванной сессии `updated` отстоял от `created` на 4 с, а
`idle` на 53 с. Какое поле правильное, сверяется на живом образце.

**Шаги** — число сообщений ассистента, если их тип однозначно
распознаётся (tasks 1.1). Иначе `null`.

Почему так, а не иначе:
- Путь worktree уникален для прогона и уже лежит в `info`. Сопоставление
  однозначное и не требует ничего добавлять в командную строку прогона.
- `opencode run --session <наш id>` — самый прямой путь, но формат ID
  не проверен, а неверный ID ломает сам прогон ревью. Это возможная
  оптимизация после живой проверки (Open Questions).
- `--format json` меняет stdout-контракт. Чтение `opencode.db`
  напрямую — внутренний формат. `opencode stats` не привязан к прогону.

Источник расхода — интерфейс с реализациями `opencode` (по умолчанию) и
`none`. Он отдаёт нейтральную структуру (`RunUsage`: сессии, итоги,
версия харнесса, проблемы формата) и никогда не бросает исключений.

### 2. Где это в коде: рекордер, передаваемый в `run_review`

`run_review` получает необязательные `usage: UsageRecorder | None`,
метки прогона (`source`, `project`, `mr_iid`) и `quota_prompt:
Callable | None` (решение 6). `polling.py` и ручной CLI создают
рекордер из конфига.

```
managed_worktree -> render prompt
  quota_before = quota_prompt("до ревью") if quota_prompt
  t0
  try:   invoke_harness
  except HarnessError: outcome = failed; raise   (после записи)
  finally (внутри with):
     duration = monotonic() - t0
     quota_after = quota_prompt("после ревью") if quota_prompt
     size     = git diff --numstat base head ; git rev-list --count base..head
     usage    = usage_source.collect(worktree)       # не бросает
     findings = count_findings(report) if report else None
     recorder.write(review_record(...))              # не бросает
```

Запись делается в `finally` внутри блока worktree: так покрыты и успех,
и `HarnessError`, а worktree ещё существует (нужен для `git diff` и
`cwd` команды `session list`). Вопрос «после ревью» задаётся сразу после
харнесса и до публикации, пока человек смотрит в UI. Все ошибки учёта
ловятся внутри рекордера. Предупреждения идут через переданный
callback. `run_review` с `usage=None` ведёт себя ровно как сейчас.

Размер изменения: `base..head` для коммитов, `git diff --numstat base
head` для файлов и строк. base от GitLab уже merge-base. Бинарные
файлы (`-\t-`) считаются в файлах, но не в строках. Промпт рендерится
до замеров и не меняется.

### 3. Схема записи: JSONL, имена OTel `gen_ai.*` + `review.*`

`<work_dir>/usage/ledger.jsonl`, одна запись — одна строка UTF-8
(`ensure_ascii=False`), только дописывание. Пример:

```json
{"schema": "review-agent.usage/1",
 "time": "2026-10-04T12:51:53+03:00", "review.run_id": "1791107508-472e2701",
 "review.source": "poll", "review.project": "b2c/front-shopping", "review.mr.iid": 544,
 "review.base_sha": "...", "review.head_sha": "...",
 "gen_ai.provider.name": "openai", "gen_ai.request.model": "gpt-5.6-terra",
 "review.reasoning_effort": "medium", "review.skills": ["frontend-pitfalls.md"],
 "review.harness.name": "opencode", "review.harness.version": "2.0.21",
 "review.outcome": "succeeded", "review.duration_ms": 312000,
 "gen_ai.usage.input_tokens": 340652,
 "gen_ai.usage.cache_read.input_tokens": 121856,
 "gen_ai.usage.cache_creation.input_tokens": 0,
 "gen_ai.usage.output_tokens": 3696,
 "review.usage.reasoning_tokens": 2269, "review.usage.steps": 4,
 "review.usage.missing_reason": null, "review.usage.format_problems": [],
 "review.sessions": [{"id": "ses_...", "parent": null, "agent": "reviewer",
    "input_tokens": 340652, "cache_read_tokens": 121856, "cache_write_tokens": 0,
    "output_tokens": 3696, "reasoning_tokens": 2269, "duration_ms": 290000}],
 "review.change.files": 12, "review.change.lines_added": 340,
 "review.change.lines_deleted": 85, "review.change.commits": 3,
 "review.findings": {"blocker": 0, "major": 2, "minor": 1},
 "review.quota": {"provider": "openai",
    "before": {"5h": 12, "week": 40}, "after": {"5h": 21, "week": 42}}}
```

- В семантике OTel `gen_ai.usage.input_tokens` — **весь** вход,
  включая кэш. OpenCode отдаёт `input` без кэша, поэтому пишем `input +
  cache.read + cache.write`, а «свежий» вход сводка выводит вычитанием.
  В `review.sessions[]` так же: `input_tokens` — весь вход.
- Для reasoning стандартного имени в стабильной части конвенций нет,
  поэтому оно лежит в `review.*`. Версию конвенций, с которой сверены
  имена, фиксируем в README.
- `review.quota` есть только у интерактивно измеренных ревью. Будущий
  автоматический замер заполнит то же поле (с `"source": "auto"`), и
  сводка не изменится.
- Почему JSONL, а не SQLite: дописывание без схемы и миграций, читается
  руками, переносится в CI как артефакт. Объём ~1–2 КБ на ревью.
- Почему не OTel SDK сейчас: лишняя зависимость ради файла. Запись уже
  совместима по именам. OTLP-sink — будущий change.

Конкурентная запись: ревью пишут журнал под `poll.lock`, его берут и
`poll`, и ручной режим. Сводка только читает журнал и пропускает
нечитаемые строки, сообщая их число.

### 4. Дрейф формата и версии: предупреждение, не ошибка

- Версия: `opencode --version` один раз за процесс (кэш в источнике)
  сравнивается с константой `VERIFIED_OPENCODE_VERSIONS = {"2.0.21"}`.
  Если не совпадает, предупреждение: «OpenCode X не проверен с учётом
  расхода (проверено: 2.0.21) — проверьте записи в журнале».
- Форма: строгая проверка ожидаемых полей и типов `info`
  (`tokens.input/output/reasoning/cache.read/cache.write` — целые,
  `location.directory` — строка, `model.id/providerID`, `time.created`).
  Сюда же относятся строки `session list`, в которых не нашлось ни
  одного `ses_…` при ненулевом выводе, и невалидный JSON экспорта.
  Каждое расхождение даёт запись в `format_problems` с коротким
  описанием (`"info.tokens.cache.read: missing"`). Затронутые числа
  становятся `null`, но частичные данные сохраняются.
- Вывод: в `poll` — `PassLog.warning` (консоль, если она есть, и лог
  прохода всегда), в ручном режиме — stderr. Одинаковые сообщения за
  процесс показываются один раз, следующие повторы только
  подсчитываются.
- Ни одна из этих ситуаций не бросает исключение и не меняет код
  выхода. В Task Scheduler (`LastTaskResult`) это не видно, поэтому
  сводка `usage` в шапке пишет: «записей с проблемами формата за период:
  N».
- «Сессия не найдена» при нормальном формате — это не дрейф: в
  `missing_reason` пишется причина, предупреждение уходит только в
  файл лога (`file_only`). Так прерванные пользователем прогоны не
  спамят консоль.

### 5. Цены: справочник LiteLLM по URL при каждом `usage` + переопределения в его формате

```yaml
usage:
  enabled: true                       # по умолчанию true
  source: opencode                    # opencode | none
  session_list_command: [opencode, session, list]
  session_export_command: [opencode, session, export, "{session_id}"]
  quota_windows: [5h, week]           # окна для интерактивного замера
  price_catalog: https://raw.githubusercontent.com/BerriAI/litellm/main/model_prices_and_context_window.json
  price_overrides:                    # формат записи справочника LiteLLM; приоритет над справочником
    openai/gpt-5.6-terra:             # пример: модель подписки, которой нет в справочнике (цифры условные)
      input_cost_per_token: 0.00000125
      cache_read_input_token_cost: 0.000000125
      output_cost_per_token: 0.00001
```

- `price_catalog` — URL (по умолчанию публичный файл LiteLLM) или
  локальный путь. **Каждый запуск `usage`** загружает его заново. При
  успехе копия сохраняется в `<work_dir>/usage/price-catalog.json`. При
  неудаче используется сохранённая копия с предупреждением «цены могут
  быть устаревшими, копия от <дата>». Если копии нет, предупреждение и
  цены только из переопределений. Загрузка — `urllib` из стандартной
  библиотеки, с таймаутом. Системные прокси учитываются по умолчанию.
- `price_overrides` — записи **в формате справочника** (те же ключи
  `input_cost_per_token`, `output_cost_per_token`,
  `cache_read_input_token_cost`, `cache_creation_input_token_cost`).
  Их можно скопировать из справочника и поправить. Переопределение
  целиком заменяет запись справочника для этой модели, без слияния
  полей. Отсутствующее поле цены считается 0 с пометкой в сводке.
  Ручных таблиц «в своих единицах» нет.
- Поиск записи: `price_overrides["<provider>/<model>"]` → справочник
  `<provider>/<model>` → справочник `<model>`. Reasoning оплачивается
  как output.
- В сводке для каждой модели указан источник цены (`override` /
  `catalog` / `catalog (копия от <дата>)`). Сводка всегда считается по
  текущему справочнику, поэтому старые ревью пересчитываются.
- Цены живут **только в сводке**. В журнале нет денег. Прогоны ревью в
  сеть за ценами не ходят.

### 6. Интерактивный замер квоты

- Включается, только если одновременно: учёт включён, ревьюится ровно
  один MR/диапазон и есть интерактивная консоль
  (`stdin_is_interactive()`). Это интерактивный `poll` (без `--all`) и
  ручная команда из консоли. В `--all`, под Task Scheduler и при `<
  NUL` вопросов нет.
- `pipeline.run_review` получает `quota_prompt` — функцию, которую
  создаёт CLI. Пайплайн не знает про консоль, а тесты подменяют ввод.
- Вопрос по каждому окну из `usage.quota_windows` — про **оставшийся**
  процент, как его показывает UI ChatGPT/Codex (так меньше ошибок ввода:
  в живой проверке «использовано» было введено как остаток). В журнал
  пишется использованный `100 − остаток`, поэтому схема и сводка от
  формулировки вопроса не зависят. Не число или вне
  0–100 → переспросить. Ctrl+C прерывает проход, как и сейчас при выборе
  MR.
- Провайдер замера — `provider.name` эффективного конфига прогона.

### 7. Доля лимитов в сводке — по группе модели

- **Измеренная доля** ревью: `after − before` по окну. Если `after <
  before`, окно сбросилось во время ревью, и замер помечается
  невалидным.
- **Коэффициент** считается для группы `(provider, model, effort,
  окно)` по валидным измеренным ревью группы: `Σ доля / Σ вес`. Вес —
  API-доллары ревью, если модель оценена. Если не оценена, вес —
  сумма токенов (весь вход + output + reasoning), и это указывается.
  Внутри одной модели оба веса сопоставимы. Доллары лучше, потому что
  отражают разную цену кэша и свежего входа.
- **Оценка** для неизмеренного ревью группы: `вес × коэффициент`,
  помечается «оценка, N замеров». У группы без замеров доли нет, есть
  подсказка «сделайте интерактивный прогон с этой моделью».
- Почему по группе: стоимость в лимитах подписки зависит от модели и
  effort. Общий коэффициент смешал бы несопоставимое.
- Ограничение точности: проценты из UI целые, одиночное ревью может
  дать Δ=0–2 %. Сводка показывает число замеров, а точность растёт с их
  количеством. Параллельная работа в ChatGPT/Codex во время замера
  завышает долю: в README рекомендация мерить без параллельной работы.

### 8. CLI `usage`

По образцу `poll` (`cli.main` смотрит на `argv[0]`): `review-agent usage
[--config PATH] [--since <N>d|YYYY-MM-DD] [--until YYYY-MM-DD] [--by
review|mr|model|day] [--format table|csv|json] [--wide]`. По умолчанию:
**весь журнал** (без ограничения периода — для обоснования стоимости нужна
вся накопленная история), `--by review`, `table`. Таблица по умолчанию
**короткая** (ключ группы, `tokens_k`, `min`, `lines`, `B/M/m`, `usd`, доля
по каждому окну с пометкой «изм.»/«оц., n=N») с легендой колонок; `--wide`
печатает все колонки — после живой проверки 25 колонок по умолчанию
оказались нечитаемы в консоли. CSV/JSON всегда со всеми колонками, в
stdout для перенаправления в файл. В шапке: период, число ревью, без
данных о расходе, без цены, с проблемами формата, источник и дата
справочника цен. Команда не трогает GitLab и не вызывает харнесс.
В сеть она ходит только за справочником.

### 9. Рабочая папка

`housekeeping.WorkDir` получает свойство `usage`. Папка не входит в
`RETAINED_AREAS`, уборка `tmp/` её не касается. Создаётся лениво при
первой записи.

### 10. Находки по SEV — эвристика по тексту отчёта

Отчёт — свободный markdown модели. Считаем строки, где слово
`Blocker|Major|Minor` стоит **как метка** (без учёта регистра):
`SEV: Major`, `SEV Major`, `[Major]`, `**Major**`, `(Major)`, `Major:` в
начале заголовка или пункта списка. Одна строка — не больше одной
находки (берётся первая метка). Это приближение: в README прямо сказано,
что это «оценка по отчёту». Альтернатива — просить модель выдавать
машиночитаемый блок находок, но это изменило бы промпт. Промпт — объект
исследования (AGENTS.md п.3), поэтому отклонено.

## Risks / Trade-offs

- [Формат `session export` / `session list` изменится в новой версии
  OpenCode] → Решение 4: явное предупреждение в консоли и логе,
  частичные данные, счётчик в сводке. Шаблоны команд в конфиге, тесты на
  образцах v2.0.21.
- [Связь родитель–ребёнок у сессий не проверена, детей в реальных
  прогонах пока нет] → Обе вероятные формы поддерживаются. Образец с
  субагентом снимается в tasks 1.1. Ограничения глубины и числа, при
  превышении предупреждение.
- [`session list` через background-сервис не видит сессию
  `--standalone`-прогона] → Проверяется живым прогоном. Если так,
  в шаблон добавляется `--standalone` (конфиг или значение по
  умолчанию).
- [Экспорт содержит текст промпта и отчёта] → Парсим в памяти, берём
  только числа и служебные поля, ничего из экспорта не пишем на диск и
  в лог.
- [Справочник LiteLLM недоступен, переехал или сменил формат] →
  Сохранённая копия плюс предупреждение. URL в конфиге. Неизвестный
  формат записи — это «нет цены» с предупреждением, не падение.
- [Эвристика находок ошибается на нестандартном отчёте] → Помечена как
  оценка. Тесты на реальных отчётах. Отчёт в GitLab — источник правды.
- [Доля лимитов грубая (целые %) и может быть завышена параллельной
  работой] → Число замеров видно, есть рекомендация в README.
  Автоматический замер — бэклог.
- [Доп. время после прогона: `--version`, `session list`, экспорты] →
  Локальные команды, секунды, таймаут на каждую.

## Migration Plan

Миграции нет: секция `usage` необязательна, по умолчанию учёт включён с
источником `opencode`. Для конфигов с другим харнессом записи пишутся с
`missing_reason` и предупреждением о версии. Откат — `usage.enabled:
false`. Журнал остаётся, его можно удалить руками.
