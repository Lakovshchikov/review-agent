# Proposal

## Why

Отчёт, опубликованный в MR, ссылается на файлы так, как их видела модель внутри
временного worktree на машине, где шёл прогон. Например, в отчёте по
`web/front-checkout-admin-panel !13` ссылка выглядела как
`[...](E:/Projects/.../.review-agent/tmp/<run>/worktree/src/.../seller-group-page.tsx#L13)`.
Для читателя MR это битая ссылка, к тому же она раскрывает локальный путь. В
отчётах по `b2c/front-shopping !587` встречается другой вариант:
`` `src/.../WidgetRendererProvider.tsx:34` `` без ссылки, и такой путь
приходится искать в репозитории вручную. Ревьюеру нужна ссылка, которая
одним кликом открывает файл в GitLab на нужной строке.

## What Changes

- Перед публикацией (и перед сохранением в dry-run) ссылки на файлы в
  тексте комментария переписываются в ссылки GitLab на файл в
  отревьюенном коммите:
  `<web-url проекта>/-/blob/<head_sha>/<путь>#L<строка>` или
  `#L<начало>-<конец>`. Если строк нет, ссылка ведёт на файл целиком.
- Ссылка закрепляется на head SHA, а не на имени ветки. Так номера строк
  не съезжают после новых пушей, а ссылка продолжает работать после мержа
  и удаления ветки. Это решение пользователя.
- Распознаются оба формата, которые встречались в реальных отчётах:
  markdown-ссылка на абсолютный путь во worktree (в том числе с `#L13` и
  `#L13-L20`) и путь к файлу в inline-коде (`` `path` ``, `` `path:13` ``,
  `` `path:13-20` ``). Путь в inline-коде превращается в ссылку только
  тогда, когда такой файл действительно есть в отревьюенном коммите. Файл,
  удалённый в MR, получает ссылку на base-коммит.
- Абсолютные пути временного worktree, которые не удалось превратить в
  ссылку (например, внутри блоков кода), заменяются путями относительно
  корня репозитория, так что локальные пути машины в комментарий не
  попадают.
- Если переписать ссылки не получилось (например, git не отдал список
  файлов коммита), отчёт всё равно публикуется. Ссылки в этом случае
  переписываются частично, а в лог прохода пишется предупреждение.
- Промпт ревью и методология не меняются (см. AGENTS.md п.3). Ручной
  режим `review-agent` без GitLab по-прежнему пишет отчёт как есть.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `review-publishing`: добавляется требование, чтобы ссылки на файлы в
  опубликованном комментарии (и в dry-run-копии) вели на файл в GitLab в
  отревьюенном коммите и чтобы в комментарий не попадали локальные пути
  временного worktree.

## Impact

- Код: новый модуль чистой логики для переписывания ссылок,
  `publishing.py`/`polling.py` (вызов перед `format_comment`),
  `pipeline.py` (`ReviewResult` дополнительно возвращает путь worktree
  прогона), `worktree.py` (список путей дерева коммита через
  `git ls-tree`).
- Внешние вызовы: один дополнительный read-only вызов `git ls-tree` на
  каждый коммит, по которому строятся ссылки (head, при необходимости
  base), в уже подготовленном репозитории (локальном или кэш-клоне).
  Новых обращений к GitLab API нет: web-URL проекта берётся из `web_url`
  MR.
- Новых зависимостей и параметров конфигурации нет.
