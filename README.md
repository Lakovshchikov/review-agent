# review-agent

Автономный движок код-ревью merge request'ов: изолированный `git worktree`
+ agentic-харнесс с подключаемым провайдером модели + прямой review-промпт
→ markdown-отчёт. Полный контекст архитектурных решений — в `/AGENTS.md`.

Два режима:

- **ручной** — `review-agent --repo ... --base ... --head ...`: ревью
  заданного диапазона коммитов в локальном репозитории, отчёт в файл,
  без обращений к GitLab (Change 1, `core-review-engine`);
- **опрос GitLab** — `review-agent poll`: найти MR, где назначен
  ревьюер из конфига, отревьюить и опубликовать отчёт комментарием
  (Change 2, `gitlab-polling-and-publishing`, см. «Опрос GitLab» ниже).

Запуск по расписанию — задача Windows Task Scheduler, которую
регистрирует `scripts/register-task.ps1` (Change 3,
`scheduling-and-multi-repo-config`, см. «Запуск по расписанию» ниже);
сам `review-agent` о расписании ничего не знает.

## Установка

1. Python 3.10+
2. Установить сам пакет и зависимости (editable-режим для разработки):

   ```bash
   pip install -e ".[dev]"
   ```

3. Установить [OpenCode](https://opencode.ai) (`opencode --version`
   должен работать в PATH) и настроить провайдера: `opencode auth login`
   для облачного провайдера (Claude/Codex), или `ollama pull <model>`
   для локальной модели. `review-agent` вызывает харнесс как внешний
   процесс — он не входит в зависимости этого пакета.
4. Только для `review-agent poll`: установить [`glab`](https://gitlab.com/gitlab-org/cli)
   и **заранее** авторизовать его на вашем GitLab:
   `glab auth login --hostname <hostname>`. Комментарии публикуются от
   имени этой учётной записи; кредов в конфиге `review-agent` нет.

## Конфигурация

Скопируйте `config.example.yaml` в `config.yaml` и отредактируйте.
Синтаксис ниже сверен с реальным OpenCode CLI v2.0.21 (`opencode --help`,
`opencode run --help`, `opencode debug agents`, схема
`opencode.ai/config.json`) — не предположение, а проверенные факты:

```yaml
provider:
  name: anthropic              # информационное имя — харнесс сам резолвит провайдера
  model: claude-sonnet-4-5
  # Явный reasoning effort — не оставляем харнессу default. У OpenCode
  # это "variant" в строке provider/model#variant (#high/#medium/#low).
  # ВАЖНО: variant есть не у всех моделей — для локальных (Ollama) без
  # вариантов любой суффикс ломает вызов ("Variant unavailable",
  # проверено вживую). Для них ставьте явно `reasoning_effort: null`.
  reasoning_effort: medium
  api_key_env: ANTHROPIC_API_KEY   # имя переменной окружения с ключом — сам ключ сюда не кладём

harness:
  command:                     # плейсхолдеры подставляются адаптером
    - opencode
    - run
    - --standalone              # ОБЯЗАТЕЛЕН — см. раздел "Безопасность" ниже
    - --agent
    - "{agent}"                # -> harness.agent_name (см. ниже про safety)
    - --model
    - "{model}"                # -> "<provider.name>/<provider.model>#<reasoning_effort>"
    - --file
    - "{prompt_file}"           # -> путь к файлу с отрендеренным промптом ЦЕЛИКОМ
    - "Внимательно прочитай вложенный файл целиком и строго следуй его инструкциям."
                                 # ^ ОБЯЗАТЕЛЬНО --file, не позиционный "{prompt}" текст —
                                 #   см. "Критичный баг" ниже
  agent_name: reviewer          # имя read-only агента, генерируемого в opencode.json
```

### Секция `storage`: рабочая папка и срок хранения

```yaml
storage:
  work_dir: ./.review-agent   # по умолчанию ./.review-agent
  retention_days: 7           # logs/, dry-run/, debug/; null — не удалять по возрасту
  repo_retention_days: 30     # кэш-клоны repos/ (с последнего использования); null — не удалять
```

Всё, что `review-agent` пишет на диск, лежит только в `work_dir` (кроме
итогового отчёта ручного режима — он идёт в `report.output_path`).
Подробно, что там лежит и когда удаляется, — раздел «Рабочая папка и что
остаётся на диске» ниже.

### Секция `gitlab` (только для `review-agent poll`)

```yaml
gitlab:
  hostname: gitlab.example.local
  reviewers: [ai-reviewer]        # MR берётся, если хоть один из них назначен ревьюером
  review_drafts: false            # draft-MR пропускаются по умолчанию
  min_report_chars: 200           # более короткий/пустой отчёт не публикуется
  claim_ttl_minutes: 240          # срок жизни claim «ревью выполняется», см. «Защита от двойного ревью»
  projects:
    - path: b2c/front-shopping    # без local_repo: review-agent сам держит кэш-клон
    - path: b2c/front-tools
      local_repo: C:/repos/front-tools
      remote: origin              # опционально (только вместе с local_repo), по умолчанию origin
    - path: b2c/front-checkout    # проект со своими настройками
      local_repo: C:/repos/front-checkout
      reviewers: [ai-reviewer, checkout-lead]
      provider: {name: openai, model: gpt-5, reasoning_effort: high}
      skills: []
    - path: b2c/legacy-admin      # выключен: не опрашивается и не считается сбоем
      local_repo: C:/repos/legacy-admin
      enabled: false
```

Секция необязательна: без неё ручной режим работает как раньше. Кредов
GitLab в конфиге нет — `glab` должен быть заранее авторизован на машине
запуска (`glab auth login --hostname <hostname>`), и комментарии
публикуются от имени этой учётной записи. Подробнее — раздел
«Опрос GitLab» ниже.

**Откуда берётся репозиторий.** Достаточно `path` проекта: если
`local_repo` не указан, review-agent при первом ревью MR этого проекта сам
делает bare-клон `https://<hostname>/<path>.git` в `<work_dir>/repos/`
(без рабочих файлов и без установки зависимостей), авторизуясь через тот
же `glab`, и переиспользует его в следующих проходах — подробнее раздел
«Кэш репозиториев» ниже. Если `local_repo` указан — используется ваш
клон, как раньше. `remote` имеет смысл только вместе с `local_repo`;
`remote` без `local_repo` — ошибка конфигурации.

**Настройки проекта.** У проекта можно переопределить `enabled`,
`reviewers`, `review_drafts`, `provider`, `skills`. Не указано — берётся
глобальное значение. Указано — **заменяет** глобальное целиком, без
слияния: `provider` проекта — это весь блок (со своим обязательным
`reasoning_effort`), `skills: []` — явно без skill'ов при непустом
глобальном списке. Глобальный `gitlab.reviewers` можно не указывать, если
у каждого включённого проекта есть свой. `enabled: false` выключает
проект, не удаляя его из конфига: он не опрашивается, его клон не
проверяется, в итоге прохода он не числится как сбой (в логе — одна
строка со списком выключенных проектов). Модель, которая реально
использовалась, указывается в шапке опубликованного комментария.

### Переключение провайдера

Смена провайдера — только правка `provider` в конфиге, без изменения
кода. Пример для локальной модели через Ollama:

```yaml
provider:
  name: ollama
  model: qwen2.5-coder:32b
  reasoning_effort: null   # у локальных моделей обычно нет variant'ов
```

## Безопасность: read-only permission setup

На каждый прогон в **корень worktree** (не в scratch — проверено, что
OpenCode сам подхватывает `opencode.json` из текущей директории, флага
`--agents-file` не существует) генерируется `opencode.json`,
определяющий ограниченного агента (`harness.agent_name`, по умолчанию
`reviewer`):

```json
{
  "agent": {
    "reviewer": {
      "permission": {
        "bash": { "npm *": "deny", "rm *": "deny", "...": "deny" },
        "edit": "deny",
        "webfetch": "deny",
        "websearch": "deny"
      }
    }
  }
}
```

`bash` — это **DENYLIST паттернов, не allowlist**. Изначально
задумывался allowlist (deny-by-default принципиально безопаснее
denylist'а, который можно обойти чуть другим вызовом команды) — но
**проверено вживую на реальном облачном провайдере** (`openai/gpt-5.6-terra`
через настоящий OpenCode v2.0.21, не стаб): если добавить `"*": "deny"`
в карту `permission.bash`, bash-инструмент становится **полностью
недоступен модели**, даже для паттернов, явно помеченных `"allow"`. Без
catch-all'а неперечисленная команда разрешена по умолчанию. То есть
рабочего способа сказать OpenCode "запрети всё, кроме этих паттернов" в
этой версии нет — пришлось перейти на denylist конкретных опасных
паттернов, принимая его известную слабость (другая формулировка той же
команды может его обойти).

Запись `opencode.json` в worktree безопасна, потому что весь worktree —
одноразовая копия, удаляемая после прогона (см. `worktree.py`), и
`opencode.json` — не то же имя файла, что `AGENTS.md`/`CLAUDE.md`, так
что не перекрывает инструкции самого ревьюируемого репозитория.

Отдельная находка: без флага `--standalone` `opencode run` может
использовать долгоживущий background-сервис, который не знает про
только что созданный worktree (каждый прогон — новая директория) и
падает с `Agent not found` на только что сгенерированном агенте —
`--standalone` в шаблоне команды выше обязателен именно поэтому.

**Что подтверждено вживую (на реальном облачном провайдере, не стабе):**

- ✅ **Allow-сторона**: `git log`, `git status` и подобные (не входящие в
  denylist) реально выполняются через bash у ограниченного агента и
  возвращают настоящий вывод
- ✅ **Deny-сторона**: явно запрещённый паттерн (`npm *`) реально
  блокируется (`Permission denied: shell`), побочного эффекта
  (файла-маркера) не возникает

Единственная оставшаяся оговорка: denylist в принципе слабее allowlist'а
(это известный компромисс, не что-то упущенное) — расширяйте
`denied_bash_patterns`, если заметите, что модель находит обходной путь
через ещё не перечисленный интерпретатор/команду.

### Критичный баг: промпт ОБЯЗАН передаваться через `--file`, не позиционным текстом

Проверено вживую на реальном бенчмарк-MR: если в `harness.command`
передать промпт как позиционный текстовый аргумент (`"{prompt}"`), на
Windows модель получает **только первую строку** промпта и отвечает на
неё одну, без единого вызова инструмента — и процесс при этом
завершается с кодом 0, без видимой ошибки.

Причина: `opencode` на Windows резолвится через PATH в `opencode.CMD`
(npm-шим). `.CMD`-файл Windows может исполнить только через `cmd.exe`, а
`cmd.exe` разбирает свою командную строку построчно — многострочный
аргумент обрывается на первом переводе строки ещё до того, как сам
`opencode`/модель его увидят.

Исправление — передавать промпт файлом через `--file {prompt_file}`
(вложение, а не аргумент командной строки), плюс короткую однострочную
сопроводительную фразу. Подтверждено вживую: модель в этом случае видит
промпт целиком, включая все абзацы, и реально исследует репозиторий. Шаблон
команды в `config.example.yaml` и примеры выше уже используют `--file` —
если переносите старый `config.yaml` с версии до этого исправления,
обязательно обновите `harness.command`.

## Запуск

```bash
review-agent \
  --repo /path/to/local/clone \
  --base <base-sha> \
  --head <head-sha> \
  --mr-title "Заголовок MR" \
  --mr-description "Описание MR" \
  --config config.yaml \
  [--debug]
```

(эквивалентно: `python -m review_agent ...`)

Что происходит за один вызов:

1. Берётся lock `<work_dir>/poll.lock` — пока идёт проход `poll` из той же
   рабочей папки, ручной прогон сразу завершается с кодом 2 («прогон уже
   выполняется»): они делят `<work_dir>/tmp/` и иначе удалили бы друг другу
   worktree.
2. Чистится возможный «осиротевший» worktree от предыдущего прерванного
   прогона.
3. Создаётся изолированный `git worktree` на `--head` в
   `<work_dir>/tmp/<run_id>/worktree` (репозиторий в `--repo` не меняется).
4. В worktree генерируется `opencode.json` (read-only агент), рядом в
   `<work_dir>/tmp/<run_id>/` — safety-note (документация) и review-промпт
   (путь к `AGENTS.md`/`CLAUDE.md`/`docs/` целевого репозитория — если
   найдены — передаются харнессу как путь, не как содержимое).
5. Вызывается харнесс (команда резолвится через PATH — на Windows это
   важно: многие npm-инструменты ставятся как `.CMD`/`.ps1`-обёртки, и
   `subprocess` без `shell=True` не находит их по голому имени).
6. Отчёт записывается по пути из `report.output_path` — это единственный
   файл, который остаётся от ручного прогона.
7. Вся папка `<work_dir>/tmp/<run_id>/` удаляется — независимо от того,
   успешно ли прошёл прогон.

`stderr` харнесса (трейс вызовов инструментов, отказы в правах) в ручном
режиме не сохраняется. Если отчёт подозрительно короткий или пустой,
повторите прогон с `--debug`: тогда промпт, safety-note, отчёт и
`harness-stderr.log` останутся в `<work_dir>/debug/<время>-manual-<sha12>/`.

## Рабочая папка и что остаётся на диске

Всё, что пишет `review-agent`, лежит в `storage.work_dir` (по умолчанию
`./.review-agent`, относительно текущей папки процесса). Единственное
исключение — итоговый отчёт ручного режима (`report.output_path`).

```
<work_dir>/
  poll.lock                      пока идёт прогон; потом удаляется
  tmp/                           временное — пусто после каждого прохода
    <run_id>/                    worktree, prompt.md, safety-note.md, report.md, harness-stderr.log
    mr-<время>-<проект>-<iid>/   тела запросов в GitLab (claim, отчёт)
  logs/
    poll-<время>-<pid>.log                       лог каждого прохода `poll`
    <время>-<проект>-<iid>.harness-stderr.log    stderr харнесса УПАВШЕГО ревью
  dry-run/<время>-<проект>-<iid>.comment.md      несостоявшийся комментарий `--dry-run`
  debug/<время>-<проект>-<iid>/                  всё из tmp/ (кроме worktree) при `--debug`
  repos/                                         кэш-клоны проектов без local_repo
    <проект>-<хэш8>.git/                         bare-клон + метка review-agent-last-used
    .incoming-<id>/                              клон в процессе (только во время прохода)
```

- **Удаляется сразу.** Всё в `tmp/` — после каждого MR, успешного или
  нет. Отчёт `poll` после публикации локально не хранится: он уже в GitLab.
  Проверить, что ничего не осталось, просто: после прохода `tmp/` пуст.
- **Остатки прерванных прогонов** (процесс убит, машина выключена)
  удаляются в начале следующего прохода `poll`, под lock'ом: сначала
  осиротевшие worktree в клонах включённых проектов и во всех кэш-клонах
  (`git worktree remove` + `prune`), затем всё содержимое `tmp/`, затем
  недокачанные (`.incoming-*`) и повреждённые кэш-клоны.
- **Кэш репозиториев `repos/`** — не временное и не «артефакт»: живёт
  между проходами и удаляется только по своему сроку
  `storage.repo_retention_days` с последнего использования (по умолчанию
  30 дней), см. «Кэш репозиториев».
- **Хранится, но не вечно.** `logs/`, `dry-run/` и `debug/`: в начале
  каждого прохода `poll` удаляется всё, что старше `storage.retention_days`
  (по умолчанию 7 дней; `null` — не удалять по возрасту). Число удалённых
  пишется в лог прохода. Проход, который упёрся в lock, ничего не удаляет.
- **`--debug`** (у обеих команд) сохраняет все файлы каждого прогона в
  `debug/`; следующий проход без `--debug` их не трогает — они уходят
  только по сроку хранения.
- Ошибка удаления (файл открыт другим процессом) — предупреждение в логе,
  проход продолжается.
- **Вне `work_dir` review-agent ничего не удаляет.** Что остаётся не от
  нас и не чистится: объекты и `FETCH_HEAD`, которые приносит
  `git fetch` в ваш локальный клон (обычные git-данные клона), и
  собственная история сессий/логи OpenCode в профиле пользователя.

**Переход с Change 1–2 (BREAKING):** флаг `--scratch-dir` убран из обеих
команд — путь задаётся только `storage.work_dir`. Старые папки
`.review-agent-scratch/` и `reports/` (отчёты `poll` раньше копились там)
review-agent больше не использует и не трогает — удалите их вручную один
раз.

## Опрос GitLab: `review-agent poll`

```bash
review-agent poll [--all] [--dry-run] [--include-closed] [--debug] [--config config.yaml]
```

Один вызов = **один проход** и выход (без цикла и демона — кто вызывает
по расписанию, команде всё равно):

1. Открывается лог прохода `<work_dir>/logs/poll-<время>-<pid>.log`.
2. Берётся lock `<work_dir>/poll.lock` — одновременно идёт не больше
   одного прогона из этой рабочей папки (см. ниже).
3. Уборка: остатки прерванных прогонов и устаревшие файлы (см. «Рабочая
   папка»).
4. Проверяется, что `glab` есть в PATH и авторизован на `gitlab.hostname`.
5. Для каждого **включённого** проекта из `gitlab.projects`: открытые MR,
   где хотя бы один из ревьюеров проекта назначен **ревьюером** (draft-MR —
   только если для проекта `review_drafts: true`). MR, на котором уже есть
   наш маркер ревью или живой claim «ревью выполняется», пропускается.
6. Выбор MR (см. «Режимы»), затем **строго по очереди** для каждого:
   свежая проверка маркера и claim → claim-комментарий в MR (см. «Защита
   от двойного ревью») → подготовка репозитория проекта (см. «Кэш
   репозиториев» ниже): одним `git fetch` подтягиваются **целевая ветка MR**
   (в ней лежит base) и `refs/merge-requests/<iid>/head` (голова MR, работает
   и для MR из форков) — в ваш `local_repo` или в наш кэш-клон → ревью тем же движком, что и в ручном режиме, на
   base/head из `diff_refs` MR, с title/description MR и с провайдером и
   skill'ами проекта → проверка отчёта → claim-комментарий заменяется
   отчётом.
7. Итоговая сводка по каждому MR: `published` / `dry-run` / `skipped` /
   `failed` с причиной, ссылкой и путями к сохранённым файлам (лог харнесса
   упавшего ревью, комментарий dry-run, debug-папка).

### Кэш репозиториев

Проекту достаточно `path`: если `local_repo` не указан, review-agent сам
держит копию его репозитория в `<work_dir>/repos/`.

- **Когда клонируется.** Лениво — только когда MR этого проекта реально
  берётся в ревью (уже после claim'а), и не чаще раза за проход. Проект без
  MR на ревьюера и MR, не выбранный в интерактивном режиме, ничего не
  скачивают. В логе прохода — строка «Клонирование ... в кэш ...».
- **Что за копия.** `git clone --bare --no-tags https://<hostname>/<path>.git`:
  полная история, без рабочих файлов, без установки зависимостей. Ревью
  читает код из отдельного worktree в `tmp/`, который удаляется сразу после
  MR; сам кэш остаётся для следующих проходов. Повторное ревью проекта
  клонирует заново только если кэш удалён по сроку или повреждён.
- **Авторизация — через `glab`.** Отдельных кредов для git не нужно: при
  клонировании в конфиг кэш-клона записывается credential helper
  `!'<путь к glab>' auth git-credential` (перед ним — пустой
  `credential.helper=`, чтобы Git Credential Manager не открывал окно
  логина). Токен на диск не пишется — `glab` достаёт его из своего
  хранилища (например, системного keyring) при каждом fetch. Все сетевые
  git-команды идут с `GIT_TERMINAL_PROMPT=0` и `GCM_INTERACTIVE=never`: без
  кредов они падают сразу, а не ждут ввода. В ваш `local_repo` хелпер не
  подставляется — там работает ваша собственная настройка git.
- **Актуализация веток MR.** Перед каждым ревью (и для кэша, и для
  `local_repo`) одним `git fetch` подтягиваются целевая ветка и
  `refs/merge-requests/<iid>/head`. В кэше обновляется ветка
  `refs/heads/<target>`; в `local_repo` — только
  `refs/remotes/<remote>/<target>`, ваши локальные ветки, индекс и файлы не
  меняются. Если какого-то ref'а на сервере нет (GitLab чистит MR-ref'ы
  старых MR), остальные всё равно подтягиваются, а в лог пишется
  предупреждение; движок затем сам пробует `git fetch <sha>`.
- **Сколько живёт.** Каждое ревью обновляет метку
  `review-agent-last-used` в кэш-клоне. В начале прохода (под lock'ом)
  кэш-клоны, не использовавшиеся дольше `storage.repo_retention_days`
  (по умолчанию 30 дней, `null` — не удалять), удаляются — в том числе
  проектов, ещё указанных в конфиге: при следующей нужде они склонируются
  заново.
- **Ошибка клонирования** (нет доступа, `glab` не авторизован) — MR
  `failed` с причиной, claim снимается, остальные MR продолжаются.

Нужно, чтобы `glab` поддерживал `glab auth git-credential` (проверено на
glab 1.115.0 с Git for Windows 2.49). Переход проекта на кэш — удалить из
его записи `local_repo` (и `remote`); откат — вернуть `local_repo`, папку
`<work_dir>/repos/` при желании удалить вручную.

### Лог прохода

Под планировщиком консоли нет, поэтому всё, что проход выводит, дублируется
в `<work_dir>/logs/poll-<ГГГГММДД-ЧЧММСС>-<pid>.log` (UTF-8, каждая строка
с временем и уровнем). Первая строка — версия, флаги, текущая папка,
конфиг и рабочая папка; дальше найденные MR, выбор (в интерактивном
режиме), ход ревью, итог и длительность прохода. Отказы до старта ревью
(проход уже идёт, GitLab недоступен, ошибка конфига) тоже попадают в лог.
Если конфиг не читается совсем, лог пишется в `storage.work_dir` из него,
если его удаётся достать, иначе — в `./.review-agent/logs/`. Ручной режим
лога прохода не пишет.

### Режимы

- **Интерактивный (по умолчанию, на время тестирования).** Выводится
  нумерованный список найденных MR — проект, `!iid`, title, автор и
  **ссылка на MR**; вы вводите номер — ревьюится и публикуется только он.
  `q` — выйти без ревью. Если MR не найдено — сообщение и выход.
- **Автоматический: `--all`.** Все найденные MR ревьюятся по очереди без
  вопросов — режим для планировщика.

Без `--all`, когда stdin не терминал (Task Scheduler, CI, `< NUL`),
команда **не ждёт ввода**, а сразу завершается с кодом 2 и подсказкой про
`--all`.

`--dry-run` работает с обоими режимами: всё как обычно, но в GitLab
ничего не пишется — ни комментария, ни claim'а. Текст несостоявшегося
комментария сохраняется в `<work_dir>/dry-run/`. Рекомендуемый первый
запуск на реальном GitLab: `review-agent poll --dry-run`.

`--include-closed` — искать не только открытые, но и **закрытые и
смёрженные** MR (для тестирования на MR, где комментарий бота никому не
мешает). Работает с обоими режимами; у таких MR в списке видно состояние
(`[merged]`, `[closed]`), остальные правила (ревьюер, draft, маркер) те же.
Если GitLab уже удалил `refs/merge-requests/<iid>/head` старого MR, это не
ошибка: движок ищет коммиты в клоне сам (для смёрженного MR без squash
они обычно уже есть в целевой ветке). Пример:
`review-agent poll --include-closed --dry-run`. В расписании не используется.

### Идемпотентность: маркер в комментарии

Состояние «отревьюено» хранится **только в GitLab**: в конце каждого
комментария — невидимый маркер `<!-- ai-review: sha=<head_sha> -->`.
Учитываются маркеры только в комментариях пользователя, от имени
которого работает `glab` (чужой комментарий с маркером ревью не
отключает).

**MR с любым нашим маркером больше не ревьюится — даже если разработчик
запушил новые коммиты.** Повторное ревью нового diff — запланированная
фича (формат маркера её уже поддерживает). Чтобы отревьюить MR заново
вручную, удалите комментарий бота.

Если ревью упало (fetch, харнесс, пустой/короткий отчёт —
`gitlab.min_report_chars`), отчёт не публикуется, claim удаляется и
маркер не ставится — MR будет кандидатом на следующем проходе. stderr
харнесса такого ревью сохраняется в `<work_dir>/logs/`.

### Защита от двойного ревью: claim в GitLab

Список MR строится в начале прохода, а ревью одного MR идёт 3–4 минуты —
к пятому MR списку уже ~15 минут. Кроме того, проходы могут идти
параллельно: на другой машине или из другой рабочей папки (lock их не
видит). Поэтому прямо перед ревью **каждого** MR:

1. Notes MR перечитываются заново: если там уже есть наш маркер ревью
   или живой claim — MR пропускается (`skipped`, «уже отревьюен» /
   «ревью уже выполняется другим проходом»).
2. Протухшие claim'ы (старше `gitlab.claim_ttl_minutes`, по умолчанию 240)
   удаляются — это следы прохода, который умер посреди ревью.
3. Публикуется **claim-комментарий**: «⏳ AI-ревью коммита `<sha>`
   выполняется (начато …). Этот комментарий будет заменён отчётом.» со
   скрытым маркером `<!-- ai-review-claim: sha=<head> started=<UTC> -->`.
4. Notes перечитываются ещё раз: если два прохода поставили claim почти
   одновременно, побеждает более ранний (меньший id комментария — порядок
   GitLab, не часов машин); проигравший удаляет свой claim и пропускает MR.
5. После ревью **тот же комментарий редактируется** в итоговый отчёт —
   на MR остаётся один комментарий бота. Если ревью упало или отчёт
   негоден, claim удаляется. Если кто-то удалил claim во время ревью, отчёт
   публикуется новым комментарием.

Что видит разработчик: на несколько минут в MR появляется комментарий «⏳
… выполняется», потом на его месте — отчёт. **Учтите:** GitLab шлёт
e-mail-уведомление при создании комментария, а при редактировании — нет,
поэтому письмо придёт с текстом claim'а, а сам отчёт нужно смотреть в MR.

`claim_ttl_minutes` должен быть **не меньше** лимита времени задачи
Task Scheduler (`-ExecutionTimeLimitHours`, по умолчанию 4 ч = 240 мин):
иначе другой проход сочтёт claim ещё работающего прохода брошенным.

**Повис claim** (проход убит, claim не удалился): ничего делать не нужно —
через `claim_ttl_minutes` следующий проход удалит его и возьмёт MR сам.
Если ждать не хочется, удалите комментарий «⏳ … выполняется» в MR вручную.

В `--dry-run` claim не ставится и ничего не удаляется; чужой живой claim
всё равно приводит к пропуску MR.

### Один прогон за раз: `poll.lock`

Пока проход (или ручной прогон) идёт, в `<work_dir>` лежит `poll.lock` с
PID процесса; второй запуск с той же рабочей папкой сразу завершается с
кодом 2 («прогон уже выполняется»). Lock удаляется в конце, в том числе
при ошибке. Если процесс был убит и lock остался, следующий запуск видит,
что процесса с этим PID нет, и спокойно перехватывает lock. Если всё же
требуется ручное вмешательство — удалите файл, путь к нему есть в
сообщении об ошибке. Защиту между разными рабочими папками и машинами
даёт claim (см. выше).

### Коды выхода

| Код | Значение |
|-----|----------|
| `0` | Все выбранные MR опубликованы (или dry-run) либо пропущены; также «нечего ревьюить» и «выбор отменён» |
| `1` | Хотя бы один MR или проект упал — проход при этом доходит до конца |
| `2` | Ничего не запускалось: ошибка конфига / нет секции `gitlab`, `glab` не найден или не авторизован, GitLab недоступен, другой прогон уже идёт, интерактивный режим без терминала |

## Запуск по расписанию (Windows Task Scheduler)

`review-agent` сам ничего не планирует: каждый вызов — один проход.
Периодически вызывает его Task Scheduler, задачу для которого создаёт
`scripts/register-task.ps1` (встроенный модуль `ScheduledTasks`, ничего
ставить не нужно).

**Собирать exe не нужно.** Задача запускает `review-agent.exe` из venv
проекта — маленький запускатель, который создаёт `pip install -e .`
(`.venv\Scripts\review-agent.exe`). Сборка в один бандл (PyInstaller и т.п.)
ничего не даёт: `git`, `opencode` и `glab` всё равно нужны на машине
отдельно, а одно-файловые exe часто ловят ложные срабатывания антивируса.

### Установка, обновление, удаление

Из PowerShell в папке проекта (с активированным venv — тогда
`review-agent` найдётся в PATH сам):

```powershell
# 1. Сначала — расписание в режиме dry-run: ревью идут, в GitLab ничего не пишется
.\scripts\register-task.ps1 -DryRun -IntervalMinutes 15

# 2. Проверили логи — перерегистрировали боевую задачу (то же имя — задача обновляется)
.\scripts\register-task.ps1

# Удалить задачу
.\scripts\register-task.ps1 -Remove
```

Если PowerShell не даёт запускать скрипты (`running scripts is disabled`),
запустите так: `powershell -ExecutionPolicy Bypass -File .\scripts\register-task.ps1 ...`.

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `-TaskName` | `review-agent-poll` | имя задачи; повторный запуск с тем же именем обновляет её |
| `-IntervalMinutes` | `30` | интервал повтора |
| `-ConfigPath` | `config.yaml` | конфиг (относительно рабочей папки) |
| `-WorkingDirectory` | папка проекта (родитель `scripts\`) | «Рабочая папка» задачи — от неё считаются относительные пути конфига, включая `storage.work_dir` |
| `-ReviewAgentPath` | `review-agent` из PATH | путь к `review-agent.exe`, если venv не активирован: `<проект>\.venv\Scripts\review-agent.exe` |
| `-LogonDelayMinutes` | `5` | дополнительный проход через N минут после входа в Windows — наверстать пропущенное, пока вы не были залогинены; `0` — не добавлять |
| `-ExecutionTimeLimitHours` | `4` | Task Scheduler завершит зависший проход; `gitlab.claim_ttl_minutes` должен быть не меньше |
| `-DryRun` | выкл. | `poll --all --dry-run` |
| `-DebugMode` | выкл. | `poll --all --debug` — сохранять артефакты прогонов в `debug/` |
| `-ShowConsole` | выкл. | показывать консольное окно во время прохода (по умолчанию окна нет, см. ниже) |
| `-RunWhetherLoggedOn` | выкл. | запускать и без входа пользователя (см. ниже) |
| `-Remove` | выкл. | удалить задачу (если её нет — не ошибка) |

Задача всегда запускает `poll --all` (без `--all` проход без терминала
отказывается работать) и никогда — с `--include-closed`. Пока проход идёт,
Task Scheduler не запускает второй экземпляр («Не запускать новый
экземпляр»); пропущенный интервал безвреден — MR возьмёт следующий проход.

Перед регистрацией скрипт проверяет, что `review-agent.exe` и конфиг
существуют, и печатает итоговую команду задачи.

**Окно.** По умолчанию проход идёт **без консольного окна**: задача
запускает `pythonw.exe -m review_agent ...` того же Python, что и
`review-agent.exe` (venv: `.venv\Scripts\pythonw.exe`, обычная установка:
`Python310\pythonw.exe`). Так окно не всплывает каждые N минут, и его нельзя
случайно закрыть — закрытие окна обрывает проход (в Планировщике это
результат `0xC000013A`). Код выхода 0/1/2 при этом доходит до
Планировщика как обычно. С `-ShowConsole` задача запускает
`review-agent.exe` напрямую и проход виден в окне — удобно для отладки, но
не закрывайте его. (`conhost.exe --headless` для скрытия не годится —
проверено, что он всегда возвращает 0 и прячет ошибки.)

**Пропущенные проходы.** В обычном режиме задача работает, только пока вы
вошли в Windows. Проход, пропущенный за это время, наверстывается: у задачи
есть второй триггер — «при входе в систему» с задержкой
`-LogonDelayMinutes` (по умолчанию 5 минут, чтобы успел подняться VPN), и
флаг «запускать при первой возможности, если плановый запуск пропущен».

**Режим запуска.** По умолчанию задача работает, **только пока вы вошли в
Windows** (`Interactive`): у неё есть доступ к вашему профилю — токен
`glab`, авторизация OpenCode, VPN вашей сессии. С `-RunWhetherLoggedOn` задача работает и
без входа (тип входа S4U, пароль не хранится), но без сетевых
кредов Windows: если `glab` хранит токен в системном хранилище
(`glab auth login --use-keyring`) или VPN поднимается только в
пользовательской сессии, проход упадёт с «GitLab недоступен» (код 2,
причина в логе). Проверено вживую (задача 7.6 Change 3): под S4U `glab` и
VPN доступны, но вызов модели не проверялся — OpenCode хранит авторизацию
провайдера не в простом файле. **Рекомендуемый режим — обычный
(`Interactive`, без флага)**; S4U использовать только после одной проверки
настоящим ревью.

## Как следить за задачей

Всё — встроенными средствами Windows, ничего ставить не нужно.

**Планировщик заданий** (`Win+R` → `taskschd.msc` → «Библиотека планировщика
заданий» → задача `review-agent-poll`):

- колонки «Состояние» (`Готово` / `Выполняется`), «Время прошлого
  запуска», «Время следующего запуска», **«Результат последнего запуска»**:

  | Результат | Что значит |
  |-----------|-----------|
  | `Операция успешно завершена. (0x0)` | проход прошёл: всё опубликовано/пропущено или нечего ревьюить |
  | `(0x1)` | проход дошёл до конца, но какой-то MR или проект упал — причина в логе прохода |
  | `(0x2)` | проход не стартовал: GitLab/VPN недоступен, ошибка конфига, другой прогон уже идёт — причина в логе |
  | `Задача выполняется. (0x41301)` | проход идёт прямо сейчас |
  | `(0x41306)` | проход был прерван: по лимиту времени (`-ExecutionTimeLimitHours`) или кнопкой «Завершить» |
  | `(0x41303)` | задача ещё ни разу не запускалась |
  | `(0xC000013A)` | проход оборван закрытием консольного окна (только с `-ShowConsole`) или Ctrl+C |
  | `(0x80070002)` / `(0x8007010B)` | Windows не нашла `review-agent.exe` или рабочую папку — перерегистрируйте задачу с правильными `-ReviewAgentPath` / `-WorkingDirectory` |

- вкладка **«Журнал»** внизу — каждый запуск и завершение задачи. Если
  она пуста, один раз включите: правая панель «Действия» → «Включить журнал
  всех заданий»;
- правая панель: **«Выполнить»** — запустить проход сейчас, **«Завершить»**
  — остановить идущий проход, «Отключить» — временно выключить расписание.

**Диспетчер задач** (`Ctrl+Shift+Esc` → вкладка «Подробности»; сортировка
по имени): во время прохода видны `pythonw.exe` (оркестратор; с
`-ShowConsole` — `review-agent.exe` и `python.exe`), `opencode`/`node.exe` (харнесс — основная нагрузка на CPU и
память), `git.exe`, `glab.exe`. Колонки «ЦП» и «Память» показывают, сколько
они едят прямо сейчас.

**Монитор ресурсов** (`Win+R` → `resmon`): те же процессы — диск
(вкладка «Диск») и сеть (вкладка «Сеть», обращения к GitLab и провайдеру
модели). Отметьте процессы галочкой на вкладке «ЦП», чтобы остальные
вкладки показывали только их.

**Просмотр событий** (`Win+R` → `eventvwr.msc` → «Журналы приложений и
служб» → Microsoft → Windows → TaskScheduler → Operational): подробная
история запусков, кодов завершения и причин, почему задача не стартовала
(например, компьютер был выключен).

**PowerShell** — то же коротко:

```powershell
Get-ScheduledTaskInfo -TaskName review-agent-poll   # LastRunTime, LastTaskResult (0/1/2), NextRunTime
Get-ScheduledTask -TaskName review-agent-poll | Select-Object -ExpandProperty Triggers   # интервал повтора
Get-ChildItem .\.review-agent\logs | Sort-Object LastWriteTime | Select-Object -Last 5   # последние логи
Get-Content (Get-ChildItem .\.review-agent\logs\poll-*.log | Sort-Object LastWriteTime | Select-Object -Last 1) -Encoding UTF8
```

**Что именно сделал проход** — только в логе прохода
`<work_dir>\logs\poll-*.log`: найденные MR, кто пропущен и почему, что
опубликовано, что упало, длительность. Логи хранятся `storage.retention_days`
дней. Если длительность прохода приближается к интервалу — увеличьте
`-IntervalMinutes`.
