# AGENTS.md — review-agent

Этот файл — основной источник контекста о проекте для любого агента
(и человека), который здесь работает: архитектурные решения, ограничения,
инструменты, дорожная карта. Читай его перед тем, как планировать или
реализовывать что-либо в этом репозитории.

`openspec/config.yaml` ссылается сюда же — не дублируй туда полный текст,
только короткую отсылку и openspec-специфичный статус.

**Важно не путать:** этот файл описывает разработку самого `review-agent`.
Он НЕ имеет отношения к `AGENTS.md`, который движок (Change 1) генерирует
на лету внутри `git worktree` для КАЖДОГО отдельного прогона ревью —
тот временный, содержит только safety/runtime-инструкции для целевого
(ревьюируемого) репозитория и описан в `design.md` Change 1.

## 1. Что это за проект

Автономный агент для код-ревью Merge Request'ов в приватном VPN-only
GitLab. По расписанию опрашивает заданные репозитории, находит MR, где
назначен сконфигурированный ревьюер, проводит код-ревью через
agentic-харнесс с подключаемым провайдером модели (Claude / Codex /
локальная модель) и публикует markdown-отчёт комментарием к MR.

## 2. Целевая среда

- Разработка и первый запуск — локально, **Windows** (нет нативного
  cron, учитывай это при выборе инструментов планирования/окружения)
- Архитектура должна быть платформонезависимой: тот же код в будущем
  переедет в приватный GitLab CI (Linux-раннер)
- Сейчас — только frontend-репозитории; архитектура не должна жёстко
  завязываться на фронтенд-специфику, в будущем добавятся backend и
  другие стеки

## 3. Ключевой эмпирический вывод, определивший архитектуру

Из предыдущего ~3-недельного исследования автора на этом же классе
задачи (бенчмарк: репозиторий `b2c/m`, MR `!544`, base SHA
`d6a9078821e467208acad0791586e577456c6c96`, head SHA
`eb73b471e4292dc40a78203b3c9f68c91ae4dec1`):

- Recall находок у агента **растёт**, когда он свободно исследует
  репозиторий сам (пустой agent без skill и без подготовленного
  контекста нашёл 9 находок — эталон)
- Recall **падает**, когда поведение жёстко задано: подробный
  workflow-skill дал 3 находки, сильно урезанный skill — 2
- Удаление skill + прямой user-prompt + минимальный runtime-конфиг
  вернули результат к 7 находкам — лучший воспроизводимый baseline
- Размер контекста НЕ коррелирует с качеством (~91k токенов что в
  хорошем, что в плохом прогоне) — не нужно экономить на context budget
  из опасения навредить, дело не в этом
- Полный diff и урезанный diff (разные значения `--unified=N`) давали
  одинаково слабый результат — сам по себе diff как промпт не работает
  хорошо, нужен tool-access к дереву файлов
- Незакрытая на момент решения гипотеза (которую архитектура обходит
  "по построению", не проверяя отдельно): заранее подготовленный
  "brief" с картой MR может анкорить модель и вызывать ранний stopping

Отсюда — прямые архитектурные требования ниже.

## 4. Движок ревью — архитектурные решения

- **Agentic-харнесс с полным tool-access** к изолированному
  `git worktree`, не diff-pipeline (см. п.3). Headless/non-interactive
  запуск. Выбран **OpenCode** как основной харнесс — провайдер
  (Claude/Codex/локальная модель) задаётся одним конфиг-значением, не
  зашит в код; вызов харнесса спрятан за тонким адаптером, чтобы можно
  было заменить харнесс позже без переделки остального pipeline
- **Reasoning effort / thinking level — явный конфиг** на провайдера, не
  оставлять на default (в исходном исследовании это осталось незакрытой
  переменной — не повторяем ошибку)
- **Никакого обязательного workflow-skill.** Методология ревью (что
  проверять: correctness/readability/testability/security/SRP/
  контракты/best practices; SEV Blocker/Major/Minor; допустимы находки
  с неполной уверенностью) идёт ОДНИМ прямым user-prompt'ом на каждый
  запуск, не системным конфигом харнесса
- **Опциональный knowledge-skill слой** — разрешён и будет использоваться
  (например, справочник частых фронтенд-ошибок), но только как подсказка
  ("вот паттерны, которые стоит иметь в виду"), НЕ как ограничение
  исследования. Механизм должен поддерживать toggle per-run (включить/
  выключить 0 или несколько skill-файлов), чтобы можно было A/B-тестировать
  эффект так же, как это делалось в исходном исследовании
- **Подготовка контекста перед запуском — минимальная.** Даём только:
  путь к изолированному worktree, base/head SHA, scratch-путь, title+
  description MR, путь (не содержимое) к `AGENTS.md`/`CLAUDE.md`
  целевого репозитория и к `docs/`, если есть. НЕ готовим заранее
  diff.patch, группировку changed-files, risk-zones, dependency-impact —
  агент строит это сам (`git log`/`git diff`/`git grep` и т.п.). Это
  обязательное требование — агент ДОЛЖЕН получить путь к `AGENTS.md`/
  `CLAUDE.md` целевого репозитория (автоопределение по приоритету:
  `AGENTS.md` → `CLAUDE.md` → `.github/copilot-instructions.md` → ничего
  не найдено, едем дальше без ошибки) — он может ревьюить несколько
  разных проектов и должен понимать их специфику
- **Безопасность во время ревью — строго read-only.** Нельзя выполнять
  код/тесты/сборку/lint из MR; разрешены read-only `git diff`/`show`/
  `grep`/`log`/`blame`/`ls-files`, `rg`, чтение файлов. Агенту не даём
  общий веб-доступ (только вызов сконфигурированного провайдера модели)
  и не даём прав на запись в GitLab — комментарий публикует только
  оркестратор, после получения отчёта, не сам агент. Это осознанно
  жёстче, чем в ручных экспериментах: цикл полностью автономный, без
  присмотра человека.
  **Механизм (проверено вживую на реальном облачном провайдере, не на
  стабе):** изначально задумывался allowlist (`permission.bash` в
  `opencode.json` — разрешить явные read-only паттерны, запретить
  остальное через `"*": "deny"`) — но это НЕ работает в реальном
  OpenCode v2.0.21: `"*": "deny"` делает bash-инструмент полностью
  недоступным модели, даже для паттернов с `"allow"`. Без catch-all'а
  неперечисленная команда разрешена по умолчанию. Поэтому реализован
  **denylist** конкретных опасных паттернов (`npm *`, `rm *`, `*test*` и
  т.п., без `"*"`) — слабее allowlist'а в принципе (обходится другой
  формулировкой команды), но это то, что реально работает. Подтверждено
  живым прогоном: `git log`/`git status` выполняются и дают настоящий
  вывод, `npm *` блокируется с `Permission denied: shell` без побочных
  эффектов. Детали — `src/review_agent/harness_config.py` и README
  Change 1. Также обязателен флаг `opencode run --standalone` — без него
  долгоживущий background-сервис может не знать о только что созданном
  worktree и падать с `Agent not found`

## 5. Интеграция и инфраструктура

- **GitLab API — `glab`** (официальный CLI от GitLab), не
  `python-gitlab` и не свой REST-клиент: листинг MR по reviewer-фильтру
  (`glab mr list --reviewer=<user> --state=opened`), проверка/публикация
  комментариев (`glab mr note`). `python-gitlab` — только fallback на
  то, что неудобно через CLI. GitLab сам рекомендует именно этот
  паттерн для AI-агентов (официальный блог-пост о `glab` + AI agent access)
- **Идемпотентность/состояние — хранится в самом GitLab**, не в
  локальном файле: маркер в комментарии бота вида
  `<!-- ai-review: sha=<head_sha> -->`, ключ `(project, MR iid,
  head_sha)`. Это намеренно даёт будущую фичу "ревью на новый diff
  после правок разработчика" без переделки — новый head_sha просто не
  находит маркера (сейчас не реализуется, но дизайн состояния уже это
  поддерживает)
- **Фильтр опроса** — только MR, где заданный в настройках пользователь
  (или список пользователей) указан как reviewer
- **Планировщик — не пишем свой кроссплатформенный cron/daemon.** Вся
  работа — один идемпотентный CLI-вызов (один проход опроса/ревью, без
  внутреннего state в процессе). Кто его вызывает по расписанию — не
  наша забота: Task Scheduler локально сейчас, cron/systemd timer или
  GitLab CI `schedule` в будущем. Entrypoint не должен знать и не
  должен зависеть от того, кто его вызвал

## 6. Рассмотренные и отклонённые готовые решения

Чтобы не переизобретать этот анализ заново:

- **PR-Agent / Qodo Merge** (open-source, зрелый, популярный) —
  архитектурно diff-pipeline с фиксированной методологией промпта.
  Отклонён: это именно та архитектура, которая эмпирически снижает
  recall под эту задачу (см. п.3)
- **`gitlab-review-agent`** (github.com/antlss) — агентский подход
  (read_file/search_code/multi_diff tool-verification loop), концептуально
  близко к нашей архитектуре. НЕ взят за основу: ~15 звёзд, молодой,
  Linux/Docker/webhook-сервер ориентирован, Windows explicitly не
  поддерживается — рискованная основа для старта на Windows. Паттерны,
  взятые на заметку (НЕ код) для будущих версий, после v1:
  - инкрементальный "smart base SHA" re-review (пересчитывать только
    новые коммиты при повторном ревью после правок)
  - verification loop перед записью finding (перепроверять гипотезу по
    реальному коду, не полагаться на одно чтение) — уже встроено как
    принцип в наш прямой промпт
  - авто-resolve старых AI-тредов при фиксе кода
  - self-generating "best practices" ruleset из истории ревью+фидбека
    (альтернатива/дополнение к ручному knowledge-skill)
- **`pr-review-bot`** (github.com/antoniooreany) — тонкая обёртка над
  PR-Agent с другим LLM-бэкендом. Отклонён по той же причине, что и
  PR-Agent, плюс сам по себе не community-proven (1 звезда, один автор)

Вывод: реально проверенный сообществом слой в этой задаче — не нишевые
GitLab-review-боты (у всех единицы-десятки звёзд), а инструменты уровнем
ниже: `glab` (вендорский), agentic-харнесс (OpenCode и подобные, с
большим adoption). Основа решения — тонкая собственная обвязка поверх
них, а не чужой монолитный бот.

## 7. Дорожная карта

Реализуется отдельными OpenSpec change (не один монолит) — см.
`openspec/changes/`. Каждый change предлагается и применяется
отдельно; следующий change пропозится только после `apply` и ручной
проверки предыдущего на реальном MR, чтобы не планировать поверх
предположений об ещё не реализованном интерфейсе.

1. **`core-review-engine`** — ✅ ЗАВЕРШЁН И ЗААРХИВИРОВАН
   (`openspec/changes/archive/2026-10-02-core-review-engine`). Walking
   skeleton: worktree + минимальный agent-конфиг + прямой промпт + вызов
   харнесса → markdown-отчёт в локальный файл (dry-run, без GitLab).
   Проверен на реальном бенчмарк-MR (`b2c/front-shopping` `!544`) с
   реальным облачным провайдером (`openai/gpt-5.6-terra`) — 5 находок
   (3 Major, 2 Minor), go-решение по переходу к Change 2 зафиксировано.
   В процессе найдены и исправлены два реальных бага транспорта (не
   архитектуры): мохибейк в выводе из-за отсутствия `encoding="utf-8"`
   в `subprocess.run`, и критичный баг — на Windows позиционный
   многострочный промпт обрезался до первой строки при резолвинге
   `opencode` в `.CMD`-шим (исполняется через `cmd.exe`, который режет
   командную строку по переводам строк); исправлено переходом на
   `--file {prompt_file}`. **Не сделано**: количественное сравнение
   находок со списком A–M из исходного исследования — тот handoff-документ
   недоступен на текущей рабочей машине (загружался в другой сессии).
   Детали — `validation-notes.md` в архиве change'а
2. **`gitlab-polling-and-publishing`** — ✅ ЗАВЕРШЁН И ЗААРХИВИРОВАН
   (`openspec/changes/archive/2026-10-02-gitlab-polling-and-publishing`).
   `review-agent poll` — один проход: поиск MR по reviewer-фильтру
   (`glab api`) + метаданные (`glab mr view`), интерактивный выбор MR со
   ссылками по умолчанию / `--all` по очереди, ревью тем же движком,
   публикация отчёта комментарием с маркером `<!-- ai-review: sha=... -->`,
   `--dry-run`, lock `poll.lock` (один проход за раз). Проверен на боевом
   GitLab (`git.platops.ru`, `b2c/front-shopping`): опубликован комментарий
   на `!544`, повторный проход его пропускает. По ходу живой проверки
   добавлен `--include-closed` (тесты на смёрженных MR) и исправлен баг:
   на Windows `isatty()` истинен для `NUL`, из-за чего `poll < NUL` без
   `--all` молча выходил с кодом 0 — теперь проверяется консольный
   дескриптор. Публикация пока от уже авторизованной учётки `glab`; креды
   в конфиге и автоавторизация — бэклог. Детали и что учесть в Change 3 —
   `validation-notes.md` в архиве change'а
3. **`scheduling-and-multi-repo-config`** — следующий change, можно
   пропозить. Task Scheduler (только с `poll --all`), конфиг на несколько
   репозиториев, логирование, очистка scratch-папок прогонов

**Бэклог (отдельные будущие change, не раньше чем после п.3):**
- авто-resolve AI-тредов при фиксе кода разработчиком
- self-generating best-practices ruleset из истории ревью+фидбека
- ревью на новый diff после правок (повторный прогон той же MR)
- backend/другие стеки помимо frontend

## 8. Процесс работы над самим проектом

- Используем OpenSpec (`.claude/skills/openspec-*`, команды `/opsx:*`).
  Один change = одна логическая порция работы, не смешиваем несколько
  change в одной пачке задач
- Change-артефакты (`proposal.md`/`design.md`/`tasks.md`/specs-дельты)
  — файлы в репозитории, не зависят от памяти конкретного чата. Новую
  сессию для следующего change открывать нормально и даже рекомендуется
  — она подхватит состояние через `openspec list`/`status` и этот файл
- После значимых изменений — коммитить и пушить, иначе результат не
  переживёт завершение сессии
- Вывод агента (ревью-отчёты, а также результаты работы OpenSpec-сессий
  в этом репозитории) — по умолчанию на русском языке

## 9. Команды разработки

```bash
pip install -e ".[dev]"     # пакет + pytest (Python 3.10+)
pytest                      # все тесты; харнесс и glab подменяются стабами
review-agent --help         # ручное ревью диапазона коммитов (без GitLab)
review-agent poll --help    # проход опроса GitLab
review-agent poll --dry-run # первый безопасный прогон на реальном GitLab
review-agent poll --all --debug   # проход без вопросов, артефакты прогонов — в <work_dir>/debug/
```

```powershell
.\scripts\register-task.ps1 -DryRun -IntervalMinutes 15   # задача Task Scheduler (Windows), сначала dry-run
.\scripts\register-task.ps1                               # боевая задача (обновляет ту же)
.\scripts\register-task.ps1 -Remove                       # удалить задачу
Get-ScheduledTaskInfo -TaskName review-agent-poll          # LastTaskResult: 0/1/2 = код выхода poll
```

Всё, что пишет review-agent, — в `storage.work_dir` конфига (по
умолчанию `./.review-agent`): `tmp/` пуст после прохода, `logs/` — лог
каждого прохода. Флага `--scratch-dir` больше нет.

Внешние инструменты (не Python-зависимости): `git`, `opencode`
(харнесс), `glab` (только для `poll`, заранее авторизованный —
`glab auth login --hostname <host>`). Линтера в проекте пока нет.
Подробности конфигурации и поведения — README.
